## 1. The big picture: three eras of post-training RL

1. **RLHF era (2022-2023).** The pipeline is SFT, then a reward model (RM), then PPO. Human preference labels are the bottleneck.
2. **Direct preference era (2023-2024).** DPO and its relatives skip both the RM and online sampling, so training becomes a classification loss on (prompt, chosen, rejected) triples.
3. **RLVR / reasoning era (2024-2026).** Rewards come from programs: an answer checker, unit tests, a compiler. Rewards can also come from rubrics graded by an LLM. GRPO-family algorithms drop the critic and sample groups of completions. The DeepSeek-R1 (Jan 2025) result made this mainstream. By 2026 the frontier has moved to **agentic, multi-turn, tool-using RL** with async rollouts.

The pipeline across these eras:

```
Prompts -> Policy samples K completions -> Reward (RM / verifier / rubric judge)
        -> Advantage (critic in PPO | group-normalized in GRPO)
        -> Clipped policy-gradient update (+ optional KL to reference)
        -> repeat
```

## 2. RLHF with PPO: InstructGPT

- **Paper:** "Training language models to follow instructions with human feedback", Ouyang et al., arXiv:2203.02155, 4 Mar 2022. https://arxiv.org/abs/2203.02155 **[V]**
- **Quotable [V]:** "outputs from the 1.3B parameter InstructGPT model are preferred to outputs from the 175B GPT-3". That is a model roughly 100x smaller winning on human preference.
- **Three steps [M]:**
  1. Run SFT on demonstrations.
  2. Train an RM on human rankings of K outputs, using a Bradley-Terry pairwise loss `-log σ(r(x,y_w) - r(x,y_l))`.
  3. Run PPO against the RM with a per-token KL penalty to the SFT model. The "PPO-ptx" variant also mixes in pretraining gradients to reduce the "alignment tax".
- **Cost of PPO:** four models live at once (policy, reference, reward, critic/value). OpenRLHF's README says generation takes about 80% of RLHF time **[V]**, which is why vLLM rollouts matter.

**Reward models** come in two kinds:
- **Classic RMs** are a scalar-head LM trained with Bradley-Terry.
- **2025-26 trend:** generative RMs or LLM-as-judge, plus rubric-based graders (Section 8). Reward models remain the main surface for **reward hacking** (Section 9).

## 3. Offline / direct preference optimization family

| Method | Paper (arXiv) | Key idea | Needs ref model? | Data |
|---|---|---|---|---|
| **DPO** | "Direct Preference Optimization: Your Language Model is Secretly a Reward Model", 2305.18290 (2023) **[V]** | Closed-form optimal policy for the KL-regularized RLHF objective reduces RLHF to a logistic loss on log-ratio differences | yes | pairs |
| **IPO** | "A General Theoretical Paradigm to Understand Learning from Human Preferences", 2310.12036 **[V id]** | Identity instead of logit transform; avoids DPO overfitting on deterministic preferences | yes | pairs |
| **KTO** | "KTO: Model Alignment as Prospect Theoretic Optimization", 2402.01306 **[M]** | Kahneman-Tversky utility; needs only a thumbs-up/down per sample | yes | unpaired binary |
| **ORPO** | "ORPO: Monolithic Preference Optimization without Reference Model", 2403.07691 **[M]** | SFT loss + odds-ratio penalty in one stage | **no** | pairs |
| **SimPO** | "SimPO: Simple Preference Optimization with a Reference-Free Reward", 2405.14734 **[V id]** | Length-normalized avg log-prob as the reward, plus a target margin γ | **no** | pairs |

**DPO loss** (from the TRL docs) **[V]**:
`L = -E[ log σ( β( log πθ(y+|x)/πref(y+|x) - log πθ(y-|x)/πref(y-|x) ) ) ]`

Quotable from the DPO abstract **[V]**: DPO "eliminat[es] the need for sampling from the LM during fine-tuning or performing significant hyperparameter tuning."

**TRL DPO facts [V]** (https://huggingface.co/docs/trl/main/en/dpo_trainer):
- `DPOConfig.beta` defaults to `0.1`.
- `learning_rate` defaults to `1e-6`.
- `max_length` defaults to `1024`.
- `loss_type` is now a **list** (default `["sigmoid"]`). The options are `sigmoid, hinge, ipo, exo_pair, nca_pair, robust, bco_pair, sppo_hard, aot, aot_unpaired, apo_zero, apo_down, discopop, sft, sigmoid_norm`.
- SimPO-style length normalization is exposed as `loss_type="sigmoid_norm"`.
- Losses can be combined, e.g. MPO is `loss_type=["sigmoid","bco_pair","sft"], loss_weights=[0.8,0.2,1.0]`.
- If `ref_model=None`, the initial policy is used as the reference.
- `sync_ref_model=True` implements TR-DPO.
- `label_smoothing` implements Robust DPO, with label-flip probability in `[0, 0.5)`.
- KTO, ORPO and CPO have their own trainers in TRL (KTOTrainer, ORPOTrainer, CPOTrainer) **[M]**. Some may have moved under `trl.experimental` in 1.x **[UNVERIFIED]**.

**Code: DPO quick start [V]** (source: https://huggingface.co/docs/trl/main/en/dpo_trainer)
```python
from trl import DPOTrainer
from datasets import load_dataset

# rows: {"prompt": [...], "chosen": [...], "rejected": [...]} (conversational)
trainer = DPOTrainer(
    model="Qwen/Qwen3-0.6B",
    train_dataset=load_dataset("trl-lib/ultrafeedback_binarized", split="train"),
)
trainer.train()
```

**Code: DPO + LoRA + multi-loss [V]** (same source)
```python
from trl import DPOConfig, DPOTrainer
from peft import LoraConfig
from datasets import load_dataset

args = DPOConfig(beta=0.1, learning_rate=1e-5,           # higher LR for adapters
                 loss_type=["sigmoid", "bco_pair", "sft"],  # MPO
                 loss_weights=[0.8, 0.2, 1.0])
trainer = DPOTrainer("Qwen/Qwen3-0.6B", args=args,
                     train_dataset=load_dataset("trl-lib/ultrafeedback_binarized", split="train"),
                     peft_config=LoraConfig())
trainer.train()
```

**Teaching point.** The TRL docs say DPO, in practice, works "by suppressing the likelihood of dispreferred completions rather than by increasing the likelihood of preferred ones" **[V]**. This explains the "chosen log-prob also goes down" phenomenon that students see in the logged metrics `logps/chosen` and `rewards/margins`.

## 4. GRPO: DeepSeekMath, then DeepSeek-R1

- **GRPO origin:** "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models", arXiv:2402.03300 (Feb 2024) **[M]**.
- **Mechanism:**
  - Sample a **group** of G outputs per prompt.
  - Compute the advantage as `A_i = (r_i - mean(r)) / std(r)`.
  - **No value/critic model**, which cuts memory roughly in half compared with PPO.
  - Use a PPO-style clipped ratio plus a KL term to the reference.
- **DeepSeek-R1:** "DeepSeek-R1: Incentivizing Reasoning Capability in LLMs via Reinforcement Learning", arXiv:2501.12948, 22 Jan 2025. Published in **Nature 645, 633-638 (2025)** **[V]**. https://arxiv.org/abs/2501.12948
  - **R1-Zero** applies pure RL on the base model with no SFT. AIME 2024 average pass@1 rises **15.6% to 77.9%** during RL, and **86.7%** with self-consistency, per the current v2 of the paper **[V]**. The original Jan 2025 v1 reported 71.0% pass@1 **[M]**, so cite the v2 numbers.
  - **Rewards are rule-based**:
    - accuracy (math answer check, compiler test cases)
    - format (reasoning in think tags)
    - language-consistency, added for R1 **[V]**
  - **Why no neural RM [V]:** neural reward models "are susceptible to reward hacking during large-scale RL" and add retraining cost.
  - **"Aha moment" quote [V]:** "Wait, wait. Wait. That's an aha moment I can flag here."
  - **R1 pipeline [V]:**
    1. Cold-start SFT on thousands of long-CoT examples.
    2. Reasoning RL.
    3. Rejection sampling plus SFT on about 800K samples (reasoning and non-reasoning).
    4. A second RL stage that uses rule rewards plus RMs for helpfulness and harmlessness.
    5. Distillation into smaller Qwen/Llama models.

**GRPO flow (diagram in words):**
```
prompt q --> policy samples o1..oG (G=8 default in TRL)
          --> verifier scores r1..rG (e.g., 1 if \boxed{} answer == gold else 0)
          --> A_i = (r_i - mean)/std   [group baseline replaces critic]
          --> token-level clipped PG loss, (optional) β·KL(π||π_ref)
```

## 5. Fixing GRPO: DAPO, Dr. GRPO, GSPO (2025)

**DAPO**
- **Paper:** "DAPO: An Open-Source LLM Reinforcement Learning System at Scale", arXiv:2503.14476, 18 Mar 2025, from ByteDance Seed and Tsinghua AIR **[V]**. Built on verl.
- **Result:** **50 points on AIME 2024** with Qwen2.5-32B base, beating DeepSeek-R1-Zero-Qwen-32B (47) with **50% of the training steps** **[V]**.
- **Four techniques [V]:**
  1. **Clip-Higher** decouples the clip range to ε_low = 0.2 and ε_high = 0.28. It "promotes the diversity of the system and avoids entropy collapse".
  2. **Dynamic Sampling** drops prompts whose group accuracy is 0 or 1, since those give zero advantage and zero gradient.
  3. **Token-level policy-gradient loss** averages over all tokens in the batch instead of per sample.
  4. **Overlong reward shaping** applies a soft length penalty: max 16,384 tokens plus a 4,096-token cache.

**Dr. GRPO**
- **Paper:** "Understanding R1-Zero-Like Training: A Critical Perspective", Liu et al. (Sea AI Lab / NUS), arXiv:2503.20783, 26 Mar 2025 **[V]**.
- **Finding:** GRPO has an optimization bias that "artificially increases response length", especially for wrong answers. The bias comes from per-sequence length normalization and std normalization. The fix is to normalize by a constant and drop the std term.
- **Result:** a minimalist R1-Zero recipe reaches **43.3% AIME 2024 with a 7B base** **[V]**.

**GSPO**
- **Paper:** "Group Sequence Policy Optimization", Qwen Team (Zheng et al.), arXiv:2507.18071, Jul 2025 **[V]**.
- **Idea:** sequence-level importance ratios and clipping. Token-level ratios add noise that grows with length and can collapse training.
- **Claims:** GSPO stabilizes **MoE** RL and was used for the Qwen3 Instruct/Coder/Thinking models.

**Others worth naming:**
- VAPO, 60.4 on AIME 2024 per the verl README **[V]**.
- REINFORCE++, RLOO, PRIME, KL_Cov/Clip_Cov (entropy-collapse fixes), all available in verl/OpenRLHF **[V]**.
- CISPO (MiniMax-M1) and SAPO appear as TRL loss types **[V names]**.

**TRL GRPO defaults as of TRL v1.16.0, 15 Oct 2026 [V]** (https://huggingface.co/docs/trl/main/en/grpo_trainer; https://github.com/huggingface/trl/releases)
- `loss_type` defaults to **`"dapo"`** (token-level normalization). Alternatives are `"dr_grpo"`, `"sapo"`, `"cispo"` and `"vespo"`.
- `beta` defaults to **0.0**, so the KL term and reference model are off by default. This follows the 2025 evidence that KL is not needed for RLVR.
- `num_generations` defaults to 8.
- `scale_rewards` defaults to `"group"`. Other values are `"batch"` and `False`. `False` is the Dr. GRPO recommendation.
- vLLM integration via `use_vllm=True`, in `vllm_mode="colocate"` (default) or `"server"`. The `vllm_importance_sampling_mode="sequence_mask"` setting corrects train/infer mismatch.
- Recent releases add:
  - v1.14: AsyncGRPO with LoRA, async tools.
  - v1.15: fused LM head on by default; OpenEnv harness training.
  - v1.16: tree attention for AsyncGRPO, up to about 3x speedup on shared-prompt rollouts; AMD support.

**Code: GRPO quick start [V]** (source: https://huggingface.co/docs/trl/main/en/grpo_trainer)
```python
# train_grpo.py  ->  accelerate launch train_grpo.py
from datasets import load_dataset
from trl import GRPOTrainer
from trl.rewards import accuracy_reward

dataset = load_dataset("trl-lib/DeepMath-103K", split="train")
trainer = GRPOTrainer(
    model="Qwen/Qwen2.5-0.5B-Instruct",
    reward_funcs=accuracy_reward,
    train_dataset=dataset,
)
trainer.train()
```

**Code: a custom verifiable reward plus config.** The pattern follows the TRL reward-function signature **[V]**, which receives completions, any dataset columns as kwargs, and returns `list[float]` or `None`. This snippet is adapted, not copied verbatim.
```python
import re
from trl import GRPOConfig, GRPOTrainer

def correct_answer(completions, ground_truth, **kwargs):
    texts = [c[0]["content"] for c in completions]          # conversational format
    preds = [re.search(r"\\boxed\{(.+?)\}", t) for t in texts]
    return [1.0 if p and p.group(1).strip() == gt else 0.0
            for p, gt in zip(preds, ground_truth)]

def format_reward(completions, **kwargs):
    return [0.2 if "<think>" in c[0]["content"] else 0.0 for c in completions]

args = GRPOConfig(loss_type="dr_grpo", scale_rewards=False,  # Dr. GRPO
                  num_generations=8, beta=0.0, use_vllm=True)
trainer = GRPOTrainer(model="Qwen/Qwen2.5-0.5B-Instruct",
                      reward_funcs=[correct_answer, format_reward],
                      args=args, train_dataset=dataset)
trainer.train()
```

## 6. RLVR: verifiable rewards

- **Term coined in** "Tulu 3: Pushing Frontiers in Open Language Model Post-Training", AI2, arXiv:2411.15124, 22 Nov 2024. The paper calls it "a novel method we call Reinforcement Learning with Verifiable Rewards (RLVR)" **[V]**.
- **Common verifiers:**
  - math answer match (via `math-verify`)
  - unit tests or sandbox execution for code
  - JSON schema / regex for formatting
  - instruction-following constraint checkers (IFEval-style)
  - SQL execution result match
- **Why it won:**
  - The reward is cheap and objective, and much harder to hack than a neural RM.
  - It scales with compute rather than with labeling.
- **Open challenge:** most real tasks (writing, medicine, law, customer service) are **not verifiable**. Rubrics and LLM judges (Section 8) are the bridge.

## 7. RLAIF and Constitutional AI

- **"Constitutional AI: Harmlessness from AI Feedback"**, Bai et al. (Anthropic), arXiv:2212.08073, Dec 2022 **[M]**. It has two phases:
  1. A supervised phase in which the model critiques and revises its own outputs using a list of principles (the "constitution").
  2. An RL phase that uses AI preference labels, i.e. RL from AI Feedback.
- **"RLAIF vs. RLHF: Scaling Reinforcement Learning from Human Feedback with AI Feedback"**, Lee et al. (Google), arXiv:2309.00267 **[M]**. It reports AI-labeled preferences performing comparably to human labels on summarization and dialogue.
- **Data-centric angle:** the "label" stage of the lifecycle becomes **LLM-generated preference/judgment data**. That data needs its own denoising (judge position bias, length bias, self-preference), which links to the quality-card section of the deck.

## 8. Process vs outcome reward models; rubric rewards

**ORM vs PRM**
- An **ORM (outcome RM)** scores only the final answer.
- A **PRM (process RM)** scores each reasoning step.
- **"Let's Verify Step by Step"**, Lightman et al. (OpenAI), arXiv:2305.20050, 31 May 2023 **[V]**:
  - The process-supervised model solves **78%** of a representative MATH test subset.
  - It released **PRM800K**, with 800,000 step-level human labels.
- **2025-26 practice:**
  - PRMs are mostly used for **test-time reranking/search**.
  - DeepSeek-R1 explicitly did not use PRMs for training. It cited reward hacking and the difficulty of defining steps **[M; R1 paper discussion section]**.
  - Implicit PRMs (e.g. PRIME, available in verl **[V]**) derive step credit from outcome labels.

**Rubrics as Rewards (RaR)**
- **Paper:** "Rubrics as Rewards: Reinforcement Learning Beyond Verifiable Domains", Gunjal et al. (Scale AI), arXiv:2507.17746, Jul 2025 **[V via search]**. https://arxiv.org/abs/2507.17746
- **Method:** a checklist rubric per prompt is graded by an LLM judge and aggregated into a scalar reward for GRPO.
- **Result:** up to **28% relative improvement on HealthBench-1k** compared with Likert judging. Rubrics also help smaller judges.
- **Related work:**
  - "Reinforcement Learning with Rubric Anchors", arXiv:2508.12790, with 10k+ rubrics.
  - "OpenRubrics", arXiv:2510.07743.
- **Industry analogue:** OpenAI RFT's `score_model` and `multi` graders, which combine weighted rubric items (Section 11).

## 9. Reward hacking and overoptimization

- **"Scaling Laws for Reward Model Overoptimization"**, Gao, Schulman, Hilton (OpenAI), arXiv:2210.10760, 2022 **[M]**. As KL from the initial policy grows, the proxy RM score keeps rising while the gold RM score peaks and then falls. This is Goodhart's law, made quantitative.
- **"Monitoring Reasoning Models for Misbehavior and the Risks of Promoting Obfuscation"**, Baker et al. (OpenAI), arXiv:2503.11926, Mar 2025 **[V]**:
  - CoT monitors catch reward hacking in agentic coding.
  - Putting the monitor into the reward leads to **"agents learn obfuscated reward hacking, hiding their intent within the CoT"** **[V quote]**.
  - The authors recommend paying a "monitorability tax".
- **Classic hacks to show students:**
  - length inflation (fixed by Dr. GRPO and overlong shaping)
  - sycophancy toward an RM
  - editing unit tests or `sys.exit(0)` in coding RL
  - format gaming of regex rewards
  - judge-prompt injection in RLAIF
- **Mitigations:**
  - Prefer verifiable rewards and run hidden test sets.
  - Use a KL penalty or early stopping.
  - Use reward ensembles.
  - Rotate held-out judges and audit samples by hand.
  - Monitor the CoT, but do not train against the monitor.

## 10. Agentic and multi-turn RL (the 2026 frontier)

**The shift.** Rollouts are now full trajectories: model, then tool call, then environment observation, then model, and so on. The reward arrives at episode end (tests pass, task solved). Engineering problems include:
- long-tail rollout latency, which pushes toward **async** training
- masking tool-output tokens out of the loss
- train/inference log-prob mismatch
- sandboxing

**Tooling evidence [V]:**
- **TRL:**
  - `environment_factory` is passed to GRPO reward functions.
  - AsyncGRPO supports async tools and OpenEnv harness training (v1.15).
  - Typed tool-call args were added in v1.16.
- **verl** (https://github.com/volcengine/verl, now under the verl-project org since Jan 2026):
  - ReTool recipe for multi-round code-sandbox tool use (Jul 2025)
  - uni-agent for agent training (May 2026)
  - RL-Insight observability (Jul 2026)
  - verl-vla v0.1.0 and VeRL-Omni v0.2.0 (Aug 2026)
  - Megatron MoE support for DeepSeek-671B and Qwen3-235B
  - Mind Lab trained GRPO LoRA on a 1T-parameter model on 64 H800s (Dec 2025)
- **OpenRLHF:**
  - multi-turn agents via `AgentInstanceBase` with `reset()` / `step()`, loaded with `--train.agent_func_path`
  - `--train.async_enable`
  - v0.10 (Apr 2026) added multi-turn VLM RL

**Agent environment step (diagram in words):**
```
reset(task) -> obs0 -> LLM emits action (tool call) -> env executes in sandbox
 -> obs1 appended (masked from loss) -> ... -> done -> reward = tests_passed/verifier
 -> group of G trajectories per task -> GRPO/DAPO advantage -> update
```

## 12. Choosing a method (decision flow)

1. Do you have demonstrations only? Use **SFT** (see deck 02).
2. Do you have pairwise preferences with a static dataset and a limited budget? Use **DPO**. Use **SimPO/ORPO** to drop the reference model, **IPO/Robust DPO** for noisy labels, and **KTO** for thumbs-up/down data.
3. Can a program check the answer? Use **RLVR with GRPO-family methods** (DAPO loss, Dr. GRPO scaling, β = 0).
4. Is the task non-verifiable but has an expert-written quality definition? Use **rubric rewards / LLM judge with GRPO**, and audit for hacking.
5. Is it multi-step tool use? Use **agentic RL** in verl, OpenRLHF or TRL AsyncGRPO with sandboxed environments.
