The best engineering case for ADK comes from the ADK team itself: they let Gemini 4 Argon work on the ADK Python codebase for 11 hours with a goal prompt that asked for an unmerged PR with before and after numbers. Step 1: it built a baseline of 4 workloads with 30 runs each and proposed 6 changes across 32 files. Step 2: maintainers shipped 2 and rejected 4; one rejected change passed all 16,892 open-source tests but broke 25 internal Google test targets, and a 17% cache gain held only on a synthetic benchmark. Step 3: the shipped work made a 158-turn run drop from 65.6 to 56.1 seconds, and the post adds an ops tip: warm up each new instance before it takes live traffic. Step 4: Anthropic's April postmortem shows the other side; three small harness and prompt changes passed review, tests and dogfooding and still lowered quality, so they now run per-model evals on every prompt change, soak and roll out gradually. Analogy: a junior engineer who works all night is useful, but a senior still reviews the pull request. A likely question is "Which Contoso changes count as deploys?": the instruction, the model id, plugin config and tool descriptions all go through the same eval and canary as code.
