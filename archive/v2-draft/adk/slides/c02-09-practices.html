Best practices Northwind claims API

Claims API rules: typed outputs, scoped state, one App per folder

1Typed outputs output_schema

  • Put reasoning first in output_schema: +15-24 pts (2608.08254).
  • Check meaning in code after extraction: valid JSON is not correct JSON.
  • Read optional keys with .get(): None fields are dropped.
  • Never set response_schema in generate_content_config: ADK raises.

2Scoped state session.state

  • user: customer, app: tenant config, temp: scratch, no prefix: this chat.
  • Write via state_delta, tools or callbacks: get_session returns a copy.
  • Use a business key as session id (claim-77): retries join one chat.
  • Never store secrets in state: adk web and GET …/sessions/… show them.

3One App per folder agents/claims_api/

  • Name the App like its folder, with underscores: the folder name must be a valid Python identifier.
  • Register plugins on the App, not the Runner: every agent gets them.

import asyncio
from google.adk import Runner
from google.adk.sessions.sqlite_session_service import SqliteSessionService
from google.genai import types
from claims_api.agent import app      # the one App, plugins included

async def main() -> None:
    runner = Runner(app=app, auto_create_session=True,      # no plugins=
        session_service=SqliteSessionService(db_path="claims_sessions.db"))
    msg = types.UserContent(parts=[types.Part(text="Is glass covered?")])
    async for ev in runner.run_async(user_id="u-tom",
            session_id="claim-77", new_message=msg):
        if ev.is_final_response() and ev.content and ev.content.parts:
            print(ev.content.parts[0].text)
    await runner.close()

asyncio.run(main())
This slide collects the chapter into rules you can test in code review; the three groups are independent rules, not a pipeline. Group one, on screen first, is typed output: keep the reasoning field first, because arXiv 2608.08254 measured +15 to 24 points for it, check meaning in code because valid JSON can carry a wrong severity, and read optional keys with .get because null fields such as incident_date are dropped. Group two is state: pick the prefix by lifetime, write only through state_delta, tools or callbacks because get_session returns a copy, and never put secrets in state because adk web and the session GET route show them. The business key claim-77 is the session id we used on the REST and SQLite slides, so a retry joins the same chat. Group three is the deployable unit: the App name equals the folder name, which must be a valid Python identifier, so no hyphens, and plugins live on the App. Last, run_claims.py imports the one App from claims_api.agent instead of building a second one, and adds only the Runner with SQLite sessions; run it from the agents folder. Likely question: "Can I keep plugins on the Runner?" No: that argument is deprecated, and with app= it raises an error.
