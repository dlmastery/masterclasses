Gotcha Deployment

Deploys lose sessions, duplicate instances or return 403 by default

1 · Cloud Run forgets the conversation SymptomAn employee loses the HR conversation after a scale event. CauseNo --session_service_uri: "the deployed container falls back to the in-memory session and artifact services … sessions and artifacts are lost whenever a Cloud Run instance is recycled." Fix--session_service_uri="agentengine://$AGENT_ENGINE_ID", or a SQLAlchemy URL.
2 · two Agent Runtime instances · cli_deploy.py L1893-1898 SymptomTwo instances exist. The client still talks to the old one. CauseWithout --agent_engine_id, every adk deploy agent_engine creates a NEW instance. If an update fails, only a newly created instance is deleted. FixPass --agent_engine_id on every update.
3 · the private service says no Symptom403 Forbidden on curl after --no-allow-unauthenticated. CauseYou sent an access token. FixSend an identity token (gcloud auth print-identity-token). Grant roles/run.invoker to the caller.

deploy.sh · google-adk 2.13.0 · the fixes
# 1: sessions outlive a recycled Cloud Run instance
adk deploy cloud_run --project=$PROJECT --region=$REGION --service_name=contoso-hr \
  --session_service_uri="agentengine://$AGENT_ENGINE_ID" \
  hr_agent -- --no-allow-unauthenticated

# 2: update the same Agent Runtime instance in place
adk deploy agent_engine --project=$PROJECT --region=$REGION \
  --agent_engine_id=$AGENT_ENGINE_ID hr_agent

# 3: a private Cloud Run service wants an identity token
URL=$(gcloud run services describe contoso-hr --region=$REGION \
  --format='value(status.url)')
TOKEN=$(gcloud auth print-identity-token)
curl -X POST -H "Authorization: Bearer $TOKEN" \
  $URL/apps/hr_agent/users/E-1001/sessions/s1

These three defaults bite the Contoso HR assistant on its first production week. First, Cloud Run without a session service URI keeps sessions in memory, so a scale event or a recycled instance throws the employee's conversation away; point it at Agent Runtime sessions or a SQLAlchemy database. Second, the animation shows that every adk deploy agent_engine without an instance id creates a new instance, so CI builds a pile of instances while the client stays on revision 1; pass --agent_engine_id and the deploy updates instance 1 in place. Think of the instance id as a house number: without it, the mover builds a new house each time instead of furnishing the one you live in. Third, a private Cloud Run service rejects an access token with 403; it wants an identity token and the caller needs roles/run.invoker. A likely question: "Why pin versions so tightly?" Because issue 6156 came from an unpinned google-adk resolving to a different version in the cloud than on the laptop. Next: the telemetry defaults from Lab 10 step 2 that also bite in production.
