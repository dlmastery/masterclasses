Step two: the two recorded chats are now a golden evalset, and this is the file you keep in git. Each case stores four things: the user turn to replay, the reference answer for the judge, the expected tool calls in order, and the session the run starts from; the small_refund case for ORD-102 has the same keys with lookup_order and then issue_refund for 79 dollars. We run it with no config file, so ADK prints "Using default criteria" and scores tool_trajectory_avg_score at 1.0 and response_match_score at 0.8; response_match_score is ROUGE-1 word overlap, so a correct answer in other words can fail, which is why the next step brings our own criteria. Think of the evalset as a flight recorder: one good flight, and every new build must fly the same route. A likely question is "what if I mistype a key?": the evalset models use extra="forbid", so "tool_use" instead of "tool_uses" fails with "Extra inputs are not permitted", but the EvalConfig behind test_config.json does not forbid extra keys, so a typo there is silently dropped.
