787 of 4,806 triaged servers (16.4%) touch the filesystem despite non-filesystem labels. 150 confirmed vulnerable. 13 advisories, 2 CVEs in Anthropic's Git MCP server. Approving one call gives the server process host filesystem access.

Which Metadata Matters for LLM Tool Selection in MCP?

The parameter schema is the strongest lever. Flat top-level params were chosen 93.3-100% on Create Issue. Renaming to to recipient_id cut selection to 1-10%. With names-only differences, the first-listed tool won 92-100%.
Use flat, well-named params. Dedupe near-duplicate tools with tool_filter. Shuffle tool order in evals.

Three papers from the last three months change how the Northwind desk picks and runs MCP servers. The first audited 414 live public servers and found that 91.8% have no OAuth, with SSRF to cloud metadata among 68 vulnerabilities, and 41.6% vanished within three days, so a public server is untrusted and unstable by default. The second shows that a tool labelled get_weather can still read your credentials file, because approving one call trusts the whole server process; put stdio servers in a container with one mount and check paths in before_tool_callback. The third shows that the parameter schema, not the tool name, decides which of two equal tools the model picks, and that list order decides it when only names differ. Think of approval like letting a plumber into the house: you approved the sink, but he can walk into every room unless you lock the doors. A likely question: "Is tool_filter enough?" It limits what the model can call, but not what the server process can do, so you need the container too. Next, what MCP tool schemas cost at Uber scale.
