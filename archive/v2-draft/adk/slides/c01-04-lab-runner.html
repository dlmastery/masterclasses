import asyncio
from google.adk.runners import InMemoryRunner
from google.genai import types
from refund_agent.agent import root_agent

APP = "refund_agent"   # match the folder name

async def main() -> None:
    runner = InMemoryRunner(agent=root_agent, app_name=APP)
    # 1) Two-line debugging: creates session "debug_session_id" on first use.
    await runner.run_debug("Is order A-1001 refundable? Changed my mind.", verbose=True)
    # 2) Production loop: explicit session, event stream.
    session = await runner.session_service.create_session(app_name=APP, user_id="cust-dana")
    msg = types.UserContent(parts=[types.Part(text="Is A-1003 refundable? It arrived damaged.")])
    async for event in runner.run_async(user_id="cust-dana", session_id=session.id, new_message=msg):
        for call in event.get_function_calls():
            print(f"  TOOL CALL  {call.name}({call.args})")
        for resp in event.get_function_responses():
            print(f"  TOOL RESULT {resp.name} -> {resp.response}")
        if event.is_final_response() and event.content and event.content.parts:
            print(f"[{event.author}] {''.join(p.text or '' for p in event.content.parts)}")
    # 3) Isolation: a new user/session does not see Dana's history.
    await runner.run_debug("What did I ask before?", user_id="cust-li", session_id="li-1")
    await runner.close()

if __name__ == "__main__":
    asyncio.run(main())
InMemoryRunner bundles in-memory session, artifact and memory services. APP must equal the folder name.
run_debug() creates the session and prints each event. It is "for debugging and experimentation only".
run_async() is the production loop: log every call and result. is_final_response() is false while calls are pending.
A new user and session start with no history. Then close() the runner.

InMemoryRunner gives you a session, artifact and memory service in one line, and its app_name must match the folder name or ADK warns "App name mismatch detected". Use run_debug to look around, but its own docstring says it is for debugging and experimentation only. The production path is the run_async loop: print every function call and every function response, because the trajectory is where agents fail; CXBench (arXiv 2610.25954) found that 55.5% of runs had the right outcome with a non-compliant process. Think of the event stream as a flight recorder: you read it after the landing, not only the arrival time. A common question is "why did my second user see nothing?": sessions are keyed by app, user and session id, so cust-li starts empty, and an unknown id raises "Session not found" unless you create it first or set auto_create_session=True.
