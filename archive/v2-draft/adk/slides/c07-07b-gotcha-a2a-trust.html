Gotcha A2A trust

A2A cards do not enforce auth, and state stays on each side

import os
from google.adk.agents.remote_a2a_agent import AGENT_CARD_WELL_KNOWN_PATH, RemoteA2aAgent
from google.adk.tools.openapi_tool.auth.auth_helpers import token_to_scheme_credential

# the server enforces auth in front: Cloud Run IAM, a gateway or middleware
scheme, cred = token_to_scheme_credential(
    "oauth2Token", "header", "Authorization", os.environ["REFUNDS_ID_TOKEN"])
refund_remote = RemoteA2aAgent(name="refund_agent", timeout=60.0,
    agent_card=f"https://refunds.example.com{AGENT_CARD_WELL_KNOWN_PATH}",
    auth_scheme=scheme, auth_credential=cred)   # data, not state, crosses
This slide covers what an A2A card does not do. First, security_schemes only decorates the card; the docstring says it is not enforced at runtime by the Starlette app, so a call with no token still gets 200 OK. Put Cloud Run IAM, an API gateway or middleware in front, and let the client send a bearer token: token_to_scheme_credential with oauth2Token returns an HTTP bearer scheme and credential that you pass to RemoteA2aAgent. Second, session state never crosses the boundary in either direction: the remote agent's output_key lands in the remote session, so triage reads None; send the data in the message or an artifact, and parse the reply on the triage side. This is by design, and since 2.12.0 ADK logs a warning when it drops state. Third, issue 6461 is open: inbound A2A messages become role='user', so a peer can send confirmed true for a pending tool confirmation, and the v2.8.0 guard was reverted, so keep confirmation-gated tools off agents you serve over A2A. Analogy: a business card does not lock the office door. A likely question: "Does a test in one process catch the state bug?" No, in-process everything works, so test behind a real to_a2a server.
