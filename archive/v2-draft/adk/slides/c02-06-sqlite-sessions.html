claims/claims_followup.py · usage: python claims/claims_followup.py "message"
import asyncio, sys
from google.adk import Agent, Runner
from google.adk.apps import App
from google.adk.sessions.sqlite_session_service import SqliteSessionService
from google.genai import types
claims_followup = Agent(name="claims_followup", model="gemini-3.5-flash",
    instruction="You handle claim {claim_id}. Remember what the user said.")
app = App(name="claims_api", root_agent=claims_followup)
sessions = SqliteSessionService(db_path="claims_sessions.db")   # file in the cwd
async def main(text: str) -> None:
    runner = Runner(app=app, session_service=sessions, auto_create_session=True)
    sid, uid = "claim-77", "u-tom"
    old = await sessions.get_session(app_name="claims_api", user_id=uid, session_id=sid)
    delta = None if old else {"claim_id": sid}                   # seed on first contact
    msg = types.UserContent(parts=[types.Part(text=text)])
    async for ev in runner.run_async(user_id=uid, session_id=sid, new_message=msg,
                                     state_delta=delta):
        if ev.is_final_response() and ev.content and ev.content.parts:
            print(f"[{ev.author}] {ev.content.parts[0].text}")
    s = await sessions.get_session(app_name="claims_api", user_id=uid, session_id=sid)
    print(f"(events stored: {len(s.events)})")
    await runner.close()
asyncio.run(main(sys.argv[1]))

Before: the session is a dict in process memory. Run 2 starts empty.

Import SqliteSessionService from its module. No extra install: aiosqlite is core.

auto_create_session makes claim-77. The first run seeds claim_id once.

Run 2 is a new process. It loads claim-77 from the file and answers.

Same code on Postgres: swap the service class. That one needs google-adk[db].

output · illustrative · two separate processes
$ python claims/claims_followup.py "My car is a 2024 Civic."
[claims_followup] Noted: a 2024 Civic on claim claim-77.
(events stored: 2)
$ python claims/claims_followup.py "Which car did I say I have?"
[claims_followup] You said you have a 2024 Civic.
(events stored: 4)
Same app name claims_api, same user u-tom, same session claim-77 as in Lab 2 step 3, and the same id is stored as claim_id, so there is one key for the claim. The before block uses InMemoryRunner: the session is a Python dict, so when the first process exits the conversation goes with it, and the second process answers that it does not have that detail. The fix swaps the session service: one constructor, SqliteSessionService(db_path="claims_sessions.db"), imported from google.adk.sessions.sqlite_session_service because it is not re-exported, and one Runner argument, session_service=sessions, with auto_create_session=True. SQLite needs no extra install because aiosqlite is a core dependency. The file is created in the current directory; delete it to start fresh. The script seeds claim_id only on first contact; a delta on every run would write the same value in a new event each turn. Run the script twice in two processes: the first run stores 2 events, the second loads claim-77 from the file, answers with the 2024 Civic, and the count goes to 4. Analogy: the in-memory runner is a whiteboard that is wiped when the meeting ends; SQLite is the claim folder in the filing cabinet. For production, install google-adk[db] and asyncpg and use DatabaseSessionService with a postgresql+asyncpg URL. If older services still run ADK 1.x, only 1.28 and later can read sessions that 2.0 writes, so upgrade every reader first.
