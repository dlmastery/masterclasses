Kyndryl first ran ADK agents as HTTP services and wrapped one A2A JSON-RPC request in each Temporal Activity, so a failure anywhere inside the agent meant redoing the whole agent call; the struck-through strip keeps that v1 design on screen for contrast. The official Temporal plugin moves the agentic loop into the Workflow and makes each LLM call and each tool call its own Activity; when a call fails, Temporal retries that exact call with the same context history and the same inputs. The code is the payout agent from this chapter: charge_gateway is your Activity that calls the gateway. Install the pinned versions and start a local dev server; the Worker needs GOOGLE_API_KEY, and the same plugin instance goes to the Client and the Worker, as the Temporal docs show. Walk the ladder: two rows complete, the worker crashes during model call 2, and a new worker replays rows 1 and 2 from history and re-runs only the failed row, shown in amber. To make replay deterministic, ADK moved its time and UUID calls behind google.adk.platform.time and uuid; that is the same reason a uuid4 key in your own replayed code breaks deduplication, as the retry gotcha showed. The integration package is moving: on sdk-python main the module now re-exports temporalio.google_adk from the new temporalio-google-adk package, but 1.34.0 keeps the contrib path on this slide. Analogy: a bank statement, where you re-read the rows you already have and only retry the payment that bounced. Likely question: "Do I need Temporal if ADK has ResumabilityConfig?" ResumabilityConfig checkpoints your ADK workflow; Temporal adds per-call retries and history across workers, and neither one makes the ACME-GmbH payout idempotent for you. Kyndryl published no production numbers, so do not quote any.
