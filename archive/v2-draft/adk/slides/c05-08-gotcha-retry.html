async def pay(ctx: Context, node_input: str):
  key = "payout-" + ctx.invocation_id   # same key on retry and resume
  yield Event(output=f"PAID idempotency_key={key}")
  # "Tool call to resume needs to be idempotent": resume is
  # at-least-once, so the gateway must dedupe on this key.
These three bugs hit the ACME-GmbH payout after the retry lab works; each one shows the buggy code first and then the fix. First, a node body that catches Exception and returns "error" hides the 503 from RetryConfig, so the node ends on attempt 1; the 2.0 migration guide says not to wrap the body like this. Let transient errors raise, and never catch BaseException, because ADK raises NodeInterruptedError, a BaseException, to interrupt a node. Second, issue 7524 is still open: the reporter's graph fans out flaky and send_email under a workflow that carries retry_config; when flaky fails once on a SQLite session, the retry re-runs the finished send_email too, so the customer gets two emails, while a retry on the flaky node itself sends one. The cause is that the finished sibling's output was still being persisted when the batch was cancelled, which is why InMemory passes and SQLite fails, so test resume and retry on the session backend you use in production. Our payout already follows the fix, because the retry sits on pay. Third, a crash between the charge and the persisted event re-runs pay, because resume is at-least-once: a uuid4 key changes on every run, so the gateway cannot detect the second charge, while payout- plus the invocation id stays the same. Think of the idempotency key as a cheque number: the bank pays a given cheque number once, however many times it is presented. Two related points for questions: Pub/Sub triggers create a new session for each redelivery, and since 2.12.0 tools can see the trigger delivery id to detect it; and do not change the graph while runs are paused, because checkpoint versioning is still an open item.
