Interview drill: prove your agent is reliable and safe

A step fails. Do you use RetryConfig, a routed back-edge or ReflectAndRetryToolPlugin?
RetryConfig for exceptions and transient faults: backoff from 1 s to 60 s, completed children are replayed, and the model sees nothing. A back-edge for semantic failures, where the output is valid but wrong: it carries the verifier's reason as feedback and needs a round counter, because graph cycles are not bounded. ReflectAndRetryToolPlugin for tool errors that the model can fix: it sends reflection_guidance, allows 3 retries by default, and needs an extract_error_from_result override for soft errors like {"status": "error"}.
What is the difference between EXACT, IN_ORDER and ANY_ORDER trajectory matching?
EXACT allows no extra and no missing calls. IN_ORDER needs the expected calls in order but allows extra calls. ANY_ORDER ignores the order. EXACT fails on a harmless extra lookup and makes a better plan look worse, so keep it for strict, regulated flows. Add ignore_args or a rubric tool-use metric when the arguments can vary.
For a customer-support agent, do you report pass@k or pass^k? Why?
pass^k: every attempt must succeed, because each customer gets one attempt. At 75% per trial, pass^3 = 0.75³ ≈ 42%, while pass@3 ≈ 98% looks fine. In ADK, set multi_run_config with num_runs: 3 and min_over_runs, or pass_rate with a threshold when some flakiness is acceptable.
Apply the Rule of Two to an email assistant that reads the inbox and can send mail.
It has all three: untrusted email [A], private data [B] and an external send [C]. Drop one per session: a read-only summarizer, or a send tool limited to allow-listed recipients. If the task needs all three, put a RequestInput approval on each send. Then add layers: ModelArmorPlugin, user identity read from trusted state (never from model arguments), egress policy, and output escaping in the UI.
Ask each question and give the room ten seconds before you press. Question 1 tests whether students separate transient, semantic and tool-level failures; strong answers mention that a broad except Exception silently disables RetryConfig. Question 2 tests eval design: the over-strict trajectory is the most common reason a better model looks worse. Question 3 is a numbers question: candidates must compute 0.75 cubed and explain why the customer experiences pass^k. Question 4 is a design question; the best answers remove a capability before they add a filter, and they name a human approval only for the action that needs all three properties. Analogy for the whole chapter: a pilot's checklist does not make the pilot smarter; it makes the flight safe on the pilot's worst day. Likely follow-up from an interviewer: "Where would you put the cheapest verifier in this email agent?" A function node that checks the recipient against the allow-list before the send tool runs.
