AgentOps watches tokens, tool errors and judge scores, not only HTTP status

Agent SLIs (illustrative SLOs)

Availability 99.5% over 28 days
p99 latency < 5 s (docs alert: 5000 ms)
TTFT p95 < 1.5 s for chat
Tokens per invocation ≤ 1.3× baseline
Tool error rate < 1% per tool
Cost per resolved task business budget
Online judge score ≥ baseline − δ
Model Armor blocks alert on a spike

Canary on Cloud Run (practice built on documented revisions)

  1. gcloud run deploy … --no-traffic --tag cand. The candidate gets its own URL and 0% traffic.
  2. agents-cli eval run --url <tag-url>. Evaluate the live candidate before users reach it.
  3. update-traffic --to-revisions REV=1, then 5, 25 and 100%. Hold each step. Keep sessions sticky.
  4. A guard breaks: --to-revisions PREV=100. Shadow agents need stubbed or read-only tools.
Cost is a reliability metric. A loop does not show up as an error. It shows up as tokens per invocation ×10.

Runbook: detect → triage by trace_id → contain (rollback, FallbackModel, lower ADK_MAX_LLM_CALLS, ForceEscalationPlugin, Model Armor fail-closed) → audit side effects (TOOL_COMPLETED rows) → learn: a new must-pass eval case before the fix ships.

Traces follow the OTel GenAI conventions

  • The conventions now live in open-telemetry/semantic-conventions-genai, status Development. input_tokens includes cached tokens; output_tokens includes reasoning tokens.
  • Switches: --otel_to_cloud on adk web and adk deploy. On Agent Runtime: GOOGLE_CLOUD_AGENT_ENGINE_ENABLE_TELEMETRY=true and OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental. Tracing is on by default for new ADK deployments since 2026-06-18. gen_ai metrics come from ADK 2.6.
  • OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT is opt-in. Get user consent first. agents-cli puts no content in spans and full content in access-controlled GCS and BigQuery.
  • BigQuery agent_events: partitioned by DATE(timestamp), clustered by event_type, agent, user_id. Tool events carry tool_origin. The Storage Write API is paid. Deduplicate on event_id.
Breaking in ADK 2.13: OTel GenAI v2 is the default and the call_llm span is gone. Dashboards keyed on it go blank. Update them, or set ADK_TELEMETRY_SCHEMA_VERSION_OPT_IN=otel_semconv_1_36.

# pip install "google-adk[bigquery-analytics]>=2.7.0"
from google.adk.apps import App
from google.adk.plugins.bigquery_agent_analytics_plugin import (
    BigQueryAgentAnalyticsPlugin)

plugin = BigQueryAgentAnalyticsPlugin(project_id="your-gcp-project-id",
                                      dataset_id="your-big-query-dataset-id")
app = App(name="my_agent", root_agent=root_agent, plugins=[plugin])

# daily token SLO per agent (a query over the documented view)
P95_TOKENS = """
SELECT DATE(timestamp) AS day, agent,
  APPROX_QUANTILES(usage_total_tokens, 100)[OFFSET(95)] AS p95_tokens,
  AVG(ttft_ms) AS avg_ttft_ms
FROM `proj.agent_logs.v_llm_response`
GROUP BY day, agent ORDER BY day DESC"""

One view per event type: v_llm_response has usage_total_tokens, ttft_ms and total_ms; v_tool_completed has tool_name, tool_origin and total_ms. The identifiers are verbatim; the SQL is a composition.

Open with the SLI list: a web SRE knows the first two rows; the tokens, judge-score and tool-error rows are new for agents. Step 1 runs a canary: the dial moves 1, 5 and 25 percent while four guards watch error rate, p99, tokens per invocation and judge score. Step 2 shows the failure that HTTP never reports: tokens per invocation jump past 1.5 times the baseline, which is the signature of a loop, and the dial snaps back with --to-revisions PREV=100; then walk the runbook, and stress that the incident ends with a new must-pass eval case. Step 3 opens the trace: invoke_agent contains invoke_workflow, then generate_content {model} and execute_tool {tool}, and the BigQuery rows show the slowest tool came from an MCP server; warn about the 2.13 change that removed call_llm. Steps 4 and 5 show the plugin and an SLO query over v_llm_response. Analogy: a heart monitor that shows only "the patient is breathing" misses a fever; tokens and judge scores are the thermometer. Likely question: "Can Agent Runtime split traffic like Cloud Run?" The fetched docs show no such feature, so the practice is blue/green: deploy a second resource and switch the client.
