Chapter 04 · Durable execution and HITL Interview lens at-least-once

Interview drill: make a paused, crashed or retried run behave correctly

How does human-in-the-loop work on the wire in ADK 2.0?
RequestInput becomes a long-running functionCall. The event lists its interruptId in longRunningToolIds. The client resumes with functionResponse(name="adk_request_input", id=...). Any client that can send a FunctionResponse can resume the run.
rerun_on_resume: true or false?
False: the node completes, and the human reply is its output. True: the node runs again from the top and reads ctx.resume_inputs. A parent that calls ctx.run_node needs True. require_confirmation turns True on for you.
After a crash, the resumed workflow charged the card twice. Why, and what is the fix?
Execution is at-least-once. Since 2.9.0, a failed node runs again on resume. Give each side effect an idempotency key (for example the order id), so the API refuses a repeat. Put a require_confirmation gate on high-risk nodes, and do not change the graph while runs are paused.
Why did your retries never fire?
A broad except Exception swallowed the error, so RetryConfig never saw a failure. Let exceptions propagate, or re-raise. Never catch BaseException: it traps NodeInterruptedError and breaks HITL pauses.

Give students ten seconds for each question before you show the answer. Q1 tests the protocol: a strong candidate says "long-running function call" and names longRunningToolIds and adk_request_input. Q2 tests who owns the reply: with False the reply flows to the next node; with True the same node handles its own question. Q3 is the most common production bug in this chapter: replay is at-least-once, so payments, emails and tickets need idempotency keys. Q4 is a debugging question: retries need an exception, and HITL pauses travel as NodeInterruptedError. Analogy for Q3: a lift button that you press twice must still call the lift once. Likely follow-up: "Where does the idempotency key come from?" Derive it from stable business data, such as the order id, and not from a random value that changes on each attempt.
