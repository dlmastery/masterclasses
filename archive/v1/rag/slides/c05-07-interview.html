Interview: designing agentic RAG

Design a support assistant that sometimes needs SQL, sometimes docs and sometimes nothing.
Put an enum router first: vector | sql | web | none with structured output, so it cannot invent a source. Add an Adaptive-RAG complexity gate: simple questions skip retrieval, complex ones get a multi-step loop. Trace every route and evaluate routing accuracy separately from answer quality.
How do you stop an agentic RAG loop?
Use four stops: a max_iterations cap in the state, a sufficiency grader that ends the loop when the evidence is enough, a token or time budget, and a fallback answer that says “not found” and cites what was searched. Log each pass to detect query drift.
Self-RAG or CRAG for a closed API model?
CRAG. It wraps any generator with a separate retrieval evaluator (T5-large, about 0.77B) and a web-search fallback. Self-RAG needs a fine-tuned model that emits reflection tokens (Retrieve, ISREL, ISSUP, ISUSE). You cannot train those into a hosted model.
Why can DRAGIN not run on a hosted API?
RIND needs token entropy from the logits and the attention that later tokens give each token. QFS needs the self-attention weights over the whole context. Closed APIs do not return attention weights. Use IRCoT or IterDRAG instead: they need only text.

Let the students answer each question before you show the model answer. Question one tests whether they start with the cheapest control: a constrained router and a complexity gate, not a free agent. Question two is the most common failure in production; a strong answer names more than one stop condition and a graceful "not found" path. Question three checks that they know the difference between a trained behaviour (Self-RAG) and a wrapper (CRAG). Question four checks white-box versus black-box access. Analogy for the whole slide: you can add a smoke detector to any house, but you cannot rewire the walls of a rented flat. Likely follow-up: "What do you measure first?" Retrieval recall and routing accuracy, before answer quality.
