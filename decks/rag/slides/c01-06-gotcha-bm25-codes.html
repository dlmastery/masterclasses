# test_bm25.py -- guards for the three fixes in lab2_bm25.py
import bm25s
from kb import IDS
from lab2_bm25 import normalise, bm25_search

def test_codes_survive_tokenizer():                # fix 1: glue codes on both sides
    assert normalise("E-4012") == "E4012"
    assert "e4012" in bm25s.tokenize(normalise("E-4012"), return_ids=False)[0]

def test_k_above_corpus_size():                    # fix 2: k = min(k, len(IDS))
    assert len(bm25_search("refund", k=20)) <= len(IDS)   # 20 of 18: no ValueError

def test_returns_string_ids():                     # fix 3: corpus=IDS gives "c11", not 10
    assert all(d in IDS for d in bm25_search("customer sees E-4012 at checkout"))

def ids_from_positions(positions: list[int]) -> list[str]:
    return [IDS[i] for i in positions]             # for any API that returns positions

Three bugs that every support or IT corpus hits in its first BM25 week. First: the default bm25s token pattern needs two word characters, so "E-4012" loses its "E" and every E-, X- or P-code with the same digits looks the same; glue the code with one shared normalise() on corpus and query, and keep the unit test in CI. Second: bm25s raises a ValueError when k is larger than the corpus; the hybrid run in Lab 4 asks for 20 of 18 chunks, so without the cap it crashes on the first query. Third: a score of 0.000 for a real retriever is almost always an id mapping bug, because bm25s without corpus= and CrossEncoder.rank return positions, not your ids. Analogy: the retriever hands you seat numbers, the answer key lists passenger names. Likely question: "Why not change token_pattern instead?" You can, but normalising the identifiers keeps one rule for every index, including the dense side. test_bm25.py imports the fixes from lab2_bm25.py, so the fixes live in one file.
