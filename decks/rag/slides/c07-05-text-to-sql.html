from neo4j_graphrag.retrievers import Text2CypherRetriever

neo4j_schema = """
Node properties: Person {name: STRING, born: INTEGER};
  Movie {title: STRING, released: INTEGER}
Relationship types: (:Person)-[:ACTED_IN]->(:Movie),
  (:Person)-[:DIRECTED]->(:Movie)
"""
examples = ["USER INPUT: 'Who acted in The Matrix?' QUERY: "
    "MATCH (p:Person)-[:ACTED_IN]->(m:Movie {title: 'The Matrix'}) "
    "RETURN p.name"]
retriever = Text2CypherRetriever(driver=driver, llm=llm,
    neo4j_schema=neo4j_schema, examples=examples)
print(retriever.search(
    query_text="Which movies did Hugo Weaving star in?"))
  • Schema in the prompt, not documents. The LLM writes Cypher from the schema and the examples.
  • Invalid Cypher raises Text2CypherRetrievalError. VectorCypherRetriever starts with a vector search, then expands with Cypher.
  • Vanna 2.0: user-aware agents with row-level security. LinkedIn KG-RAG over tickets: MRR +77.6%, median resolution time −28.6%.
Some answers are not in prose at all; they are rows in a warehouse or paths in a graph database. Then retrieval changes target: you retrieve the schema and a few similar question-to-SQL examples, the LLM writes a query, the database runs it, and errors go back to the LLM for a retry. Analogy: you do not photocopy the whole library catalogue; you ask the librarian who knows the shelves to fetch the exact rows. The numbers are sobering: the BIRD leader is at 82.95 against 92.96 for humans, and on Spider 2.0, with enterprise schemas of over 1,000 columns, an o1-preview agent solves 21.3%. The graph version is the same pattern with Cypher, and neo4j-graphrag gives it to you as Text2CypherRetriever. Close with the decision table, which is the one-slide summary of the whole chapter. Likely question: "How do you stop the LLM from dropping a table?" Run with a read-only role and row-level security, and validate the query before execution.
