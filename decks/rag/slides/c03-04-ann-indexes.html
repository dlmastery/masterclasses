HNSW descends from long links to short links, while IVF-PQ, DiskANN and ScaNN trade memory for recall

Every index is a point on the recall / latency / memory / build-time surface. HNSW (Malkov & Yashunin, IEEE TPAMI 2018) is the default in pgvector, Qdrant, Weaviate, Milvus, Elasticsearch/OpenSearch and FAISS.

PQ

Split a vector into M sub-vectors; code each with 2nbits centroids. 768-d float32: 3,072 B → PQ96x8: 96 B.

DiskANN / Vamana

PQ codes in RAM; graph and full vectors on SSD. SIFT1B on a 64 GB box: >5,000 QPS, <3 ms, 95%+ 1-recall@1.

ScaNN + SOAR

Anisotropic quantization. SOAR spills each vector to a second, near-orthogonal cluster. Vertex AI Vector Search and AlloyDB use it.

HNSW knobs and bytes per vector

  • M: graph degree → memory and recall
  • efConstruction: build quality → build time
  • efSearch: beam width → latency vs recall
  • Flat 4·d · IVFPQ ⌈M·nbits/8⌉+8 · HNSWFlat 4·d + M·2·4
HNSW works like a road network: the top layer is the highway with a few long links, and layer 0 is the street level with every vector. The search enters at the top, moves greedily to the neighbour nearest the query until it cannot improve, drops one layer, and repeats; on layer 0 it runs a beam search of width efSearch and returns the top k. Step 4 shows the other family: IVF cuts the space into nlist k-means cells and searches only the nprobe nearest cells, and PQ compresses each vector to 96 bytes. DiskANN keeps only PQ codes in RAM, which is how one workstation serves a billion vectors. Likely question: "HNSW or IVF-PQ?" Answer: HNSW for the best recall and latency when the vectors fit in RAM; IVF-PQ or DiskANN when memory is the limit, and always measure recall@k against exact k-NN.
