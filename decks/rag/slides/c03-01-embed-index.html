Embed and index: vectors you can trust, search you can tune

You embed 4 tickets, index 100k vectors and run a filtered SQL top-10. A wrong task type, norm or metric gives no error, only worse rankings.

Chapter 3 is Lab 3: we build the Northwind Mutual claims and ticket index. We embed resolved support tickets with gemini-embedding-001 at 768 dimensions, embed the Lab 2 claims chunks on-prem with Qwen3-Embedding at 256 dimensions, sweep FAISS HNSW and IVF against exact search, serve tenant-filtered top-k from pgvector, and re-ingest an edited policy without re-embedding unchanged chunks. Click 1: similar texts cluster in the embedding space. Click 2: a query enters the top layer of an HNSW graph, hops greedily, drops a layer, and ends at its 5 nearest neighbours. Define the two words the labs use all the time: M is the number of links each node keeps in the graph, and efSearch is the size of the candidate list the search keeps while it descends; a bigger list finds more true neighbours but costs latency. The task type tells the embedding model whether the text is a document or a query, so the two sides get vectors that match. Analogy: HNSW is a motorway, then main roads, then side streets; efSearch is how many side streets you are willing to check. Likely question: "Which part fails silently, the embedding or the index?" Both: a missing norm or wrong task type gives wrong vectors, and an L2 metric or efSearch=16 gives wrong neighbours, with no error in either case.
