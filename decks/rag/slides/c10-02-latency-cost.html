Five levers for latency and cost

  • Retrieve less: rerank the top-50 to the top-5.
  • Prompt cache: static prefix first; reads cost 0.1x (Anthropic).
  • Semantic cache: ~0.05 s hit vs ~1.8 s LLM call.
  • Route and cascade: small model first, escalate on low confidence.
  • Batch APIs for indexing and offline eval.

Freshness: stop zombie chunks

index() + RecordManager hashes each chunk and skips unchanged ones. Cleanup: incremental · full · scoped_full. Never point it at a store that another process filled. New embedding model = full blue/green re-embed.

semantic_cache.py · RedisVL

from redisvl.extensions.cache.llm import SemanticCache
from redisvl.utils.vectorize import HFTextVectorizer
from redisvl.query.filter import Tag

cache = SemanticCache(name="llmcache",
    redis_url="redis://localhost:6379",
    distance_threshold=0.1,     # Redis COSINE 0-2, lower = stricter
    vectorizer=HFTextVectorizer("redis/langcache-embed-v1"),
    filterable_fields=[{"name": "user_id", "type": "tag"}])
def answer(q: str, uid: str) -> str:
    hit = cache.check(prompt=q,
                      filter_expression=Tag("user_id") == uid)
    if hit:                               # ~0.05 s instead of ~1.8 s
        return hit[0]["response"]
    out = rag_answer(q)                   # retrieve, rerank, generate
    cache.store(prompt=q, response=out, filters={"user_id": uid})
    cache.set_ttl(3600)                   # freshness bound
    return out
Partition by user_id or tenant, or user A gets user B's answer. At distance_threshold=0.5, a "Nice" question hit the cached "Paris" answer. Tune the threshold with CacheThresholdOptimizer.
Step 1 draws one request as a trace. Every hop is a span, and each span records what you need to debug it: the retriever span keeps the top-k ids, scores, the filter and the index version. Step 2 turns on prompt caching and a semantic cache. The prefill bar shrinks because the static prefix is read from cache at 0.1x price; a repeated question returns in about 0.05 s instead of 1.8 s. The bar widths are illustrative; the 0.05 s and 1.8 s values come from the RedisVL docs demo. Step 3 is freshness: hash every chunk, re-embed only the changed ones, write tombstones for deleted ones, and invalidate cache entries tagged with that doc_id. Steps 4 to 6 walk the RedisVL code: the partition field, the filtered check, and the TTL. Analogy: a semantic cache is a librarian who remembers recent questions; without a partition, the librarian tells you someone else's answer. Likely question: "Why not cache by exact string?" Exact match misses paraphrases; a semantic cache catches them, but it needs a strict threshold.
