Best practices

Eval rules: real queries, canary slices, a pinned judge, paired gates

Do

  • Start with 20-50 real failures. Grow to 100-300 labelled queries.
  • Add canary, multi-turn and all-evidence slices. Sharded turns: up to 21% drop.
  • Gate on deterministic recall@5 first. It needs no judge.
  • Report coverage next to every judge score. NaN rows raise the mean.
  • Pin judge model, prompt hash, temperature. Re-calibrate on any change.
  • Quote kappa against the human ceiling, plus the unsupported-admit rate.
  • Evaluate at temperature 0. Disagreement 14.3% → 3.4%.
  • Count "not enough evidence" as INCONCLUSIVE. Compare paired rows.

Don't

  • Ship from an isolated A/B test. +47% predicted, +17% together.
  • Merge TestsetGenerator rows unreviewed. Mix in ~20% real queries.

These are the rules that turn the ShopCo gate from a demo into a release process. Build the golden set from real failures first, 20 to 50 is enough to start, and add slices for canaries, multi-turn sharded questions and all-evidence questions, because each slice fails in its own way. Gate on deterministic recall before any judge, and print coverage next to every judge score, because ragas drops NaN rows and the mean goes up as rows fail. Pin the judge like a model you ship: model id, prompt hash and temperature live in baseline.json, and any change means re-calibration. Analogy: you would not change the scale in a lab and keep the old readings. A likely question: "Why is INCONCLUSIVE its own state?" Because a gate that cannot decide must not pass silently; RAGWarrant separates it from PROMOTE, BLOCK and REJECT so a human looks at it.
