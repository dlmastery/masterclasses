Filtered top-k in pgvector returns 10 rows with an iterative scan

lab7_pgvector_claims.py · pgvector 0.8.7 · Postgres 18
import datetime as dt, os
import numpy as np, psycopg
from pgvector import Vector
from pgvector.psycopg import register_vector
conn = psycopg.connect(os.environ["PG_DSN"], autocommit=True)
conn.execute("CREATE EXTENSION IF NOT EXISTS vector")
register_vector(conn)                                   # after CREATE EXTENSION
conn.execute("DROP TABLE IF EXISTS claim_chunks")
conn.execute("""CREATE TABLE claim_chunks (
    id bigserial PRIMARY KEY, tenant_id int NOT NULL, product text NOT NULL,
    effective_date date NOT NULL, content text NOT NULL,
    embedding_model text NOT NULL, embedding vector(256) NOT NULL)""")
emb = np.random.default_rng(1).standard_normal((50_000, 256)).astype(np.float32)
emb /= np.linalg.norm(emb, axis=1, keepdims=True)   # omitted: COPY 50,000 rows + emb
conn.execute("SET maintenance_work_mem = '1GB'")          # build after load
conn.execute("CREATE INDEX claim_hnsw ON claim_chunks USING hnsw"
             " (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64)")
conn.execute("ANALYZE claim_chunks")
SQL = """SELECT id, product, effective_date, embedding <=> %s AS dist FROM claim_chunks
         WHERE tenant_id = %s AND product = %s AND effective_date >= %s
         ORDER BY embedding <=> %s LIMIT 10"""
q = Vector(emb[123])
with conn.transaction():
    conn.execute("SET LOCAL hnsw.ef_search = 100")
    conn.execute("SET LOCAL hnsw.iterative_scan = relaxed_order")   # pgvector >= 0.8.0
    rows = conn.execute(SQL, (q, 3, "home", dt.date(2025, 1, 1), q)).fetchall()
    plan = conn.execute("EXPLAIN " + SQL, (q, 3, "home", dt.date(2025, 1, 1), q)).fetchall()
print(len(rows), "rows; first:", rows[0][:3])
print("\n".join(r[0] for r in plan[:4]))

Call register_vector after CREATE EXTENSION: it reads the vector type OIDs. Store embedding_model on every row.
Build HNSW after the load. vector_cosine_ops must match <=>. m 16 and ef_construction 64 are the defaults.
If a condition matches 10% of rows, with HNSW and the default hnsw.ef_search of 40, only 4 rows will match on average.Docs pgvector README · FilteringFix: iterative_scan reads more batches until 10 rows match. SET LOCAL is safe with connection pools.
Only ORDER BY embedding <=> q LIMIT 10 uses the index. ORDER BY 1 - (embedding <=> q) DESC does not.

This is the last step of Lab 3: the Qwen3 claims vectors (256 dims, as in step 2) move into Postgres, loaded as 50,000 rows over 20 tenants, and each query filters by tenant, product and date. Steps 1 and 2: register the vector type after CREATE EXTENSION, keep the model name on every row, and build the cosine HNSW index after the bulk load. Step 3 is the trap: pgvector filters after the index scan, and this filter keeps about 0.8% of rows (1/20 tenants x 1/4 products x 2/3 years), so even the 100 candidates of ef_search 100 give under one matching row (the README case with the default 40 gives 0.3); the iterative scan keeps reading until 10 rows match or hnsw.max_scan_tuples (20,000) is reached. Analogy: a waiter brings 40 dishes and then removes all dishes that you did not order; the iterative scan sends the waiter back to the kitchen until you have 10. Step 4: check EXPLAIN for "Index Scan using claim_hnsw", and keep the distance operator in ORDER BY ascending. Likely question: "Why not always use iterative scan?" It costs extra reads on selective filters; for many tenants the README recommends partitions, and the planner can also pick the B-tree and an exact sort.
