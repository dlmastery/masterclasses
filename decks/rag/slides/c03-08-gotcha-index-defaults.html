Gotcha Vector indexes

Index defaults: L2 metrics, tiny search breadth, a 2,000-dim cap

northwind_index/index_settings.py · set every default on purpose
import os
import chromadb, faiss, numpy as np, psycopg
D = 256
xb = np.load("out/claims_qwen256.npy")                           # Lab 3 step 2 vectors
xq = xb[:5].copy()                                               # five probe queries

index = faiss.IndexHNSWFlat(D, 32, faiss.METRIC_INNER_PRODUCT)   # default metric is L2
faiss.normalize_L2(xb); faiss.normalize_L2(xq)                   # IP == cosine on unit vectors
index.add(xb)
_, I = index.search(xq, 10, params=faiss.SearchParametersHNSW(efSearch=128))  # default 16

col = chromadb.PersistentClient(path="./chroma_claims").get_or_create_collection(
    name="claims_qwen3_256", embedding_function=None,
    configuration={"hnsw": {"space": "cosine", "ef_search": 100}})  # None -> "l2"

conn = psycopg.connect(os.environ["PG_DSN"], autocommit=True)
conn.execute("CREATE INDEX ON claim_chunks_3072 USING hnsw "
             "((embedding::halfvec(3072)) halfvec_cosine_ops)")  # vector caps at 2,000 dims
# claim_chunks (Lab 3 step 4) already declares embedding ... NOT NULL
assert np.abs(xb).sum(axis=1).min() > 0, "all-zero embedding: the embed call failed"
FAISS 1.15.1 · HNSW and IVF SymptomRankings look wrong after the switch to HNSW. CauseIndexHNSWFlat(d, M, metric = METRIC_L2) defaults to L2. Inner product is not by itself cosine similarity, unless the vectors are normalized. efSearch 16 and IVF nprobe 1 are low for RAG. Fixnormalize_L2 + IP. Per-query efSearch 64-256.
Chroma 1.5.9 · own embeddings SymptomDistances do not behave like cosine. CauseWith embedding_function=None the space default is "l2". The configuration applies only on create. FixSet "space": "cosine" on the first create. One collection per embedding model and dim.
pgvector 0.8.7 · 3072-d gemini-embedding-001 SymptomERROR: column cannot have more than 2000 dimensions for hnsw index. An index scan returns fewer rows than a seq scan. Causevector indexes stop at 2,000 dims (halfvec 4,000, bit 64,000). NULL and zero vectors (cosine) are not indexed. Fix768/1536 dims or a halfvec expression index. CHECK NOT NULL. Reject all-zero vectors: a failed embed call often returns zeros.

Every vector store ships defaults that are safe for a demo and wrong for a RAG index. FAISS HNSW uses L2 unless you ask for inner product, inner product is cosine only on unit vectors, and efSearch 16 or nprobe 1 gives low recall; the Lab 3 sweep showed how much recall comes back at 64 to 256. Chroma with your own vectors silently uses l2, and the configuration is fixed when the collection is created, so a later call with cosine changes nothing. pgvector cannot index more than 2,000 dimensions on the vector type, so 3072-d gemini-embedding-001 needs a smaller output_dimensionality or a halfvec expression index, and NULL or zero vectors simply vanish from index scans. Analogy: a new car with the seat, mirrors and lights in factory positions; it drives, but you set each one before the motorway. Likely question: "Does halfvec lose quality?" Measure recall against exact search on your own queries, exactly as in the Lab 3 sweep. Hand-off: these settings are right today; the papers on the next slide show why they drift as the corpus and the embedder change.
