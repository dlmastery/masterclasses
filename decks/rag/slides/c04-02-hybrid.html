BM25 and dense retrieval fail on different queries, so run both

BM25 wins. Dense vectors miss exact tokens: error codes, SKUs, names and rare acronyms.

Dense wins. "car" ≈ "automobile". BM25 misses synonyms and paraphrase.

Both hit. The failures barely overlap, so the union raises recall. BEIR (NeurIPS 2021): "BM25 is a robust baseline."

SPLADE (Formal et al., SIGIR 2021): a BERT MLM head projects each token onto the whole 30,522-term vocabulary. Log-saturation and a FLOPS regulariser keep a few hundred weights. Expansion adds "vehicle" and "automobile" to a "car" passage.

It is still an inverted-index vector: Lucene, Elastic, OpenSearch, Qdrant sparse. Sentence Transformers: SparseEncoder("naver/splade-cocondenser-ensembledistil").

Score fusion, if you fuse scores: Weaviate relativeScoreFusion (default since v1.24) min-max normalises, then weights by alpha (0.5 default, 1 = pure vector, 0 = pure BM25). Qdrant DBSF normalises each list with mean ± 3σ. Rank fusion is on the next slide.

Start with three real query shapes. "error E1023" is an exact token, so BM25 finds it and a dense vector blurs it. "How to make the car faster" uses other words than the document, so only the dense retriever finds it. "Q3 revenue ACME" is found by both, and the point is that the two failure sets barely overlap, so running both raises recall. Then show the three vector types for one passage: BM25 keeps only the words that are there, dense spreads meaning over 768 numbers, and SPLADE learns weights over the whole vocabulary and adds expansion terms in blue, while it still runs on an inverted index. Analogy: one witness remembers exact names, another remembers what happened; ask both. Likely question: "Does SPLADE replace hybrid search?" It narrows the gap, but most production systems still fuse a sparse list and a dense list, and you measure on your own queries.
