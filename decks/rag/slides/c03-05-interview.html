Interview: embeddings and ANN index design

Design an index for 1B vectors on a tight memory budget.
Use DiskANN (PQ codes in RAM, graph and full vectors on SSD) or IVF-PQ. Cut to 768 dims with MRL, then use int8 or binary. Re-score the top candidates with the full vectors. Measure recall@k against exact k-NN on a sample. DiskANN served SIFT1B from one 64 GB workstation at >5,000 QPS.
What do HNSW M, efConstruction and efSearch change?
M is the graph degree: more memory (HNSWFlat costs 4·d + M·2·4 B) and higher recall. efConstruction sets build quality: higher values make the build slower. efSearch is the query beam width: higher values give more recall and more latency. You set efSearch at query time.
Can you query a gemini-embedding-001 index with gemini-embedding-2 vectors?
No. The two models make different vector spaces, so the distances have no meaning. Do a blue/green re-embed: build a second index with the new model, compare both on the golden set, then move the traffic.
Numbers to know.
10M × 3072 × 4 B ≈ 123 GB; 768-bit binary ≈ 0.96 GB. PQ96x8 = 96 B per vector (3,072 B for 768-d float32). MRL: up to 14× smaller at the same accuracy. Exact k-NN: O(N × d) per query.
Ask the room each question first and give them twenty seconds before you reveal the answer. For the billion-vector design, the expected structure is: compress (MRL plus quantization), pick a memory-light index (DiskANN or IVF-PQ), re-score with full vectors, and prove it with recall@k against exact search. Analogy for the model-swap question: you cannot use GPS coordinates from one map projection on a different map. A strong candidate also says how to migrate safely: run both indexes side by side and switch only after the golden-set numbers agree. Likely follow-up: "How big is the golden set?" Answer: enough real queries with labelled gold chunks to see a recall difference of a few points, and keep it versioned with the index.
