Retrieved text is untrusted input, so injection and poisoning attack through the index

Indirect prompt injection

The attacker writes into a source that your retriever reads: a web page, an email, a PDF, a ticket. A normal query then pulls the text into the prompt.

Paper Greshake et al., arXiv 2302.12173
0PoisonedRAG attack success with five texts per target question, in a database of millions
  • Retrieval condition: the text is close to the target question, so it ranks in the top-k.
  • Generation condition: the text states the attacker's answer.
Paper PoisonedRAG, USENIX Security 2025

OWASP example: a résumé hides white-on-white text. The model obeys it. Data leaves through a markdown image URL or a tool call.

1 · Control what enters the index

Trusted sources only, with provenance and signatures. Review before ingestion. Detect duplicates and anomalies. Keep immutable retrieval logs.

This slide replays one attack, then replays it with defences. Step 1: the attacker plants cv_17.pdf in the corpus. Step 2: a normal user query retrieves it, and it rises to rank 1 because PoisonedRAG texts are written to be close to the target question; five texts per question give 90% success. Step 3: the hidden text tells the model what to do, and data leaves through a tool call and a markdown image URL. Steps 4 to 6 add defence layers. Assume each layer can fail, so stack them: provenance at ingestion, Spotlighting and CaMeL at the model, least privilege and egress filters at the tools. Analogy: a letter in the in-tray that says "the boss told you to wire money". Likely question: "Can a better system prompt stop this?" No. Prompt text is not a security boundary; CaMeL gives provable guarantees because the plan comes only from the trusted query.
