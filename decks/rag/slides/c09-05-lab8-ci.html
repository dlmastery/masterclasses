.github/workflows/rag-eval.yml
name: rag-eval
on: { pull_request: { paths: ["rag/**", "prompts/**", "golden.jsonl"] } }
jobs:
  gate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with: { python-version: "3.12" }
      - uses: actions/cache@v6           # re-use judge verdicts across runs
        with: { path: .ragas_cache, key: ragas-${{ hashFiles('golden.jsonl') }} }
      - run: pip install ragas==0.4.3 openai==3.37.0 diskcache==5.6.3 -r requirements.txt
      - run: python run_pipeline.py --golden golden.jsonl --out runs/candidate.jsonl
        env: { GEMINI_API_KEY: "${{ secrets.GEMINI_API_KEY }}" }
      - run: python eval_gate.py
        env: { GEMINI_API_KEY: "${{ secrets.GEMINI_API_KEY }}" }
      - uses: actions/upload-artifact@v7
        if: always()
        with: { name: eval-report, path: eval_report.json }

This is the last step of Lab 8: the same eval_gate.py from the previous slide now runs on every pull request. The paths filter is the scope decision: a change to the retrieval code, a prompt, the model or the golden labels can move quality, so each one starts the job. The cache step restores .ragas_cache keyed on golden.jsonl, so unchanged rows reuse earlier judge verdicts and a re-run costs little. When recall@5 falls to 0.812 against a baseline of 0.860 with a 0.03 tolerance, the script exits 1 and GitHub marks the check as failing, but if: always() still uploads eval_report.json so the reviewer can see why. Analogy: a smoke detector that also keeps the log of what it smelled. Likely question: "The check flips between FAIL and ok on the same commit, why?" The judge is non-deterministic at small n: keep the ragas temperature default, grow the golden set, use the cache, and cap concurrency with asyncio.Semaphore when you see 429 errors. Next: the gate trusts the faithfulness judge, so the build-up measures that judge against human labels before it blocks any merge.
