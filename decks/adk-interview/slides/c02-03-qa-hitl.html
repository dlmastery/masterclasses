Human approval is a protocol message with an interrupt id

How does a human-in-the-loop pause work on the wire in ADK 2.0?
The node yields RequestInput, sent as a FunctionCall named adk_request_input. Any client resumes with a FunctionResponse with the same id.
A paused node gets its answer. Should @node(rerun_on_resume=...) be True or False, and what changes?
False (default) is hand-off: the reply becomes the node's output. True is re-entry: the node runs again from the top and reads the reply from ctx.resume_inputs.
The manager types 100, or approve. What does the node get?
Replies are JSON-parsed when possible, so 100 arrives as an int. A response_schema does not reshape the reply: plain text fails validation.

On the wire: one interrupt id, two messages

two separate processes
$ adk run refund_approval "A-2040 820" --session_id case-2040
$ adk run refund_approval yes --session_id case-2040

Same session_id with an open interrupt: the CLI sends the text as the FunctionResponse.

Two ways to resume a paused node

False · hand-off (default)
gate→pause→reply = gate output→next node
True · re-entry
gate→pause→gate reruns from top→reads resume_inputs[iid]→route
re-entry: inside manager_gate
answer = ctx.resume_inputs.get(iid)
if answer is None:  # first run: ask
    yield RequestInput(interrupt_id=iid, message="Approve?")
    return

Ask each question and let the candidate answer before you reveal the step. The first frame already shows the outgoing FunctionCall as a hint. Question 1: a strong answer names the wire format. RequestInput becomes a FunctionCall called adk_request_input whose id is the interrupt id, listed in event.long_running_tool_ids. Any client answers with a FunctionResponse with the same id, even from a new process: adk run exits with code 2 while paused, and the next call with the same --session_id auto-resumes the open interrupt, so you do not pass the id yourself. Scripts can branch on exit code 2 to mean "waiting for a human". In Python the reply is types.FunctionResponse(id=interrupt_id, name="adk_request_input", response={"result": text}). The analogy is a claim ticket at a coat check. Question 2: with False the reply simply becomes the node's output; with True the node runs again from the top and finds its answer with ctx.resume_inputs.get(iid). The debug drill at the end of the chapter shows how to build iid. Question 3: the engine JSON-parses string replies when it can, so "100" becomes an int and '{"approved": true}' becomes a dict, which is how a structured reply reaches a response_schema node. The docs say response_schema does not reshape the reply, so a manager who types approve gets pydantic_core.ValidationError: 1 validation error for ManagerDecision.
