State scope and memory deletion are where privacy bugs hide

Which state prefix holds a user's language, an app-wide setting (company name) and scratch data?
user:language follows the user. app:company_name is shared by every user of the app. temp: lasts one invocation (one user message). tool_context.state["user:language"] = "de" # saved through the tool's event
per-tenant data: one app_name per tenant, never app:
Memory is a store searched across sessions. preload_memory or load_memory?
preload_memory searches on every turn. load_memory is a tool: the model searches only when needed. Neither one writes memory. Agent(..., tools=[load_memory], after_agent_callback=save) async def save(callback_context): await callback_context.add_session_to_memory() # InMemoryRunner has a memory service
A user asks you to erase their data. You call delete_session(). Are you done?
No. Memory keeps its own copy: search_memory() still finds it (#7109). Call delete_memory() with the MemoryEntry.id (2.13+). RAG memory sets no id: delete in that backend.

Read each question, pause, and let the student answer before you reveal the model answer. Q1 tests the scopes: user: for the language, app: for an app-wide value such as the company name, temp: for scratch data that lives for one invocation (one run_async call for one user message), and no prefix for this conversation. The trap: app: is shared by every user of that app_name, so per-tenant data under app: leaks across tenants; use one app_name per tenant or a tenant-keyed store. A write persists only through an event: state_delta, tool_context.state or callback_context.state; get_session() returns a copy, which is the debug drill at the end of this chapter. Q2: memory is a searchable store across sessions; preload_memory costs tokens on every turn, load_memory lets the model decide, and you write memory yourself with add_session_to_memory(). Q3, click 3: deleting the session does not delete what memory copied. Click 4: wire delete_memory into the erasure path; it is set up for InMemory, Firestore and Memory Bank, which set MemoryEntry.id. Follow-up for strong candidates: CarryoverBench (arXiv 2610.28425) shows that injections planted in memory re-fire across five rounds, so treat recalled memory as untrusted. Analogy: shredding the meeting notes does not shred the photocopy in the archive. Never store secrets in state, because adk web prints it.
