Read the prompt and the three clarifying questions together, and let the room answer before you click. Step 1 shows the answers: the label set is closed, so classify gets a Literal output_schema; one ticket can have two labels, so route_ticket emits a list route; and the support lead owns human_queue, the fallback. Then build the graph in the order of the steps: intake writes the ticket text to state["ticket"] for the audit trail and for the prompts, classify returns a Triage object with labels and a priority, and route_ticket is plain code, so the rule "outage or any p1 pages on-call" is a unit test, not a prompt. The code card shows the new parts, intake and the edges: DEFAULT_ROUTE has its own key, because DEFAULT_ROUTE inside a list with other routes raises GraphValidationError. At step 4 a p1 billing ticket emits route=["billing", "page"], so both edges run at the same time, and "other" or any surprise label falls to human_queue instead of a silent end of the branch. Do the numbers: 10,000 tickets a day is about 7 a minute, or 0.12 a second, so even a 10x peak is small; the hard parts are correctness and the 60-second p1 budget, which is why paging is decided in code before any reply is written. For the audit trail, every event carries node_info.path (for example ticket_triage@1/classify@1), so you can sum cost and latency per node; and run an eval set where each case states the expected route, because CXBench (2610.25954) found 55.5% of runs had the right outcome with a non-compliant process. Analogy: the model is the nurse who reads the symptoms, the code is the hospital rule that decides the ward.
