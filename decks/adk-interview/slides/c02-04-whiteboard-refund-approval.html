Whiteboard: refunds over $500 wait for a manager, even overnight

Prompt

Design a refund flow. $500 or less: auto‑approve. Above it, a manager approves, rejects or asks for a revised email, maybe the next day. The service redeploys and crashes. Never pay a refund twice.

# intake, draft_reply, manager_gate, issue_refund,

root_agent = Workflow(name="refund_approval", edges=[
  ("START", intake, draft_reply, manager_gate),
  (manager_gate, {"approved": issue_refund,
                  "rejected": notify_rejected,
                  "revise": draft_reply}),
])
durable = ResumabilityConfig(is_resumable=True)
app = App(name="refund_approval", root_agent=root_agent,
          resumability_config=durable)

Read the prompt and let the candidate ask questions first. Good clarifying answers: sessions live in SQLite locally and Postgres or VertexAiSessionService in production; the manager may approve a lower amount (ManagerDecision.amount); and the session's events are the audit record. Click 2: the gate approves amounts up to $500 itself; above that it yields RequestInput, the pause is saved in the session store, and process 1 exits with code 2. The analogy is a bookmark in a book that anyone can pick up. Click 3: process 2 opens the same session; intake and draft_reply are fast-forwarded from their saved events, so the LLM is not called again, and the gate receives the answer. The counter is still 0. Click 4: only now does the approved route run, and issue_refund pays once with the key refund-<order>, because resume is at-least-once. Click 5: revise writes the manager's note to state and loops back to draft_reply; each pass gets its own interrupt id, built from invocation_id and run_id (one run_id per loop pass), and a rerun of the same pass keeps it. The debug drill on the next slide shows that line. Click 6: do not change the graph while runs are paused, because the ADK architecture note lists checkpoint versioning as an open item. To drain, list the sessions whose last event has an open interrupt in the session store, and resolve or expire each one before the deploy; or version the app name. Click 7: the whole graph in code, with ResumabilityConfig(is_resumable=True) for cross-process durability. Say this at the end: durable session store, a re-entry gate with a deterministic interrupt id, a payload that shows exactly what is approved, and an idempotency key on the refund call. A likely follow-up: "What if the manager approved a different amount?" Validate the reply against the payload you showed and log both with the interrupt id.
