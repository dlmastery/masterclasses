Retries and resume replay work, so design every write for twice

After a crash, the resumed payouts workflow paid the payee twice. Why, and what is the fix?
Resume is at-least-once: pay crashed before its event was saved, so it ran again. Send the gateway an idempotency key from a stable business id, payout-<order>, never uuid4().
Your RetryConfig never fires. What are the two usual causes?
A broad except Exception hides the failure. Or a timeout raises NodeTimeoutError, which is not in exceptions: add it by name. The attempt counter resets on resume, so the key still matters.
Which retry tool fits which failure: RetryConfig, a routed back-edge or ReflectAndRetryToolPlugin?
Classify the failure first. A transient error, a wrong answer and a fixable tool error each have their own tool.

from google.adk import Context
from google.adk.workflow import RetryConfig, node
gateway = ...  # stub: your payment client
@node(retry_config=RetryConfig(
        max_attempts=4, initial_delay=0.5,
        backoff_factor=2.0, jitter=0.0,
        exceptions=[ConnectionError, "NodeTimeoutError"]),
      timeout=2.0)
async def pay(ctx: Context, order_id: str, amount: float):
    key = f"payout-{order_id}"  # same key as Q1
    gateway.pay(order_id, amount, idempotency_key=key)
before: NodeTimeoutError → no retry exceptions=[ConnectionError], timeout=2.0 A timeout is not a ConnectionError, so it is not retried.

Ask each question and let the candidate answer before you reveal the model answer. Prerequisites: the chapter 1 slides on routes and loops introduced the routed back-edge; RetryConfig and the plugin are defined on the last card here. Question 1: the panel first shows the bug, two payouts after a crash between the gateway call and the saved event of pay. ADK's own docstring says the "tool call to resume needs to be idempotent". With a key from a stable business id such as payout-<order>, the gateway sees the second call as a duplicate, so the count drops to one. order_id and amount reach pay from state by parameter name (parameter_binding="state" is the default). The lab prints a key from ctx.invocation_id; that works only while resume keeps the same invocation, so lead with the business id. Question 2, first click: the focus is on exceptions. It matches the class name of the exception or any parent class name (Python's method resolution order), as strings or classes, so "NodeTimeoutError" needs no import (the class lives in the private module google.adk.workflow._errors). A broad except Exception hides the failure from the engine, and catching BaseException also traps NodeInterruptedError and breaks human pauses. Second click: the focus moves to the delays and the timeline draws. This config uses jitter=0.0, so the waits are exactly 0.5 s and 1.0 s, and try 4 is the cap because max_attempts counts the first try. The defaults are 5 attempts, 1.0 s, 60 s max, x2, jitter 1.0. The attempt counter is not persisted: a crash after try 3 and a resume give the node a full new budget, so the idempotency key still protects you. Question 3: classify the failure, then pick the tool. Wrong: Workflow(..., retry_config=RetryConfig(...)) on the parent; right: @node(retry_config=...) on the flaky node, because issue #7524 (open) shows a finished sibling re-running on a real database backend. ReflectAndRetryToolPlugin comes from google.adk.plugins and goes in App(plugins=[ReflectAndRetryToolPlugin(max_retries=2)]); for soft errors in a dict, override extract_error_from_result. Analogy: a courier who may ring twice must carry a parcel number, so the second ring does not deliver a second parcel. Next slide: the human pause itself, in the refund_approval flow.
