An unmatched route ends the branch with only a log line

How do you branch in an ADK 2.0 Workflow, and what happens to an unmatched route?
A function yields Event(route=...); a dict edge maps routes to nodes.An unmatched route ends the branch with a log warning only: no error, no reply.Fix: a Literal output_schema, and DEFAULT_ROUTE, the edge taken when no other route matches.
Why let the LLM classify but let code make the routing decision?
A plain function is unit-testable without a model call."p1 always pages on-call" stays deterministic. Routing and review calls use 32-44% of multi-agent tokens (2610.21411).
Two branches both end with an output. What happens?
The run fails: a workflow allows one terminal output.A terminal node has no outgoing edge.Fix: side branches emit Event(message=...), or add a JoinNode before one final node.

ticket_triage/agent.py · the LLM labels, code routes
class Triage(BaseModel):
  labels: list[Literal["billing", "outage", "how_to", "other"]]
  priority: Literal["p1", "p2", "p3"]
classify = Agent(name="classify", output_schema=Triage,
                 instruction="Classify this ticket: {ticket}")
def route_ticket(node_input: Triage):
  routes = [l for l in node_input.labels if l != "outage"]
  if "outage" in node_input.labels or node_input.priority == "p1":
    routes.append("page")      # outage or any p1 pages on-call
  # "other" has no edge: DEFAULT catches it only if nothing matched
  yield Event(output=node_input.model_dump(), route=routes)

Read each question, pause, and let the candidate answer before you reveal the model answer. Q1 is the silent-failure trap, in two clicks: first the failure alone, where the LLM writes "Billing" with a capital B, no dict key matches, and the branch just ends with a log warning, so the customer gets no reply and no alert fires; then the fix: a Literal output_schema so the model cannot invent a label, and DEFAULT_ROUTE (import it from google.adk.workflow, checked against the v2.13.0 source), the edge taken when no other route on that node matches. Matching is an exact string match, and there is no strict mode that raises, so add a unit test that every Literal label has an edge. Q2 tests the boundary: the model only labels into a closed set, and a plain function holds the business rule, which you can unit-test without a model call; an outage label or any p1 ticket becomes the separate "page" route, so paging never depends on the meaning of a label, and a p1 billing ticket runs billing and page_oncall. Watch the "other" label: it has no edge, so DEFAULT_ROUTE catches it only when nothing else matched; next to "billing" it is ignored, which is fine because billing answers the ticket. Known labels get explicit edges; DEFAULT is for surprises. Q3: a terminal node is a node with no outgoing edge, and the workflow keeps exactly one terminal output: let side-effect branches such as paging emit a message, or join first. Analogy: a mail room where an unknown postcode goes in the bin unless you add a "return to sender" tray. Likely follow-up: "Can one ticket take two branches?" Yes, a list route runs every matching edge, but DEFAULT_ROUTE cannot share a list with other routes: that raises GraphValidationError.
