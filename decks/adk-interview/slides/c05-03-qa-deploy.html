Agent Runtime, Cloud Run or GKE?
Agent Runtime: managed sessions, least ops. Cloud Run: your API and revisions. GKE: your cluster, private by default.ClusterIP
How do Cloud Run sessions survive a recycled instance?
Pass --session_service_uri with a shared store. Without it, sessions live in memory and die with the instance.agentengine://ID
How do you call the private service safely?
Send an identity token and grant roles/run.invoker. An access token gets 403. Never ship --with_ui.403 = wrong token

    --cluster_name=agents-prod \

One shared session store for every instance

deploy.sh · google-adk[gcp]==2.13.0 · output illustrative
# 1) create the Agent Runtime instance once: it prints the ID
$ adk deploy agent_engine --project=$PROJECT --region=$REGION \
    --display_name="refund-agent" refund_agent
Created a new instance: projects/my-proj/locations/us-central1/
    reasoningEngines/1234567890      # the ID

# 2) Cloud Run keeps its sessions in that instance
$ adk deploy cloud_run --project=$PROJECT --region=$REGION \
    --service_name=refund-agent \
    --session_service_uri="agentengine://1234567890" \
    refund_agent \
    -- --no-allow-unauthenticated --min-instances=1
# everything after "--" goes straight to gcloud run deploy
No --session_service_uri: the container falls back to in-memory sessions. They are lost when an instance is recycled.
Postgres also works: any SQLAlchemy URL, with google-adk[db].

Private service: identity token, invoker role

smoke.sh · output illustrative
$ URL=$(gcloud run services describe refund-agent \
    --region=$REGION --format='value(status.url)')
$ TOKEN=$(gcloud auth print-identity-token)
$ curl -X POST -H "Authorization: Bearer $TOKEN" \
    $URL/apps/refund_agent/users/u1/sessions/s1
200
$ BAD=$(gcloud auth print-access-token)
$ curl -X POST -H "Authorization: Bearer $BAD" \
    $URL/apps/refund_agent/users/u1/sessions/s2
403 Forbidden   # access token: wrong kind of token

Read each question and let the candidate answer before you reveal the step. For question 1, a strong answer chooses the target by who owns sessions and operations: Agent Runtime manages sessions and Memory Bank for you, Cloud Run gives you your own API surface and revisions, GKE gives you your own cluster and adk deploy gke defaults to ClusterIP. For question 2, name the trap: without --session_service_uri the Cloud Run container falls back to in-memory sessions that die with the instance. The agentengine:// ID is the number at the end of the resource name that adk deploy agent_engine prints; pass --agent_engine_id on later deploys, or every deploy creates a new instance. For question 3, the 403 comes from sending an access token to a private Cloud Run service: send an identity token and grant roles/run.invoker. Analogy: the coat check keeps your coat at the front desk, not in one waiter's pocket. Likely follow-up: "Which store would you pick?"
