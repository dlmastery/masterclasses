Say this: a gateway owns auth and per-tool authorization, agents see a small preselected tool set, tool results are screened, writes need confirmation, and every call is traced.
Give the candidate the prompt and two minutes to ask the clarifying questions on the left; they stay on screen while you build the answer. Click 1 is token cost: 100+ tool schemas cost Uber about 50K-70K tokens per request, so a tool search preselects a small set. In ADK this is custom code, not a built-in: a BaseToolset subclass whose get_tools() embeds the user's intent, retrieves the top 8 tool descriptions from a vector index, and returns those tools; the 300-to-8 counter is illustrative. Click 2 is identity: the gateway is a proxy you build or buy; it checks the user's OAuth token and authorizes each tool, because the official MCP SDKs lack fine-grained per-tool authorization and dual-persona support (2609.22573), and 91.8% of 414 audited internet-facing MCP servers had no OAuth (2608.00150). Click 3 is the servers: each team's McpToolset uses tool_filter and tool_name_prefix="hr" so 40 teams do not clash on names, and write tools use require_confirmation; 16.4% of 4,806 triaged servers expose filesystem capability under another category (2610.22301), so approval is not a sandbox. Click 4: the result is screened before the agent reads it. This is custom wiring, an after_tool_callback that calls the Model Armor API, because the stock ModelArmorPlugin screens prompts and model replies, not tool results. Click 5: every call is traced. GatewayBench compared 7 gateways over 11,118 real tools (2610.23449), so measure tokens per turn and attack success on your own model. Likely follow-up: "Why not expose all 300 tools?" Tokens grow with every schema, and in a two-tool test the first-listed tool won 92-100% of the time (2610.14334). Next: a debug drill on the "writes need confirmation" gate.
