Give the candidate the prompt card and two minutes to ask clarifying questions before you build the reference answer. The reference follows Rippling's layers: offline evals on every commit, 300 to 400 integration queries after merge, about 10 deploy-blocking scenarios, then a canary and production. The dashed return rail means any gate that exits 1 sends the build back to the PR; in the animation the Integration gate fails. Step 2 is the key detail for ADK: since 2.13.0 adk eval exits 1 on a failed case, so CI really blocks; before 2.13.0 the exit code did not reflect failures. Integration runs the agent against sandbox backends plus the llm_backed user simulator with personas, which gives multi-turn cases. Deploy-blocking is a second, small evalset of must-pass cases. On the canary, shift a small share of traffic with gcloud run services update-traffic and compare agent SLIs with the baseline: tokens per invocation, LLM calls per invocation (a sudden rise is the loop signature, as in the illustrative 3.1 vs 2.0), tool error rate, and an online task-success score from a judge calibrated against humans, as Shopify did (κ 0.61 against a human 0.69). When a production session fails, save its turns as a new case in refund.evalset.json, or add a scenario with adk eval_set add_eval_case, so the same failure is caught offline next time. MASIF (arXiv 2610.25852) found implicit failures in 54.3% of successful multi-agent traces, which is why traces, not only outcomes, feed the evalset. Analogy: a car factory with test benches, a test track and a recall desk, where every recall becomes a new bench test. Next: a debug drill on the deploy step of this pipeline.
