Symptom. After a traffic spike or a new revision, some users lose their conversation in the middle of a refund.
Line 8: --min-instances=1 but no maximum. How many instances can run, and where does each keep sessions?
CauseLine 6: sessions.db is on one instance's disk. A new or recycled instance starts with an empty file. FixOne shared session service for all instances. --max-instances=1 is not a fix: a new revision starts empty.

Show the script and the output, and ask why the same session id s1 works at 10:02 and is gone at 10:04. The hint is line 8: --min-instances=1 sets a floor, not a ceiling, so Cloud Run adds instances under load and replaces them on every new revision. The answer is line 6: sqlite:///./sessions.db is a file on one container's disk, so each new instance has its own empty file and a recycled instance takes its file with it. Some requests still reach instance A and work, which is why it looks random; Cloud Run session affinity is best effort and does not survive a new revision, so it only hides the bug. A run request that lands on instance B starts an empty conversation, which is what the user sees. No flag at all gives the same failure in memory, as the deploy Q&A showed. Fix it with one shared store: agentengine://ID for managed Agent Runtime sessions, or a managed Postgres URL with google-adk[db] (for Cloud SQL, also connect the service to the instance). Analogy: a bank where each teller keeps your file in a desk drawer, so a new teller has never heard of you.
