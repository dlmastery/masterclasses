Three numbers to quote, each with the action it implies

Why: errors compound. Toy model, 0.95 per step: 0.9520 = 36%. It assumes each step fails independently.
Number 116steps to near-zero success

Cut LLM steps: make routing and checks function nodes. Every tested model fell to near zero within 16 steps on the paper's agentic task (10,664 trajectories).

Number 2500LLM calls per run, default

Lower it: pass RunConfig(max_llm_calls=5) to runner.run_async(run_config=…), or set ADK_MAX_LLM_CALLS (since 2.8.0). Over the cap: LlmCallsLimitExceededError. Lab 0 makes 1 call, 2 with billing.

Number 313minor versions in 5 months

Pin google-adk==2.13.0 in local and deployed requirements. 2.0.0 (2026-05-19) to 2.13.0 (2026-10-23). Minors break things: 2.12.0 dropped Python 3.10.

Quote each number with the action it implies. First the why: if each step succeeds 95% of the time and the steps fail independently, 20 steps succeed 0.95 to the power 20, about 36% of the time. Analogy: a relay of 20 runners who each drop the baton 1 time in 20 finishes clean only about 1 race in 3. Number 1: arXiv 2609.01660 fits the same geometric law, but measured per-step reliability is lower, so on its agentic task every tested model falls from near-perfect to near zero within 16 steps; cut the number of LLM steps. Number 2: the default budget is 500 LLM calls per run. Pass RunConfig(max_llm_calls=...) from google.adk.agents.run_config to runner.run_async, or set the ADK_MAX_LLM_CALLS env var, added in 2.8.0; over the cap the run raises LlmCallsLimitExceededError with "Max number of llm calls limit of 500 exceeded". Lab 0 makes one LLM call per ticket, two when billing runs, so a cap of 5 is a safe net. Number 3: thirteen minor versions in five months, and minors carry breaking changes, so pin the version. A likely student question is "why 36% and not 95%?": the failures multiply across steps.
