Generate many candidates, verify them from cheap to costly, and keep only what passes

  1. Sample K candidates per prompt from seeds, personas or Magpie. Llama 3 uses K “typically between 10 and 30”.
  2. Static checks first: format, parse and lint. They cost almost nothing, so they run on every candidate.
  3. Execute: unit tests for code; exact match or a symbolic check for math. Llama 3: over 2.7M synthetic code examples; about 1M dialogues used execution feedback.
  4. Judge, then critique: a reward model or a judge rubric, then a constitutional critique. Keep best-of-K (SFT) or pass/fail pairs (DPO). Dedup and decontaminate.

Judges are biased. GPT-4 judges agree with humans “over 80%”, but they show position, verbosity and self-enhancement bias. Swap the answer order. Use rubrics and reference answers. Use a judge from another model family.

RLVR (Tulu 3) moves the same check into the RL reward: the reward is 1 only if the answer is verifiably correct.

reject_sample.py · illustrative pattern, standard library only

import subprocess, tempfile, textwrap

def passes_tests(solution: str, tests: str, timeout=5) -> bool:
    prog = solution + "\n\n" + textwrap.dedent(tests)
    with tempfile.NamedTemporaryFile("w", suffix=".py",
                                     delete=False) as f:
        f.write(prog)
    try:
        r = subprocess.run(["python", "-I", f.name],
                           capture_output=True, timeout=timeout)
        return r.returncode == 0
    except subprocess.TimeoutExpired:
        return False

def rejection_sample(prompt, tests, generate, k=16):
    cands = [generate(prompt, temperature=0.8) for _ in range(k)]
    good = [c for c in cands if passes_tests(c, tests)]
    # keep all passing (SFT) or pair passing/failing (DPO)
    return good
Run generated code in a sandbox: a container, no network. python -I and a timeout are not a sandbox. Llama 3 ran its tests in containers.
This is the core pattern of synthetic data: generate wide, then filter hard with verifiers in order of cost. Step 1 drops 16 candidates for one prompt. Each gate is more expensive than the one before, so the cheap lint gate removes obvious failures before we pay for execution, and we pay for an LLM judge only on the few that run. The survivors go two ways: best-of-K examples become SFT data, and a passing answer paired with a failing answer becomes a DPO pair. Llama 3 did this at scale for code, and about 20% of solutions were first wrong but fixed themselves with error feedback. Analogy: a hiring funnel; a CV screen is cheap, an on-site interview is costly, so you do the cheap step first. Likely question: "Why not use only the LLM judge?" It is the most expensive gate and it has position, verbosity and self-enhancement bias; programs are cheaper and harder to fool.
