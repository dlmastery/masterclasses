Start with error analysis on real traces, then freeze a versioned golden set

“Error analysis is the most important activity in evals.”

Guide Husain & Shankar, AI Evals: Everything You Need to Know (2026-09-18)
  1. Read at least 100 real traces. Annotate at least 30 yourself before you trust the suggestions of a model.
  2. Open coding: write one free-text note on each failing trace.
  3. Axial coding: cluster the notes into a failure taxonomy. “Write evaluators for errors you discover, not errors you imagine.”
  4. Each failure mode becomes a slice with a binary pass/fail evaluator. “Binary evaluations force clearer thinking.” Use code assertions first (regex, JSON schema, exact match). Use an LLM judge only for subjective criteria.

One benevolent dictator owns the quality definition. Align the judge to that expert (TPR / TNR). Gate CI on each slice. Watch criteria drift: “grading outputs helps users define criteria” (Shankar et al., arXiv 2404.12272). Evals before code? The FAQ says “Generally no”: the loop is error-analysis-first.

The order matters: look at real failures first, then write evaluators. Step 1 fills the grid with 100 production traces; Husain and Shankar say to read at least that many and to label at least 30 yourself. Step 2 is open coding: one free-text note per failure, with no categories yet. Step 3 is axial coding: the notes cluster into a small failure taxonomy, and these piles are examples. Step 4 turns each pile into a named slice with a binary pass or fail check, cheap code checks first and an LLM judge only for taste. Step 5 freezes the result as an immutable, owned version with clear rules. Analogy: a doctor examines patients before she writes the lab test, not the other way round. Likely question: "Why not a 1 to 5 score?" Binary labels force a clear definition of failure and give more consistent labels.
