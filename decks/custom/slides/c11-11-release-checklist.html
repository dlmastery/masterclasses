Best practices

Release checklist: the ten checks the quality card enforces

Design the eval 1-3

  • Pre-register slices and min n=30.Post-hoc slices are p-hacking.
  • Wilson CIs; resample whole claim files.Naive CI: 17% too narrow.
  • Paired bootstrap or McNemar; compute MDE first.MDE at n=400: ~7 points.

Measure honestly 4-7

  • Never trust a library default.method="wilson", level_of_measurement, n_bins, scoring
  • Calibrate; set thresholds at production prevalence.Enriched-set threshold cost 66% more.
  • Judge vs gold labels: TPR and TNR.Correct pass rates with Rogan-Gladen.
  • Report pass@1, pass@k and pass^k.ThinkingBox: pass@20 fell after RL.

Release 8-10

  • Never ship a single-run delta.Run N≥3; report the flip rate.
  • Separate capability and regression suites.Retire saturated evals (Anthropic).
  • Gate on CI lower bounds in code.Store one card per (model, eval hash).

import sys
GATES = {"min_slice_ci_low": 0.50, "min_slice_n": 30, "min_judge_kappa": 0.60}
# g: per-slice k, n, Wilson lo/hi; OTHER: judge numbers (both built in step 3)
failures = [f"slice {r.line}/{r.lang}: CI low {r.lo:.2f} < {GATES['min_slice_ci_low']}"
            for r in g.itertuples() if r.lo < GATES["min_slice_ci_low"]]
failures += [f"judge kappa {OTHER['judge_kappa']:.2f} < {GATES['min_judge_kappa']}"] \
    if OTHER["judge_kappa"] < GATES["min_judge_kappa"] else []
thin = [f"{r.line}/{r.lang} (n={r.n})" for r in g.itertuples() if r.n < GATES["min_slice_n"]]
# (card dict, json.dump and quality_card.md omitted: see step 3)
sys.exit(0 if not failures else 1)

This slide closes the chapter: ten checks, and the quality card is the place where each one becomes code. The first group designs the eval before anyone sees a result: pre-registered slices with a minimum n, Wilson intervals that resample whole claim files, and paired tests with the minimum detectable effect computed first. The second group keeps the measurement honest: pass every library default explicitly, calibrate before a threshold reads a probability, validate the judge against gold labels, and report pass@1 next to pass@k and pass^k. The third group is the release itself: repeat runs, separate capability and regression suites, and a gate on CI lower bounds that exits 1 in CI. Analogy: the card is a pre-flight checklist, and the pilot does not decide on the runway which items count. Likely question: "Will more data alone flip the gate?" Not always: more cases make the interval narrower, but a slice that really sits at 56% still fails, so the next release needs both more Spanish cases and a better model or judge; the last step is a target state, not a measured result.
