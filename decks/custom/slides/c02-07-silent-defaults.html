SymptomTypeError: SFTTrainer.__init__() got an unexpected keyword argument 'tokenizer' CauseTRL 1.x renamed the kwargs. SFTConfig also rejects max_seq_length and warmup_ratio. Fixprocessing_class, max_length, warmup_steps=0.03. Pin trl==1.16.0.
fixed.py · trl 1.16.0
trainer = SFTTrainer("Qwen/Qwen3-0.6B", processing_class=tok,
    args=SFTConfig(output_dir="out", max_length=1024,
                   warmup_steps=0.03,              # float = ratio
                   model_init_kwargs={"dtype": torch.bfloat16}),
    train_dataset=ds["train"],
    peft_config=LoraConfig(r=16, lora_alpha=32, task_type="CAUSAL_LM",
                           target_modules="all-linear"))
print(next(trainer.model.parameters()).dtype)   # torch.bfloat16
Most SFT tutorials on the web are pre-1.0, and porting one to TRL 1.16 fails in two ways. The loud way: tokenizer is now processing_class, max_seq_length is max_length, and warmup_ratio is gone in transformers v5, where warmup_steps takes a float below 1 as a ratio; each of these raises a TypeError, which is easy to fix. The silent way comes after the renames, when the run starts: with no target_modules, PEFT uses the qwen3 default of q_proj and v_proj only, so 2.29 million trainable parameters instead of 10.09 million with all-linear; and SFTTrainer loads a string model id in float32, so a 0.6B model takes about 2.4 GB of weights instead of 1.2 GB, before gradients and optimizer states. Both give a worse or more expensive run with no warning. Fix both as in Lab 1 step 2, and log the dtype at step 0. Think of it like a rental car with the seat set for somebody else: it drives, but not well, until you check every setting. A likely question: "Why does TRL keep float32 as the default?" The maintainers keep it on purpose because their training-inference mismatch results were measured at that precision. Next: the same refund rows on managed Gemini tuning, with no GPU of our own.
