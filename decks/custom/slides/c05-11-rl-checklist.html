Best practices

RL run checklist: ten checks before and during every GRPO job

Before launch

  • Unit-test each reward on a hack.A known hack must score 0.
  • Keep prompts with 0 < pass < 1.Probe the base 8x; keep 0.08 to 0.90.
  • bfloat16, whole groups per batch.Default is float32. 32 = 4 x 8.
  • beta=0.0 for a verifiable reward.Judge reward: beta > 0.
  • Rollouts: top_p=1.0, top_k=-1.Else the IS ratio is biased (TRL #6789).

During the run

  • Log each reward channel.Stop when accuracy falls and total rises.
  • clipped_ratio < 10%, or mask.Cut-off answers score as wrong.
  • Gold-audit a sample every N steps.41-66% of proxy gain is rent (2610.19832).
  • Watchdog on global_step.Stalled vLLM hangs, no error (TRL #6973).
  • Do not score timeouts as 0.Refill the group (ThinkingBox).
Load in bf16. 8 per device x 4 accumulation = 32 completions = 4 prompts x 8.
No KL for an exact verifier. Truncated answers give no gradient.
Z-score each reward in its group. Log completions for the audit.

from trl import GRPOConfig

args = GRPOConfig(
    output_dir="claims-kl0.0",
    model_init_kwargs={"dtype": "bfloat16"},
    per_device_train_batch_size=8,
    gradient_accumulation_steps=4,  # 32 = 4 x 8
    num_generations=8,
    max_completion_length=384,
    loss_type="dapo",
    beta=0.0,                       # exact verifier
    mask_truncated_completions=True,
    reward_weights=[1.0, 0.3],      # accuracy, brevity
    multi_objective_aggregation="normalize_then_sum",
    logging_steps=5,
    log_completions=True,
    report_to="trackio",
)

Read this as the pre-flight list for every GRPO job, and every line maps to a bug from this chapter or from the TRL issue tracker. The left column runs before you spend a GPU hour: test the rewards against a known hack, drop prompts the base always or never solves, load in bf16 with whole groups per batch, keep beta at zero for an exact verifier, and sample rollouts with top_p 1 and top_k minus 1. The right column runs while the job trains: watch each reward channel and the tripwire, keep the clipped ratio under 10 percent, audit against gold, put a watchdog on the step counter, and refill infrastructure timeouts instead of scoring them as wrong. Think of a pilot's checklist: nobody skips it because the last flight was fine. A likely question: "Why not always keep a KL term to be safe?" Answer: with an exact verifier there is no proxy to over-optimize, so KL only slows learning; add it when the reward is a learned model or a judge.
