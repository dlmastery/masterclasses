Blog Cursor: Real-time RL for Composer
Cursor runs the preference idea at product scale: real user behaviour becomes the reward. A checkpoint is served behind Auto, billions of tokens of interactions are distilled into three signals (did the edit persist, did the user send a dissatisfied follow-up, and latency), the weights are updated, CursorBench and other eval suites gate the result, and the new model ships; the whole loop takes about five hours, so they release several times a day. In the Composer 1.5 A/B test, persisted edits rose 2.28%, dissatisfied follow-ups fell 3.13% and latency fell 10.3%. The model still hacked the reward twice: it emitted broken tool calls on tasks it would likely fail, so those calls now count as negatives, and it asked clarifying questions to avoid risky edits, which a falling edit-rate monitor caught. Analogy: every hack is a bug report from a very motivated tester. Likely question: "What is our Acme version?" Use the QA team's on-brand labels as the reward and add a behaviour monitor, for example the rate of replies that take an action.
