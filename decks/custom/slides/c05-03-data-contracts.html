A data contract makes schema, semantics and SLAs executable in CI

1 · Schema

Fields, types, nullability, keys.

2 · Semantics

Allowed values, ranges, formats, units, meaning: “amount is gross EUR incl. VAT”.

3 · SLAs and quality

Freshness, completeness, volume, uniqueness, an owner.

4 · Change policy

Versioned in git. CI finds breaking changes.

import pandas as pd
import pandera.pandas as pa       # not: import pandera

class SFTRow(pa.DataFrameModel):  # contract for an SFT shard
    prompt: str   = pa.Field(str_length={"min_value": 1})
    response: str = pa.Field(str_length={"min_value": 1})
    lang: str     = pa.Field(isin=["en", "de", "fr"])
    quality: float = pa.Field(ge=0.0, le=1.0)

    class Config:
        strict = True             # no unexpected columns

A data contract is an agreement between the team that makes the data and the teams that use it. It is versioned in git and CI runs it on every batch. For ML and LLM data, the consumer is the training or eval pipeline. Step 1: the field types are the schema. Step 2: isin, ge and le are semantics, the allowed values and ranges. Step 3: strict mode refuses unexpected columns, and lazy=True collects every failure in one report, which is the quality gate. Step 4: a synthetic generator sends a row with an empty response; the str_length rule catches it and the build stops before training. Step 5: the change policy; datacontract breaking compares two contract versions and fails when v2 removes a column. Step 6: the tool choice. Analogy: a contract is a type system for data that crosses a team boundary. Likely question: "Pandera or Great Expectations?" Pandera when the check lives inside Python training code; Great Expectations or Soda when the data lives in a warehouse and many teams read it. Pitfall: use import pandera.pandas as pa; the old top-level import gives a FutureWarning.
