This is step 3 of Lab 7: the same 6,000 refund events, now evaluated the way the model meets them in production, in time order. Step 1: TimeSeriesSplit only uses row order, so we sort by event_day with a stable sort first. Step 2: chargebacks take about 7 days to arrive, so the last week before a test window has no labels yet; the gap parameter counts rows, so we convert 7 days into 112 rows ourselves. Step 3: each fold trains on all earlier days, from 1,088 to 4,688 rows, and every preprocessor such as a target encoder must sit inside a Pipeline so it is re-fit per fold. Step 4: the assert is a one-line leakage test that fails the build if any training day is later than a test day; put it in CI. Step 5: when the model must also work on new customers, combine the time cut-off with group exclusion. Analogy: you grade a weather forecast only on days after the forecast was made, never on days it already saw. Likely question: why not a date-based splitter? You can write one; the important part is that the gap is in the same unit as the label delay. Hand-off: now the ROC-AUC is honest, but the hold rule needs probabilities, so step 4 checks whether the scores are calibrated.
