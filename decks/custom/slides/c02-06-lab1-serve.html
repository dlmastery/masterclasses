This is the last step of the refunds lab: the model goes behind an OpenAI-compatible endpoint. Option A serves the merged copy, which is right for one tenant, or for the GGUF path: GGUF is the llama.cpp file format for CPUs, laptops and phones. Option B keeps one bf16 base on the GPU and loads LoRA adapters by name. Here the shipping adapter stands for a second team's adapter, trained with the same recipe. vLLM defaults to max_loras 1 and max_lora_rank 16, so for two adapters we pass --max-loras 2. The VRAM bar is the real cost picture: vLLM takes 90% of the GPU by default; the weights are about 1.2 GB and two adapters about 80 MB, and the rest becomes KV cache for concurrent requests. Think of the base as a shared kitchen and each adapter as a recipe card. The client sends the same system prompt as training and enable_thinking false through chat_template_kwargs, so the prompt prefix matches what the model learned; without it you get garbage think text. A likely question: why does the adapter work in Python but not in vLLM? Under transformers v5 the module names can differ; compare logprobs of base and adapter in CI, and try --model-impl transformers (PEFT issue 3896).
