Gotcha QLoRA and export

QLoRA traps: fp4 by default, 4-bit merges drift, exports ship the base

1 · Quant type
SymptomA copied script scores below the recipe. CauseNo bnb_4bit_* lines: fp4, no double quant. FixOne bnb with nf4 for every loader.
2 · Merge into 4-bit Repo PEFT #3878
SymptomEach merge / unmerge cycle moves the base. CauseA merge into 4-bit quantizes again: lossy. FixA/B on a reloaded base. Merge into bf16.

SymptomThe GGUF answers exactly like the base. CauseA PeftModel wrapper makes the export skip the merge. FixLoad the adapter folder with FastModel.

from unsloth import FastModel   # first import: Unsloth patches transformers
import torch
from peft import PeftModel
from transformers import AutoModelForCausalLM, BitsAndBytesConfig
BASE, ADAPTER = "Qwen/Qwen3-4B-Instruct-2507", "qwen3-4b-claims-qlora/final"
# 1 · one bnb for every loader (lab3 training, lab4 eval): nf4 + double quant
bnb = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4",
                         bnb_4bit_use_double_quant=True, bnb_4bit_compute_dtype=torch.bfloat16)
base4 = AutoModelForCausalLM.from_pretrained(BASE, quantization_config=bnb)   # A/B: reload, never merge
# 2 · export: merge into a fresh bf16 base, then compare greedy outputs on 50 rows
base16 = AutoModelForCausalLM.from_pretrained(BASE, dtype=torch.bfloat16)
merged = PeftModel.from_pretrained(base16, ADAPTER).merge_and_unload(safe_merge=True)
merged.save_pretrained("qwen3-4b-claims-merged")
# 3 · GGUF: load the adapter folder through Unsloth in 16-bit, export, then run 3 probes
model, tokenizer = FastModel.from_pretrained(model_name=ADAPTER, load_in_4bit=False)
model.save_pretrained_gguf("claims-gguf", tokenizer, quantization_method="Q8_0")
Three traps cost QLoRA teams days, and none of them raises an error. Trap one: BitsAndBytesConfig without the bnb_4bit lines falls back to fp4 with no double quantization, while the TRL CLI defaults to nf4, so a script and a CLI run both called QLoRA are different runs. Lab 2 sets both explicitly; reuse one bnb object in every script that loads the base. Trap two: PEFT warns "Merge lora module to 4-bit linear may get different generations due to rounding errors". Merging into 4-bit weights quantizes them again, so merge then unmerge does not give the base back, and each cycle drifts further. Reload the base for A/B tests, merge into a bf16 copy for export, and check that greedy outputs of the merged model match the adapter model on 50 held-out rows. Trap three: an Unsloth GGUF export through a PeftModel wrapper silently ships the base model, because the export method is bound to the base object. Load the adapter folder with FastModel; with load_in_4bit=False the merge happens in 16-bit, not in 4-bit. Then run three probe prompts on the GGUF: the answers must differ from the base. Unsloth pins its own transformers range, so install it in a separate environment. A related report: a merged Gemma 4 gave garbled output while the adapter-only save worked (Unsloth #7318); gate each merge by comparing perplexity of merged and adapter models on 50 rows, within about 1%. Think of a 4-bit merge like photocopying a photocopy: every pass loses a little.
