Gotcha Preference data · TRL 1.16.0

Truncated preference pairs give empty answers and NaN weights

1 · Truncation empties a response
Symptomloss_type="simpo" (CPOTrainer): loss = 0, grad_norm = nan, all rewards and logps nan after the first optimizer step. Other loss types silently use logp = 0. CauseBoth responses are cut to max_length - longer_response_length. When negative, lst[:negative] cuts from the end and can empty the shorter one. Length normalisation divides 0 by 0. FixDrop long pairs before training. Fail fast on the first non-finite grad_norm. CPO fix: PR #6588.
2 · Flipped labels steer DPO
SymptomDPO moves toward an attacker's preference. CausePreference label flips. arXiv 2610.24945 (18 Oct 2026) gives Trim-K Robust-DPO with bounds. FixAudit labels. Use label_smoothing=0.1 as the cheap built-in.
3 · Judge labels are unstable
SymptomThe same pair gets a different verdict on a re-run. CauseA re-run of Arena-Hard's GPT-4.1 judge flips 21.2% of prompt outcomes; the aggregate moves ~1 pt (2610.30512). FixJudge each pair twice. Keep only pairs with the same verdict.

support_dpo/filter_pairs.py · trl 1.16.0
from datasets import load_dataset
from transformers import AutoTokenizer
from trl import DPOConfig
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
ds = load_dataset("json", data_files="acme_qa_pairs.jsonl", split="train")  # QA export
L = 1024                                       # the same value as DPOConfig.max_length
n0 = len(ds)
ds = ds.filter(lambda r: len(tok(r["prompt"] + r["chosen"]).input_ids) <= L and
                         len(tok(r["prompt"] + r["rejected"]).input_ids) <= L)
print(f"kept {len(ds)} of {n0} pairs")         # every kept pair fits: no empty response
args = DPOConfig(output_dir="support-dpo", max_length=L, beta=0.1,
                 model_init_kwargs={"dtype": "bfloat16"},
                 loss_type=["sigmoid", "sft"], loss_weights=[1.0, 0.2],
                 label_smoothing=0.1)          # Robust DPO; other Lab 5 settings unchanged
Filter on the full prompt + response length, with the training tokenizer.
label_smoothing assumes some labels are wrong.
Re-judged pairs land in the same JSONL; the filter runs again.
This bug does not crash; it destroys the run quietly. When a pair is longer than max_length, TRL cuts both responses to max_length minus the longer response length, and if that number is negative, the Python slice cuts from the end and can empty the shorter response. With a length-normalised loss such as SimPO this divides zero by zero, the first optimizer step writes NaN into every weight, and the loss shows 0. The fix is a data contract: drop every pair that does not fit, with the same tokenizer and the same max_length, and stop the job on the first non-finite grad_norm. Think of it as a luggage check at the gate: a bag that does not fit is removed before boarding, not cut in half in the air. The other two cards are about label quality: flipped labels can steer DPO, and LLM judge verdicts flip on about one prompt in five even when the aggregate looks stable. A likely question: does DPOTrainer have the same bug? DPO already drops long pairs; the empty-response NaN is in CPOTrainer, and PR 6588 fixes it there.
