from peft import LoraConfig
from trl import GRPOConfig, GRPOTrainer
from trl.rewards import accuracy_reward
from claims_data import claims_dataset
args = GRPOConfig(
    output_dir="qwen-claims-grpo",
    model_init_kwargs={"dtype": "bfloat16"},  # string ids load in float32
    per_device_train_batch_size=8,            # 8 x 1 GPU x 4 accum
    gradient_accumulation_steps=4,            # = 32 = 4 prompts x 8
    num_generations=8,
    use_vllm=True, vllm_mode="colocate",      # needs vllm==0.31.0
)                                             # no auto_find_batch_size
trainer = GRPOTrainer(
    model="Qwen/Qwen2.5-0.5B-Instruct",
    reward_funcs=[accuracy_reward],
    args=args,
    train_dataset=claims_dataset(2000, seed=7),
    peft_config=LoraConfig(r=16, lora_alpha=32, target_modules="all-linear",
                           task_type="CAUSAL_LM"),
)
trainer.train()
1 · Batch divisibility
SymptomValueError: generation_batch_size (6) must be divisible by num_generations (8). GRPO requires at least 2 generations per prompt to calculate the advantages. CauseAdvantages are computed within a group. A batch must hold whole groups. Fixper-device × GPUs × grad-accum = a multiple of num_generations: 1 GPU × 8 × 1, or 4 GPUs × 4 × 1 with num_generations=16.
2 · float32 OOM · TRL #6684
Symptomtorch.OutOfMemoryError … Tried to allocate 3.81 GiB for a 4B model on an 80 GB H100. CauseA string model id loads in float32: 16.1 GB weights + 16.1 GB grads + 32.2 GB AdamW ≈ 64 GB before activations. Fixmodel_init_kwargs={"dtype": "bfloat16"}. Log next(model.parameters()).dtype at step 0.
3 · vLLM pin and rollout sampling
Symptompip resolver conflict: vllm 0.32.0 is outside trl[vllm] vllm>=0.22.0,<=0.31.0. CauseTRL 1.16.0 pins the range. Truncated sampling (top_p, top_k) also biases the IS ratio. FixPin vllm==0.31.0. Sample rollouts with top_p=1.0, top_k=-1. Remove auto_find_batch_size: ValueError: auto_find_batch_size is not supported by GRPO.

These three errors stop most first GRPO runs, so fix them before you look at any reward curve. GRPO computes each advantage inside a group of completions for one prompt, so the batch must hold whole groups: 6 slots cannot hold a group of 8, and 8 per device times 4 accumulation steps gives 32, which is 4 prompts times 8. The OOM comes from a silent default: a model given as a string loads in float32, and for a 4B model the weights, gradients and AdamW states already need about 64 GB before activations, so one line with bfloat16 fixes it. The vLLM pin is a packaging trap: the newest vLLM is outside the range TRL 1.16 accepts, and when you do use vLLM, keep top_p at 1 and top_k at -1 so the importance-sampling ratio is not biased. Analogy: a relay race needs every runner of a team on the track; half a team cannot score. Likely question: "Does the eval batch also have to be divisible?" Yes, the same rule applies to the eval batch.
