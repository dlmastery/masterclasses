Interview · Embedding migration

A new embedding model means a new index, not a mixed one

Can you query a gemini-embedding-001 index with gemini-embedding-2 vectors?
No. Two models make two different vector spaces. Re-embed every chunk into a new table.
What else changes when you move from 001 to embedding-2?
No task_type: put task: search result | query: … in the text. A list of strings returns one vector. Truncated output is unit length.
How do you prove the migration is safe?
Golden set = queries with their expected chunk ids. Switch only if recall@10 of v2 ≥ v1. Keep v1 for rollback. Half-migrated index: 42% of the full re-embed gain

migrate.py · reads claim_chunks(id, title, content) from ingest
import os, numpy as np, psycopg
from google import genai
from google.genai import types
from pgvector.psycopg import register_vector
conn = psycopg.connect(os.environ["PG_DSN"], autocommit=True)
register_vector(conn)                    # after CREATE EXTENSION vector
client = genai.Client()                  # reads GEMINI_API_KEY
conn.execute("""CREATE TABLE claim_chunks_v2 (id bigint PRIMARY KEY,
  title text, content text, embedding vector(768) NOT NULL)""")  # no sequence
for cid, title, body in conn.execute(
        "SELECT id, title, content FROM claim_chunks").fetchall():
    doc = f"title: {title} | text: {body}"   # no task_type on embedding-2
    r = client.models.embed_content(model="gemini-embedding-2",
        contents=[types.Content(parts=[types.Part.from_text(text=doc)])],
        config=types.EmbedContentConfig(output_dimensionality=768))
    v = np.array(r.embeddings[0].values, dtype=np.float32)
    conn.execute("INSERT INTO claim_chunks_v2 VALUES (%s, %s, %s, %s)",
                 (cid, title, body, v))  # same ids as v1
conn.execute("CREATE INDEX ON claim_chunks_v2"
             " USING hnsw (embedding vector_cosine_ops)")
swap.sql · psql "$PG_DSN" -f swap.sql
-- run only after the gate passes:
-- recall@10(claim_chunks_v2) >= recall@10(claim_chunks)
BEGIN;
ALTER TABLE claim_chunks RENAME TO claim_chunks_v1;  -- rollback
ALTER TABLE claim_chunks_v2 RENAME TO claim_chunks;
COMMIT;

Ask each question and give the room twenty seconds before you reveal the answer. Q1 analogy: GPS coordinates from two map projections cannot be compared, so a vector from one model means nothing in the other model's index. Q2: gemini-embedding-2 has no task_type, so the RETRIEVAL_QUERY and RETRIEVAL_DOCUMENT settings that 001 used must move into the text: "task: search result | query: ..." for queries and "title: ... | text: ..." for documents. A plain list of strings in contents gives one aggregated vector (debug slide at the end of this chapter), and embedding-2 normalises truncated output itself. The code keeps v1's chunk ids in v2 (id bigint with no sequence), so the golden set maps to both tables. Do not copy v1 with LIKE ... INCLUDING DEFAULTS on a bigserial column: the copy reuses v1's sequence, which stays owned by v1, and dropping v1 later breaks v2's default. In production, send 100 inputs per call, each in its own Content. Q3: the golden set is a file of queries with their expected chunk ids. The memory-portability paper (2609.05339) found that a 50/50 mixed index recovered only 4.96 of the 11.90 points that a full re-embed gained, about 42%. Likely follow-up: "What about dual-read?" Send each query to both tables, serve v1, log v2 recall, and switch when v2 is equal or better.
