Interview · HNSW parameters

Tune efSearch against exact search, not against a default

What do HNSW M, efConstruction and efSearch change?
M = links per node: RAM, recall. efConstruction = build beam: build time, graph quality. efSearch = query beam ≥ k: recall, latency.
efSearch defaults: FAISS 16 · pgvector 40 · Chroma 100
How do you pick efSearch?
Sweep it against an exact flat index on a query sample. Raise it until recall@10 ≥ 0.95, then stop.
Re-tune when the corpus grows 10x: cost grows as Nc, not log N.

sweep.py · faiss-cpu 1.15.1 · no env vars
import faiss, numpy as np
rng = np.random.default_rng(7)
N, D, K = 100_000, 256, 10
centers = rng.standard_normal((1_000, D)).astype(np.float32)
noise = lambda n, s: s * rng.standard_normal((n, D)).astype(np.float32)
xb = centers[rng.integers(0, 1_000, N)] + noise(N, 0.3)   # clustered
xq = xb[rng.choice(N, 500, replace=False)] + noise(500, 0.1)
faiss.normalize_L2(xb); faiss.normalize_L2(xq)     # cosine == IP

flat = faiss.IndexFlatIP(D); flat.add(xb)          # exact baseline
_, gt = flat.search(xq, K)
hnsw = faiss.IndexHNSWFlat(D, 32, faiss.METRIC_INNER_PRODUCT)  # M=32
hnsw.hnsw.efConstruction = 80                      # default 40
hnsw.add(xb)
for ef in (16, 64, 128, 256):
    p = faiss.SearchParametersHNSW(efSearch=ef)    # per query
    _, I = hnsw.search(xq, K, params=p)
    r = np.mean([len(set(a) & set(g)) / K for a, g in zip(I, gt)])
    print(f"efSearch={ef:<4} recall@10={r:.3f}")

Ask each question and give the room twenty seconds before you reveal the answer. Q1: M is the number of links per node; more links cost RAM and give better recall. efConstruction is the candidate list while you build; a bigger list gives a better graph and a slower build, and you set it before you add vectors. efSearch is the candidate list per query; it must be at least k, and a bigger list gives more recall and more latency. The defaults are low: FAISS efSearch 16, pgvector hnsw.ef_search 40, Chroma 1.5.9 ef_search 100. Q2: build an exact IndexFlatIP on a sample of 500 to 5,000 queries, sweep efSearch, and stop at the first value that meets the recall target; in this run that is 64. Set efSearch per query with SearchParametersHNSW, which is thread-safe; changing index.hnsw.efSearch globally is not. The power-law paper (2609.02143) shows that graph-search cost grows as N to the power c, with c between 0 and 1, so re-tune when the corpus grows 10x. Analogy: efSearch is how many shops you check before you buy. Likely follow-up: "Why not set efSearch to 1,000?" Latency grows with it, and past the target the extra recall is too small to matter.
