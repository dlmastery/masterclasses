Prompt

Acme Insurance: 2M policy PDFs (some scanned), 1% change a day. Cite the page. Budget: re-embedding cost.

  1. Hash each file. Skip the 99% that did not change.
  2. Parse with layout. Keep prov.page_no. OCR only scans.
  3. Chunk by structure, in embedder tokens.
  4. Enrich once, at ingest. Compiled claims (LLM-extracted facts): 85.2% at 2.2k tokens vs 72.5% at 16.3k.
  5. Hash each chunk. Embed new hashes. Delete the doc_id's stale ids.
  6. Test in CI. Hidden white text (injection) never reaches a chunk. Pages out = pages in.

Back of envelope: 2M × 1% = 20k PDFs a day × ~40 chunks (assumed) = 800k hashed. Embed only new hashes; fixed-size re-embeds 57-68%.

Read the prompt aloud and ask the candidate for the day-2 plan before they draw the first load. A strong answer starts with change detection at two levels: a cheap hash of the file bytes before parsing, because with 1% daily churn the cheapest embedding is the one you never compute, and then a sha256 per chunk at the embedder, because spans and chunks exist only after parsing. Unchanged files are skipped and their vectors stay as they are; nothing is written. Parse with layout and keep page numbers as provenance: Docling stores them in each item's prov list, and that page goes into the chunk metadata. Chunk by structure in the embedder's tokens, enrich once at write time, and store doc_id, page, acl_groups and the embedding version on every vector. For an edited file, delete the ids of that doc_id that the new version no longer produces, then upsert the new ones, so stale wording cannot be cited. Analogy: the change detector is a library's returns desk; only the books that came back changed go back to the bindery. The CI test catches the silent failures: hidden PDF text that becomes a prompt-injection path, and parsers that drop pages without an error. Hand-off: the debug drill takes one stage of this pipeline, chunk then embed, and shows how it loses text without an error.
