Interview · Filters and normalisation

Filters and unnormalised vectors return wrong rows without an error

A filtered top-10 in pgvector returns only 4 rows. Why?
The filter runs after the index scan: 40 candidates (ef_search) × 10% match = 4 rows.
Fix: SET LOCAL hnsw.iterative_scan (0.8.0+). Assert rowcount == LIMIT.
Why do cosine and dot-product rankings disagree after truncation?
Request output_dimensionality=768 from 001 and the vector is not unit length. Normalise it yourself. embedding-2 normalises for you. Inner product = cosine only for unit vectors.
search.py · pip install "psycopg[binary]==3.3.6" pgvector==0.5.1 numpy
import os, numpy as np, psycopg
from pgvector.psycopg import register_vector
conn = psycopg.connect(os.environ["PG_DSN"])  # postgresql://u:pw@host/rag
register_vector(conn)
q = np.random.default_rng(0).standard_normal(768).astype("float32")  # demo
TENANT = 42                            # the caller's tenant, from auth
SQL = ("SELECT id FROM claim_chunks WHERE tenant_id = %s"
       " ORDER BY embedding <=> %s LIMIT 10")
with conn.transaction():               # SET LOCAL ends at commit
    conn.execute("SET LOCAL hnsw.iterative_scan = relaxed_order")
    rows = conn.execute(SQL, (TENANT, q)).fetchall()
assert len(rows) == 10, f"filtered top-10 returned {len(rows)} rows"
print(len(rows), "rows")               # expected: 10 rows
normalize.py · pip install faiss-cpu==1.15.1 google-genai==2.33.0 · GEMINI_API_KEY
import faiss, numpy as np
from google import genai
from google.genai import types
r = genai.Client().models.embed_content(model="gemini-embedding-001",
    contents=["Refund not received", "Login loop after Okta SSO"],
    config=types.EmbedContentConfig(output_dimensionality=768))
xb = np.array([e.values for e in r.embeddings], dtype=np.float32)
print(np.linalg.norm(xb, axis=1))      # not 1.0: 001 below 3,072 dims
faiss.normalize_L2(xb)                 # in place: inner product == cosine
assert np.allclose(np.linalg.norm(xb, axis=1), 1.0, atol=1e-3)
# do the same to every query; in pgvector use vector_cosine_ops

Ask each question and give the room twenty seconds before you reveal the answer. Q1 is the most common pgvector surprise. The pgvector README says: "If a condition matches 10% of rows, with HNSW and the default hnsw.ef_search of 40, only 4 rows will match on average." The index returns its beam of 40 candidates first, and the WHERE clause runs on that beam afterwards. Iterative scan (pgvector 0.8.0 and later) keeps scanning until LIMIT rows match or hnsw.max_scan_tuples (default 20,000) is reached; in the animation it scans about 100 tuples to find 10 matches. relaxed_order can return rows slightly out of order, so re-sort in an outer query or use strict_order. SET LOCAL lasts only for the transaction, which is why the query sits inside conn.transaction(); that is also safe with connection pools. Q2: if you request output_dimensionality=768 from gemini-embedding-001, the returned vector is not unit length, so inner product ranks by length as well as by angle. Call faiss.normalize_L2 on data and queries, or use vector_cosine_ops in pgvector. gemini-embedding-2 normalises truncated output itself. Likely follow-up: "How would you catch this in CI?" Assert unit norm on a sample at write time, and assert rowcount == LIMIT on filtered queries.
