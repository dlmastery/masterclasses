### c01-03-workflow-vs-agent.html - Climb from workflow to agent only when an eval shows the lower rung fails
- **id:** `adk-c01-workflow-vs-agent`
- **content:** Definitions (Anthropic 'Building effective agents', 2024-12-19, https://www.anthropic.com/engineering/building-effective-agents): workflows are 'systems where LLMs and tools are orchestrated through predefined code paths'; agents are 'systems where LLMs dynamically direct their own processes and tool usage'. The complexity ladder (five rungs): single call + retrieval -> prompt chain / router workflow -> single agent with tools -> orchestrator-workers -> multi-agent with handoffs / A2A. Cost of climbing (Anthropic 'How we built our multi-agent research system', 2025-06-13): agents use ~4x the tokens of chat, multi-agent ~15x. Compounding error: at 95% per-step reliability a 20-step run succeeds 0.95^20 = ~36%. Google's rule: 'If you can clearly map the workflow, use determinism.' (Why we built ADK 2.0, 2026-07-01). Illustrative refund benchmark from the same post (gemini-3.5-flash, mock APIs): 5,152 -> 2,265 tokens per run, 7.2 s -> 5.7 s, vanilla tool-calling agent vs ADK 2.0 workflow. .callout.pitfall: starting with a multi-agent design before one agent with tools has failed an eval. Interview angle: 'when would you NOT build an agent?'

### c03-02-first-workflow.html - A chain tuple wires nodes, and each return value becomes the next node's input
- **id:** `adk-c03-first-workflow`
- **content:** What can be a node (NodeLike): plain Python functions (sync, async, generators; auto-wrapped in FunctionNode), Agents (usually mode='single_turn'), BaseTool instances, nested Workflows, START (sentinel '__START__', never executes). Every node: (1) validate node_input against input_schema, (2) run user logic, (3) normalize each yield - None is dropped, an Event passes through, a RequestInput becomes an interrupt, any other value becomes Event(output=value). Event fields: output (to next node; only ONE per node run), message (shown to user), state (delta), route. You do not need session state for hand-offs. Ten construction-time validation rules include: unique names, START present with no incoming edges and no routes, every node reachable, no unconditional cycles, output_schema must equal successor input_schema (often inferred from type hints), an LlmAgent(mode='chat') only directly after START. ### c03-06-dynamic.html - Dynamic workflows use plain Python control flow and still checkpoint every child node
- **id:** `adk-c03-dynamic`

### c04-03-retry.html - RetryConfig handles transient faults, and a broad except silently disables it
- **id:** `adk-c04-retry`
- **content:** RetryConfig (google.adk.workflow, Pydantic) defaults: max_attempts 5 (includes the first try; 0 or 1 = no retry), initial_delay 1.0 s, max_delay 60 s, backoff_factor 2.0, jitter 1.0, exceptions None (retry on all). ctx.attempt_count is exposed. @node(timeout=30.0) raises NodeTimeoutError, which counts as retryable. Semantics: a failed node reruns in full including children started with ctx.run_node; completed children are replayed, not re-executed; a failed sub-workflow is retried as a whole; with parallel_worker the policy applies per item. Contrast: RetryConfig = transient, backoff, the model sees nothing; ReflectAndRetryToolPlugin(max_retries=3, 4 attempts total) = semantic, the error goes back to the model as reflection guidance. ### c07-03-router-parallel.html - Routing and parallel fan-out pay off when the split is cheap to decide
- **id:** `adk-c07-router-parallel`
- **content:** Router pattern: classify, then dispatch to a specialist; use when inputs fall into distinct categories you can classify accurately (Anthropic). Resource-aware routing (Gulli ch. 16): a Flash/Lite classifier sends SIMPLE to a cheap agent and COMPLEX to a Pro agent; failure modes - a weak router sends hard queries to the cheap model, the router's own cost is ignored, tone differs between models, evals pass on the big model and silently regress on the small one (run the full suite per model). Code-first variant: the ambient expense recipe routes on amount with a plain function (under $100 auto-approve, zero LLM calls). Parallelization: sectioning (independent sub-tasks) vs voting (self-consistency: N candidates -> JoinNode -> voter); Anthropic: parallel subagents and tool calls cut research time up to 90%. Failure modes: cost multiplies with N, conflicting outputs the merge cannot reconcile, race on shared state, rate limits. Mitigations: DEFAULT_ROUTE, log the chosen route per request (BigQuery analytics), per-branch keys. Interview angle: when is a deterministic router better than an LLM router? (data-determined decisions, thresholds, status codes).

### c07-05-generator-verifier.html - A generator-verifier loop converges only as fast as its verifier is trustworthy
- **id:** `adk-c07-generator-verifier`
- **content:** Evaluator-optimizer (Anthropic): use when there are 'clear evaluation criteria, and iterative refinement provides measurable value'. Verifier's rule (Jason Wei, 2025-07-15): 'The ease of training AI to solve a task is proportional to how verifiable the task is' - objective, fast, scalable, low-noise, continuous. Evidence: Self-Refine ~20% absolute average gain; Reflexion 91% pass@1 on HumanEval vs 80% for GPT-4; AlphaCodium 19% -> 44%. Separate evaluator beats self-evaluation: Anthropic 'Harness design for long-running apps' (2026-03-24) - retro game maker solo run 20 min, $9, core game broken; full planner-generator-evaluator harness 6 h, $200, working; evaluator uses Playwright on the live app. ADK 2.0 shape: generator -> verifier (schema, function, lint/tests, or critic LLM with Literal output) -> router with PASS / FAIL (back-edge with the failure reason in state) / GIVE_UP (escalate to ModelConsultTool or RequestInput), bounded by MAX_ATTEMPTS. 1.x vs 2.0 in codelabs: 'Building a Multi-Agent System using Gemini and Gemma models' uses LoopAgent(max_iterations=3) + escalate; in 2.0 the Judge becomes a router node and the back-edge is the loop. Failure modes: sycophantic critic approving round 1, critic that never approves, oscillation between drafts, context bloat from appended critiques; retry without feedback repeats the same failure. Interview angle: why should the evaluator be a different agent (or code) than the generator?
- **visual:** Bespoke loop (Deck.register): generator (n-model) -> sql_guard diamond (n-risk) splitting PASS (green to run_query n-tool), FAIL (dashed back-edge carrying a speech bubble 'starts with DELETE'), GIVE_UP (to human n-human). A token circles with an attempt counter 1 -> 2 -> 3; on step 3 the FAIL path is blocked and the token exits to GIVE_UP; alternate step shows PASS. Step 4: the 20 min/$9 vs 6 h/$200 stat pair counts up with 'broken' vs 'working' tags.
- **code:** From research-adk-platform/07 section 2.2 (Pattern A guard node, ~18 lines): class Draft(BaseModel): sql: str; attempts: int = 0; writer = Agent(name='sql_writer', ..., output_schema=Draft); MAX_ATTEMPTS = 3; def sql_guard(node_input: Draft): ok = node_input.sql.strip().upper().startswith('SELECT') and 'DELETE' not in node_input.sql.upper(); if ok: return Event(route='PASS', output=node_input); if node_input.attempts + 1 >= MAX_ATTEMPTS: return Event(route='GIVE_UP', output=node_input); return Event(route='FAIL', output=node_input.model_copy(update={'attempts': node_input.attempts + 1})); root_agent = Workflow(name='verified_sql', edges=[('START', writer, sql_guard), (sql_guard, {'PASS': run_query, 'FAIL': writer, 'GIVE_UP': escalate_to_human})]). ### c08-03-harness-verifiers.html - Put the cheapest reliable verifier after every risky step, and turn every failure into a sensor
- **id:** `adk-c08-harness-verifiers`
- **content:** Verifier ladder (cheapest first; research-adk-platform/06 section 6 and /07 section 1): 1 schema (output_schema / input_schema / state_schema, StateSchemaError) -> 2 rule or function node (regex, ID exists, SQL dry run, lint, unit tests) -> 3 calibrated classifier (ClassifierNode threshold) -> 4 LLM critic node with rubric -> 5 stronger-model consult (ModelConsultTool) -> 6 human (RequestInput). Cost and latency rise per rung; 'use the lowest rung that catches the error'; Anthropic's SDK post orders verification the same way (rules, visual feedback, then LLM-as-judge 'not very robust'). Harness engineering (Hashimoto 2026-02-05; Bockeler 2026-04-02): guides (feedforward: instruction, static_instruction, skills, schemas, graph topology) and sensors (feedback), each computational or inferential. ADK sensors: function nodes, RetryConfig, ToolCallIntegrityPlugin (HMAC-SHA256 'v1:' stamp on each function call, blocks tampered or replayed calls; not applied to tools run as workflow nodes), critic nodes, ClassifierNode, ModelArmorPlugin, AutoTracingPlugin. The Hashimoto loop in ADK: every production failure -> adk eval_set add_eval_case -> CI gate. Antigravity as the dev-time harness: lifecycle hooks in .agents/hooks.json (SessionStart, PreToolUse, PostToolUse, PreInvocation, PostInvocation, Stop); a Stop hook that returns {'decision': 'continue', 'reason': ...} keeps the agent working until tests or evals pass; PreToolUse can deny or force_ask; a read-only verifier custom agent (permissionMode: plan) ends every report with APPROVED / CONDITIONAL / BLOCKED. Interview angle: what does a PRM add, and does ADK ship one? (no built-in PRM; wrap one as a guard node or custom metric).

### c08-06-guardrails.html - Design for compromise: limit what a successful prompt injection can do
- **id:** `adk-c08-guardrails`
- **content:** Threat models: the lethal trifecta (Simon Willison, 2025-06-16): private data + untrusted content + external communication = exfiltration; 'LLMs are unable to reliably distinguish the importance of instructions based on where they came from.' Agents Rule of Two (Meta AI, 2025-10-31): within one session an agent may have at most two of [A] processes untrusted input, [B] accesses sensitive systems or private data, [C] changes state or communicates externally; all three -> require HITL or a fresh session. Detection alone fails: adaptive attacks broke 12 defenses at over 90% (research-frontier/05). Architectural defences: CaMeL ('Defeating Prompt Injections by Design', Google / Google DeepMind / ETH Zurich, arXiv 2503.18813): a privileged LLM writes a program from the trusted query, a tool-less quarantined LLM parses untrusted data, an interpreter tracks provenance; plan-then-execute / action-selector in ADK: the LLM classifies, code decides what can run. Google defence in depth for ADK (https://adk.dev/safety/): identity (Agent Identity - SPIFFE-based, 24 h X.509 certs, no long-lived keys); in-tool policy (SELECT-only on allow-listed tables; identity from trusted state); callbacks (before_tool_callback blocks refunds over a limit); plugins - ModelArmorPlugin (2.8) screens prompts and responses, fails closed by default, templates must be in the same region; hermetic sandboxed code execution with no network; Agent Gateway egress allow/deny; escape model output in the UI (an injected <img> tag can exfiltrate). ADK hardening: 2.8 'fence relayed agent output so it cannot pose as instructions', 2.11 ToolCallIntegrityPlugin, A2A requires https for non-loopback agent cards (2.9). Limits: Model Armor is single-turn, no Base64 decoding, no audio or video, 4 MB documents; console Model Armor settings in Gemini Enterprise do NOT protect ADK agents - configure it in code. Supply chain: LiteLLM 1.82.7/1.82.8 PyPI compromise -> pin and hash dependencies. Codelab 'Build a Secure Agent with Model Armor and Identity' (https://codelabs.developers.google.com/secure-customer-service-agent/instructions): Model Armor callbacks, AGENT_IDENTITY, conditional IAM limited to one dataset, red-team scripts. OWASP Top 10 for Agentic Applications for 2026 exists (2025-12-09) - cite the title only.

### c08-07-qa.html - Interview drill: prove your agent is reliable and safe
- **id:** `adk-c08-qa`
- **content:** Four .qa pairs. Q1: RetryConfig, a routed back-edge, or ReflectAndRetryToolPlugin? A: RetryConfig for exceptions and transient faults (backoff, completed children replayed, model sees nothing); a back-edge for semantic failures where the output is valid but wrong (carries feedback, needs a counter); ReflectAndRetryToolPlugin for tool errors the model can fix (reflection_guidance, 3 retries, override extract_error_from_result for soft errors). Q2: EXACT vs IN_ORDER vs ANY_ORDER trajectory matching? A: EXACT allows no extra or missing calls; IN_ORDER requires the expected calls in order but allows extras; ANY_ORDER ignores order; over-strict EXACT fails on harmless extra lookups. Q3: pass@k or pass^k for a customer-support agent, and why? A: pass^k - every attempt must succeed; at 75% per trial pass^3 is ~42%; use multi_run_config with min_over_runs or pass_rate. Q4: Apply the Rule of Two to an email assistant that reads inbox and can send mail. A: it has all three (untrusted email, private data, external send); drop one per session (read-only summarizer; or send only to allow-listed recipients) or put a RequestInput approval on send; add ModelArmorPlugin, identity from state and egress policy as extra layers.
