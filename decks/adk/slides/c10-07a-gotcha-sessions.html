Cloud Run forgets the HR conversation without a session service

SymptomAn employee loses the conversation after a scale event. CauseNo --session_service_uri: the container "falls back to the in-memory session and artifact services". FixPoint sessions at Agent Runtime, or at a SQLAlchemy URL.
labs/adk/c10-acme-hr/ship.sh · excerpt
adk deploy cloud_run --project=$PROJECT --region=$REGION \
  --service_name=acme-hr \
  --session_service_uri="agentengine://$AGENT_ENGINE_ID" \
  hr_agent -- --no-allow-unauthenticated

This is the first of three deploy defaults that bite the Acme HR assistant in its first production week. Press once: turn 1 of the conversation lands on instance A, and turn 2 lands on a new instance B after a scale event. Press again: Cloud Run recycled instance A, and without a session service URI the container keeps sessions in memory, so session s1 is gone; the ADK docs say the container "falls back to the in-memory session and artifact services" and loses them when an instance is recycled. Press again: the fix is one flag: --session_service_uri with agentengine:// and the Agent Runtime id, or a SQLAlchemy URL for your own database; now both instances read and write the same store. Analogy: a waiter who keeps the order in his head goes home at the end of the shift; write the order on the ticket. Likely question: "Does min-instances=1 fix it?" No: a warm instance still restarts and scales out, so keep the state outside the container. The same logic applies to --artifact_service_uri for files.
