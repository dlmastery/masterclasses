ROPE: an origin check in code stops every reworded injection

arXiv 2608.274962026-08-27

ROPE: Routed Origin Policy Enforcement against Indirect Prompt Injection

Deterministic origin checks on a few sensitive parameters: attack success 1.6-2.6%, with 82-100% of clean utility kept.
List the 5-10 params that move money or data out. Guard only those.
ROPE, from August, makes the security decision in code instead of asking a model to spot the attack. Press once: without a gate, a web page returned by a tool carries an injected IBAN ending 6666, the agent copies it into transfer_funds, and the money goes to the attacker. Press again: the origin gate checks only the sensitive parameter: a value passes only if your code saw it in the user turn or in a trusted record, so the user's IBAN ending 1001 passes and the injected one stops; the paper reports attack success of 1.6 to 2.6% while keeping 82 to 100% of the clean utility. Press again: the attacker rewords the injection five times and the gate gives the same answer every time, because it never reads the wording, only where the value came from. The action for Monday: list the five to ten parameters that move money or data out of Acme and guard only those. Analogy: a bank checks that the payee is on your saved list; it does not judge whether the phone call sounds suspicious. Likely question: "Where does the trusted list come from?" From your own code: the parsed user turn and your CRM, never from model output. The next slide shows the hook.
