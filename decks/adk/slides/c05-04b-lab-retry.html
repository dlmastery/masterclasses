RetryConfig retries the gateway 503 with exact 0.5 s and 1.0 s waits

labs/adk/lab5b-payouts-durable/payouts/app.py · excerpt
@node(retry_config=RetryConfig(max_attempts=4, initial_delay=0.5,
                               backoff_factor=2.0, jitter=0.0,
                               exceptions=[ConnectionError,
                                           "NodeTimeoutError"]),
      timeout=2.0)
async def pay(ctx: Context, node_input: str):  # the analyst's reply
  yield Event(message=f"gateway attempt {ctx.attempt_count}")
  if node_input.strip().lower() != "yes":
    yield Event(output="CANCELLED"); return
  if ctx.attempt_count < 3:
    raise ConnectionError("gateway 503")   # attempts 1-2 fail, 3 pays
  key = "payout-" + ctx.invocation_id      # same key on every run
  yield Event(output=f"PAID idempotency_key={key}")

Step 2 of Lab 5B is the pay node. Walk the RetryConfig line first: max_attempts counts the first try, so 4 means one try and up to three retries, and with jitter at zero the waits are exact: 0.5 seconds and then 1.0 second, because the delay is initial_delay times backoff_factor to the power attempt minus one. The node fails twice with a gateway 503 and pays on attempt 3, which ctx.attempt_count shows; the fourth slot stays unused. The last click is the idempotency key: payout- plus the invocation id, the same value on every retry and every resume, so the gateway can drop a duplicate charge. The output needs the driver main(), which the next slides build. Think of backoff as a polite caller: wait a little, then a little longer, so a busy line has time to clear. A likely question: "Is the attempt counter saved?" No: after an interrupt or a restart the node gets its full retry budget back.
