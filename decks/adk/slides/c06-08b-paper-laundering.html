Approving one MCP call is not a sandbox for the server process

arXiv 2610.22301 2026-10-15

My Credentials, Please: Detecting Filesystem Capability Laundering in MCP Servers at Scale

787 of 4,806 triaged servers (16.4%) touch the filesystem despite non-filesystem labels. 150 confirmed vulnerable.
Run stdio servers in a container with one mounted directory. Check path arguments in before_tool_callback.
Paper arXiv 2610.22301
The second paper shows why a human "yes" is not enough. Step 1: the authors triaged 4,806 MCP servers; 787 of them, 16.4%, touch the filesystem even though their labels say something else, and 150 were confirmed vulnerable, with 13 advisories and 2 CVEs in Anthropic's Git MCP server. Step 2: a tool called get_weather can open your cloud credentials file, because approving one call trusts the whole server process, with your user's file permissions. Step 3: the real boundary is the process: run stdio servers in a container that mounts one directory, here the claims documents. Step 4: also check path arguments against an allow-list in before_tool_callback, so a tool cannot even ask for a file outside it. Think of approval like letting a plumber into the house: you approved the sink, but he can walk into every room unless you lock the doors. A likely question: "Is tool_filter enough?" It limits what the model can call, but not what the server process can do, so you need the container too.
