The instruction reads state. {user:language?} renders '' if missing.

Session 2 gets app: and user: back. Unprefixed keys stay behind.

Same file, the agent and the second session. Step 0: this is the state after Tom asked about glass in session 1; the temp:last_topic key was trimmed before commit, so it was never stored. Click 1: the instruction reads state with curly-brace templates. The question mark in {user:language?} makes the key optional, so a missing key renders as an empty string; without the question mark a missing key raises a KeyError on the first turn, so seed required keys at create time. Click 2: output_key writes the final answer into last_answer, which has no prefix, so it belongs to this chat only. Click 3: create a second session for the same user: it starts with the app: and user: keys and nothing else. The in-memory service keeps these only while the process runs; the next slide moves sessions into a SQLite file. Analogy: a new call opens the same customer file, with a clean notepad. A likely question: "Can I read user: keys before any session exists?" Yes, with get_user_state on services that support it.
