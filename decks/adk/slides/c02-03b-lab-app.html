An App bundles the agent and its plugins into one deployable unit

labs/adk/lab2-claims-api/agents/claims_api/agent.py · excerpt
from google.adk import Agent
from google.adk.apps import App
from google.adk.plugins import LoggingPlugin
# ... lookup_policy and AuditPlugin from the previous slide

root_agent = Agent(
    name="claims_assistant",
    model="gemini-3.5-flash",
    instruction=("Answer coverage questions. "
                 "Always call lookup_policy first."),
    tools=[lookup_policy],
)

# adk run / web / api_server use a variable named `app` when it exists
app = App(name="claims_api", root_agent=root_agent,
          plugins=[LoggingPlugin(), AuditPlugin()])

The App is what you run and deploy: one agent tree plus its plugins.

root_agent answers coverage questions with one tool.

App takes name, root_agent and plugins. A wrong kwarg raises.

The CLI loads app if it exists. Else it wraps root_agent.

Same file, bottom half. Click 1: root_agent is the claims assistant with one tool. Click 2: the App holds the agent and the plugins as one deployable unit. App is a pydantic model that rejects unknown fields, so App(agent=...) fails: the field is root_agent. It has three more config fields (events compaction, context cache, resumability) that later chapters use. Click 3: adk run, adk web and adk api_server share one loader. It imports agent.py through __init__.py ("from . import agent"); if the module has a variable named app it uses that App and its plugins, otherwise it wraps root_agent. Put the .env file with GOOGLE_API_KEY in agents/claims_api/. The audit log is visible in the adk web State tab, or through the session GET two slides later. Analogy: the App is a shipping container: the agent is the cargo, and the plugins travel in the same box. Never pass plugins to the Runner: that is deprecated, and with app= it raises.
