class ManagerDecision(BaseModel):
  approved: bool
  amount: Optional[float] = None          # partial refund
  note: str = ""
# ... manager_gate, run 2 (rerun_on_resume=True):
  answer = ctx.resume_inputs.get(iid)     # None on the first run
  # ... (the "if answer is None" branch is skipped)
  d = ManagerDecision.model_validate(answer)
  if not d.approved:
    yield Event(route="rejected")
  elif d.note:
    yield Event(state={"note": d.note}, route="revise")
  else:
    yield Event(state={"final_amount": d.amount or amount},
                route="approved")

The reply must fit this schema.

A JSON object such as {"approved": true} fits it.

The function runs again from the top. Now get(iid) returns the reply.

One route fires: approved, rejected or revise.

A note means revise: a new pass, a new run_id, a new id.

Step 3 of Lab 5A is the second half of manager_gate. ManagerDecision is the reply schema: approved is required, amount allows a partial refund, and note asks for a new draft. Because the decorator says rerun_on_resume=True, the whole function runs again from the top after the reply, and this time resume_inputs.get(iid) finds the answer, since invocation_id and run_id are the same on a resume. With the default rerun_on_resume=False, the hand-off pattern, the reply itself becomes the node output and the next node must read it; Lab 5B uses that pattern. model_validate turns the reply into a ManagerDecision, and exactly one route fires. The revise route goes back to draft_reply inside the same invocation, so the gate runs again with run_id 2 and asks with a new id ending in _2. Think of a revise as a new form with a new ticket number, so an old answer can never approve a new draft. A likely question: "What if the manager types approve, not JSON?" model_validate raises a ValidationError; step 5 shows why.
