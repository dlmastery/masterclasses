Gotcha OpenAPIToolset

The SSRF guard blocks 127.0.0.1 until you allow private access

SymptomThe tool result says Tool get_claim_status execution failed. ... Execution Error: Blocked host: 127.0.0.1 Causeallow_private_network_access=False by default. Loopback, private, link-local (cloud metadata), *.internal and *.local are refused. FixSet it to True for a dev or internal API only. In production, call a public or VPC-routed hostname.
This is the error you hit the first time OpenAPIToolset calls a local API. Step 1: the tool does not raise; it returns an error result that ends in "Execution Error: Blocked host: 127.0.0.1". Step 2: the cause is ADK's SSRF guard. By default, REST API tools refuse loopback, private and link-local addresses, which include the cloud metadata service, plus names such as localhost, metadata.goog and anything under .internal or .local. Public hostnames pass. Step 3: allow_private_network_access=True lets 127.0.0.1 through, which is right for this lab, but it lifts the guard for every private host, including the metadata endpoint, which holds cloud credentials. So keep it for a dev or internal API only, and in production call a public or VPC-routed hostname. Note that MCP connections do not go through this check. Think of a mail room that refuses letters addressed to the vault: turning that rule off for your desk turns it off for the vault too. A likely question: "Why is metadata dangerous?" A prompt-injected URL could make the agent fetch the instance's service-account token; the paper slides show SSRF to metadata in real MCP servers.
