from google.adk.tools import FunctionTool, ToolContext

def add_to_cart(item: str, tool_context: ToolContext) -> dict:
    """Adds an item to the user's cart."""
    cart = tool_context.state.get("user:cart", [])
    cart.append(item)
    tool_context.state["user:cart"] = cart      # all sessions
    tool_context.state["temp:last_op"] = "add"  # this call only
    return {"status": "success", "cart_size": len(cart)}

async def confirmation_threshold(amount: int,

A tool is an interface for a model, so design it with the same care as a user interface; Anthropic calls this the agent-computer interface. Step 1: the endpoint-style tool returns UUID rows that the model cannot use, and it fills the window; the workflow-style search returns three names, and the concise format uses about one third of the tokens. Step 2: the error morphs from a stack trace into a hint that tells the model what to do next. Steps 3 to 5 walk the ADK code: the docstring is the description, ToolContext is found by its type annotation and is hidden from the model, state prefixes set the scope, and require_confirmation takes a boolean or an async predicate. Analogy: a good tool is a vending machine with labelled buttons, not a warehouse key. Likely student question: "How many tools is too many?" There is no fixed number; overlap is the failure, and with hundreds of tools you defer-load them with Tool Search, which cut definition tokens by 85 percent.
