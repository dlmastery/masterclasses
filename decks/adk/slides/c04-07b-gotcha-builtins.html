Gotcha Built-in tools

Gemini 2.x rejects google_search next to a function tool

pricing_analyst/agent.py · one agent, mixed tools

from google.adk.tools import google_search

def my_function_tool(policy_id: str) -> dict: ...   # any FunctionTool

pricing_analyst = LlmAgent(
    name="pricing_analyst", model="gemini-2.5-flash",

400 INVALID_ARGUMENT: Tool use with function calling is unsupported
ModelBuilt-in + function tool in one agent
Gemini 3+Accepted in the same request.
Gemini 2.xRejected. Use AgentTool, or GoogleSearchTool(bypass_multi_tools_limit=True).
Symptom400 INVALID_ARGUMENT: Tool use with function calling is unsupported CauseBefore Gemini 3, a built-in tool and function declarations cannot share one request (model_name_utils.py L199-214). FixGive each built-in its own agent and call it through AgentTool, as on the last slide.
This is the bug that made the AgentTool split necessary in the first place. Put google_search and any function tool on one Gemini 2.x agent and the API rejects the request with 400 INVALID_ARGUMENT: Tool use with function calling is unsupported. The rule lives in utils/model_name_utils.py, lines 199 to 214: Gemini 3 and later accept built-in tools in the same request as function declarations, earlier models do not. You have three fixes: give each built-in its own agent and call it through AgentTool, as on the last slide; or on an older model use GoogleSearchTool(bypass_multi_tools_limit=True), which makes ADK swap in a search sub-agent for you; or move to Gemini 3 and later. The same family of errors shows up at startup as "Agent ... has sub-agent transfer targets but is configured with GoogleSearchTool without bypass_multi_tools_limit=True" when the agent also has sub_agents. Analogy: on the old models the search tool insists on an office of its own. A likely question: "If Gemini 3 accepts the mix, why keep AgentTool?" Each subagent keeps its pages and code out of the root context, so the root stays small and cheap.
