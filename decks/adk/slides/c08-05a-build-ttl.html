Post Running a Software Factory Efficiently at Uber Scale
The cache lab used a 15-minute TTL for a three-turn demo, but real Acme customers go quiet while they look for a bill or make coffee. The timeline shows one chat with turns at minutes 0, 2, 14 and 40, and the cache is created on turn 2, so each TTL counts from minute 2. At the start you see a 5-minute TTL, which Uber used before: it misses both long pauses. Press once: the lab's 900 seconds survives the 12-minute pause but not the 26-minute one, so turn 4 re-sends all 9,480 tokens. Press again: 3,600 seconds keeps both turns a hit, so turn 4 reads 8,960 tokens from the cache and sends only 520 fresh. Press again: the trade-off is storage, because a longer TTL bills more storage-hours while the customer is idle, so pick about the 90th-percentile pause, not the longest one. Think of the TTL like a parking meter: pay for the time your customers really stay. A likely question: "What if I mistype the field?" The config classes are pydantic models with extra="forbid", so a typo such as ttl_second raises a validation error instead of being ignored.
