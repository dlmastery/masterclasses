root_agent = Agent(name="hr_agent", model="gemini-3.5-flash",
    instruction=("Answer Acme HR policy questions. "
                 "Use get_salary_band only for the caller."),
    tools=[get_salary_band])

template = os.environ["MA_TEMPLATE"]      # full resource name
app = App(name="hr_agent", root_agent=root_agent, plugins=[
    HrGuardPlugin(),                      # runs first
    ModelArmorPlugin(config=ModelArmorConfig(
        prompt_template_name=template,
        response_template_name=template,
        tool_output_template_name=template,   # new
        block_on_screening_failure=True)),    # default
])

tool_output_template_name screens tool results: the indirect-injection path.

Plugins run in list order. A reused plugin name raises already registered.

If the Model Armor API errors, the turn is blocked: fail closed.

The managed ModelArmorPlugin is the inner ring, and App is where both rings meet. Press once: one template screens three paths, the prompt, the model reply and, new in this release, every tool output, which is the path indirect injection uses; watch the E-1001 call pass the own-id check, the L5 result pass the tool-output screen, and the reply pass the response screen. Press again: App takes the plugin list in order, so our deterministic guard runs before the classifier, and two plugins with the same name raise "already registered". The loader picks app before root_agent, so adk web finds the plugins without a code change. Press again: an injection prompt stops at the prompt screen and the user gets the default blocked message; block_on_screening_failure=True is the default, so an API error also blocks the turn. Analogy: the badge reader is our code, the security scanner inside is Model Armor; it looks for dangerous content but does not know the org chart. Likely question: "Why not set Model Armor in the Gemini Enterprise console?" Those settings do not protect ADK agents, so the plugin stays in code. Next: step 2 traces this guarded app.
