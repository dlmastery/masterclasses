POST /run returns the whole turn as a JSON list of events

$ curl -s -X POST localhost:8000/run \
    -H "Content-Type: application/json" -d '{
  "appName":"claims_api","userId":"u-tom","sessionId":"claim-77",
  "newMessage":{"role":"user","parts":[
    {"text":"What is my collision deductible on POL-448120?"}]}}'

One POST runs one turn of the App in the session you created.

Bodies use camelCase: appName, sessionId. snake_case also works.

The reply arrives once, when the turn ends: tool call, tool result, answer.

The last event holds the text. Read content.parts for it.

Click 1: the request names the app, the user and the session; the bodies use camelCase, and snake_case names such as app_name also work because the request model accepts both. Click 2: /run waits for the whole turn and then returns a JSON list of Events: the model's functionCall for lookup_policy, the functionResponse with the deductible, and the final text. The AuditPlugin also ran, so the session now has one audit_log entry; the next-but-one slide reads it. Click 3: the answer is in the last event's content.parts. Analogy: /run is a letter that arrives when the turn is done. A likely question: "Is the response shape stable?" It is the Event model that the Python Runner yields, serialised with camelCase aliases, so the same parsing code works for both.
