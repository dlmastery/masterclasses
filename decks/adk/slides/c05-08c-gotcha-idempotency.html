from uuid import uuid4
async def pay(ctx: Context, node_input: str):
  key = str(uuid4())            # a new key after every resume
  yield Event(output=f"PAID idempotency_key={key}")

  key = "payout-" + ctx.invocation_id      # same key on every run

The third retry bug is the expensive one. Resume is at-least-once: if the process crashes after the gateway charged the card but before the node's event was saved, the resumed run executes pay again. With a uuid4 key, the second charge carries a new key, so the gateway cannot tell it is a repeat and ACME-GmbH is paid twice. With payout- plus the invocation id, every retry and every resume of the same run sends the same key, and the gateway drops the duplicate. The ResumabilityConfig docstring says it plainly: "Tool call to resume needs to be idempotent." Think of the idempotency key as a cheque number: the bank pays a given cheque number once, however many times it is presented. Two related points for questions: Pub/Sub triggers create a new session for each redelivery, and since 2.12.0 tools can see the trigger delivery id to detect it; and do not change the graph while runs are paused, because checkpoint versioning is still an open item.
