Scoped state: pick the prefix by lifetime, write through events

  • Pick the prefix by lifetime: app:, user:, no prefix, temp:.
  • Write through state_delta, tools or callbacks, not a copy.
  • Use a business key as session id: retries join one chat.
  • Never store secrets in state: adk web and the GET route show them.

Rules for state, one click each. Click 1: pick the prefix by lifetime: app: for tenant config shared by every user, user: for the customer, no prefix for this chat, temp: for scratch values that die with the turn. Click 2: write state only through events: state_delta on run_async, tool_context.state in a tool, or callback_context.state in a callback; an edit on the object that get_session returns is lost, because it is a copy. Click 3: use a business key such as claim-77 as the session id, as we did on the REST and SQLite slides, so a retry or a channel switch joins the same chat and support staff can find it. Click 4: never put secrets in state, because adk web and GET /apps/.../sessions/... show it to anyone who can call them. Analogy: state is the claim folder: anything in it can be photocopied by whoever opens it. A likely question: "Where do API keys go then?" In environment variables or a secret manager that your tools read.
