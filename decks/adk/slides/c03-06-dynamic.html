Dynamic workflows use plain Python control flow and still checkpoint every child node

code_workflow · bounded verifier loop (verified APIs, sketch binding)

from google.adk import Context
from google.adk.workflow import node

@node(rerun_on_resume=True)      # required for ctx.run_node
async def code_workflow(ctx: Context, node_input: str):
    code = await ctx.run_node(coder_agent, node_input=node_input)
    for _ in range(3):           # bounded loop
        check = await ctx.run_node(lint_and_test, node_input=code)
        if not check.findings:
            return code
        code = await ctx.run_node(fixer_agent,
            node_input={"code": code, "findings": check.findings})
    raise RuntimeError("verification failed after 3 rounds")
  • Loops, recursion and asyncio.gather are ordinary Python. A parent that calls ctx.run_node must set rerun_on_resume=True.
  • Graph: declarative, checked by 10 rules, drawn in adk web. Dynamic: data-dependent loops and recursion.
  • Codelab L4b: @node(parallel_worker=True, rerun_on_resume=True) spawns deeper research only while depth < MAX_DEPTH.
  • Go: workflow.NewDynamicNode, workflow.RunNode. TS: node(fn, {rerunOnResume: true}), ctx.runNode().
  • Each child run gets a deterministic id: the parent id plus a counter "1", "2", … These ids are the checkpoint keys.
  • A custom run_id must contain a non-numeric character. The docs discourage custom ids.
  • Always await ctx.run_node directly. In asyncio.create_task() “errors are silently swallowed”.

“Successful sub-nodes are automatically skipped when resuming the workflow, making complex logic durable and resumable by default.”

A dynamic workflow is a node whose body is Python: here a for loop calls three child nodes through ctx.run_node. Steps 1 to 4 walk the code and fill the checkpoint list on the right: the coder runs, the test finds problems, the fixer runs, and then the second test run crashes. Step 5 is the key idea: on resume, ADK replays the event log, skips children 1 to 3 because their ids already have results, and re-runs only child 4. That works because the child ids are deterministic counters, so never generate ids from random values or timestamps. Step 6 shows the parallel form with asyncio.gather and the pitfall: the official Python sample has no round cap. Analogy: a video game save point. You restart at the last checkpoint, not at level one. Likely question: "Why must the parent set rerun_on_resume=True?" Because the parent body must run again to reach the interrupted child; the completed children return their stored results instantly.
