Resume replays the event log: finished nodes fast-forward and failed nodes run again

Always on, in one invocation

The Workflow scans the session events (ReplayManager.scan_workflow_events) and rebuilds completed nodes, outputs and pending interrupts. Completed nodes fast-forward. The interrupted node runs again.

Limit: checkpoints are written but not read yet. Resume cost grows with history length.

is_resumable=True

  • Adds durability: resume across separate runner calls, with no new message.
  • agent_state / end_of_agent checkpoint events in the log.
  • Function responses go to their original invocation.
  • The ADK Web UI and CLI cannot resume.

Upgrade every reader of a shared session DB before you write 2.0 events. The new node_info and output fields break rigid schemas. Use adk migrate session.

Peers: Temporal activities · Restate ctx.run() · DBOS steps · LangGraph checkpointers by thread_id · Anthropic Managed Agents wake(sessionId).

Step 1: the run completes fetch and analyze, then charge_card sends the payment and the process crashes before the node completes. Step 2: we resume with the same invocation id; ADK reads the log, skips the two finished nodes and runs charge_card again. Step 3 is the trap: execution is at-least-once, and since 2.9.0 a failed node runs again on resume, so the card is charged twice. Step 4: an idempotency key derived from the order makes the payment API refuse the repeat. Step 5: is_resumable adds checkpoint events and resume across separate runner calls. Analogy: a cashier who restarts a shift from the receipt roll; without receipt numbers, the cashier rings up the same sale twice. Likely question: "Can I change the graph while a run is paused?" Answer: no; a paused run can outlive a deploy, and checkpoint versioning is still an open item, so drain or finish paused runs before you change the graph.
