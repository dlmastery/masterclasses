auditor = Agent(name="auditor", model="gemini-3.5-flash",
    output_schema=LineVerdict,
    instruction=("You audit one expense line from the user message "
                 "against policy: meals <= $75/person, no alcohol, "
                 "hotels <= $250/night. Return a verdict."))

@node(rerun_on_resume=True)  # REQUIRED for any ctx.run_node caller
async def orchestrate(ctx: Context, node_input: str):
  lines = [l.strip() for l in node_input.split(";") if l.strip()]
  yield Event(message=f"Auditing {len(lines)} lines in parallel.")
  raw = await asyncio.gather(*[
      ctx.run_node(auditor, node_input=l, use_sub_branch=True)
      for l in lines])

This is the orchestrator-workers pattern on an Acme employee's travel expenses: the number of lines is known only at run time, so the graph cannot be static. Copy expense_audit from labs/adk/c04-expense-audit; it needs the same .env as the copy review. Walk the bands. One auditor agent is defined once; for an agent child, node_input becomes the user message, which is why its instruction says "from the user message" and has no placeholder. The orchestrator must be decorated with @node(rerun_on_resume=True): after an interruption the parent runs again from the top, and finished children are replayed from history. It splits the input, so three lines give three workers. Then asyncio.gather starts one auditor run per line with ctx.run_node, all at once, and use_sub_branch=True keeps the three runs from seeing each other's events. Think of a claims manager who hands each receipt to a different clerk and collects the slips. A likely question: "Why not a static fan-out tuple?" A tuple fixes the number of branches when you build the graph; here the user decides it with every request. Next: the hotel line, which the model flagged wrongly.
