RetryConfig handles transient faults, and a broad except silently disables it

RetryConfig

  • Transient faults. Fires on an exception. A verifier can raise to get a retry.
  • The failed node reruns with its ctx.run_node children. Completed children replay.
  • A failed sub-workflow retries as a whole. parallel_worker retries per item.
  • The model sees nothing.
vs

ReflectAndRetryToolPlugin

  • Semantic faults. The error goes back to the model as reflection guidance.
  • max_retries=3 gives 4 attempts in total.
  • Override extract_error_from_result to catch {"status": "error"}.
  • Register it once on App(plugins=[...]).
samples/workflows/retry/agent.py

from google.adk.workflow import RetryConfig, node
@node(retry_config=RetryConfig(max_attempts=5, initial_delay=1))
def get_weather(ctx: Context) -> str:
  yield Event(message=f"attempt {ctx.attempt_count}")
  if random.random() < 0.7:
    raise HTTPError(url="http://mock-api.example.com",
                    code=500, msg="ISE", hdrs={}, fp=None)
  yield "sunny"
pitfall.py

try:
    data = call_api()
except Exception:          # masks the failure: retries never fire
    return {"status": "error"}
except BaseException: ...  # traps NodeInterruptedError: breaks HITL
Other levers. @node(timeout=30.0) raises NodeTimeoutError, which is retryable. abort_signal stops a run (2.11). FallbackModel fails over to another model (2.9).
Docs Welcome to ADK 2.0 (breaking changes)
Step 1: with the defaults, attempt 1 runs at 0 s and the retries wait 1, 2, 4 and 8 s; max_attempts=5 counts the first try. The bar chart shows why max_delay exists: if you raise max_attempts, the delay doubles until it hits the 60 s cap. Step 2 is the bug that students meet in real code: a broad except Exception returns an error dict, so the node looks successful and RetryConfig never sees a failure. Catching BaseException is worse, because the HITL pause travels as NodeInterruptedError. Step 3 separates two kinds of retry: RetryConfig repeats the same call for a transient fault, and ReflectAndRetryToolPlugin tells the model what went wrong so it can change the arguments. Analogy: RetryConfig redials a busy phone line; reflect-and-retry tells the caller that the number is wrong. Likely question: "Why did your retries never fire?" Answer: an except block swallowed the exception; let it propagate, or re-raise after logging. Also mention cancellation: abort_signal is an asyncio.Event on the Runner, the Workflow and nodes, and /run_sse cancels the run when the client disconnects.
