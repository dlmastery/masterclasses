Day two is a new session with the same user id. Press once: memory generation is asynchronous on the service, so wait_for_memory polls search_memory every five seconds, for up to a minute, until the facts exist; the spinner on the bank shows that wait. Press again: the user asks about the bill; preload_memory, the tool we attached on the previous slide, searches the bank with the new user turn and injects the matches into the system context before the model call, so the answer already uses the Family 4-line plan and the SMS preference. The alternative tool, load_memory, lets the model decide when to search. Press again: memories are keyed by app_name plus user_id, so a new user id looks like a stranger; to honour a forget-me request call delete_memory, new in 2.13, because delete_session leaves memories in place. Think of it as the next call-centre agent reading the customer file before picking up the phone. A likely question: "Can recalled memory authorise an action?" No: treat it as untrusted data and re-check with a tool, because injected text can come back later posing as a user commitment.
