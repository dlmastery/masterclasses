02

Structured output, state and the App

By the end, adk api_server serves the claims App on :8000, and sessions live in a SQLite file.

This chapter builds one service in five steps, in this order: typed intake with output_schema, an App with an audit plugin, the same App over REST and SSE with adk api_server, state scopes that remember the customer, and sessions in a SQLite file that survive a restart. Each later step adds one file to the same lab folder, so point at the road map when you start each step. It is Lab 2 because Lab 1 was the refund desk in chapter 1. Analogy: the App is a shipping container; the agent is the cargo, and plugins, config and state go in the same box. A likely question is "Why not call the model with a JSON schema directly?" Because the App gives you state, plugins and a server, and the schema result lands in state where the next agent can read it. Everything is tested against google-adk 2.13.0 with Python 3.11 or newer. The complete files live in labs/adk/lab2-claims-api; the slides show only the lines that carry each idea, and the next slide sets the folder up.
