The header comes from session state, so something must put the tenant there before the first message. Step 1: your login step creates the session with user:tenant already set. adk api_server --with_ui serves the ADK REST API next to the dev UI, so here we use curl against /apps/claims_agent/users/broker-b/sessions; in production your web app does the same call after it checks the user. Step 2: the response shows the session and its state; open that session in the UI. Step 3: from now on every handbook call carries X-Tenant-ID: broker-b, read by tenant_headers. The model never writes this value: it comes from login, through state, into a header. Think of the front desk that codes your hotel key card before you reach the lift. A likely question: "What happens in adk web without this step?" tenant_headers raises, the handbook toolset fails closed, and the agent answers without handbook tools; the gotcha slides show how to alert on that.
