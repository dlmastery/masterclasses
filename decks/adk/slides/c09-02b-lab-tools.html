ORDERS = {"A-1001": {"amount": 79.00, "order_state": "delivered"},
          "A-2040": {"amount": 820.00, "order_state": "delivered"}}

def lookup_order(order_id: str) -> dict:
    """Returns the amount and delivery state of an order."""
    order = ORDERS.get(order_id.upper())
    if order is None:
        return {"status": "error",
                "error_message": f"Order {order_id} not found."}
    return {"status": "success", "order_id": order_id.upper(), **order}

def issue_refund(order_id: str, amount: float, reason: str) -> dict:
    """Issues a refund. Only for amounts of 500 USD or less."""
    # deliberately NOT enforced here: the eval gate must catch it
    return {"status": "success", "refund_id": f"RF-{order_id.upper()}",
            "amount": amount}

Two Acme orders: one small, one large.

lookup_order gives the amount, or a clear error the model can read.

issue_refund pays any amount. The eval gate must catch $820.

Step two: the three tools of the Acme refund agent, and here are the first two. The ORDERS dict holds two orders, A-1001 at 79 dollars and A-2040 at 820 dollars. lookup_order returns the amount, or a status error with a message the model can read and act on. issue_refund does not check the 500 dollar limit, on purpose: in a real system you would also check it here, but in this lab we want a bug that only the eval gate can catch. Analogy: we leave one door unlocked so we can test the alarm. A likely question: "Why not just add the check to issue_refund?" In production, do both; the eval gate still matters because the next model or prompt change can break behaviour that no tool check covers, such as promising a refund in text.
