YAML configs declare agents and whole graphs, while Python keeps the logic

samples/workflows/loop_config/root_agent.yaml · 2.9.0+

agent_class: Workflow
name: root_agent
edges:
  - - START
    - .agent.process_input
    - generate_headline.yaml
    - evaluate_headline.yaml
    - .agent.route_headline
  - - .agent.route_headline
    - unrelated: generate_headline.yaml
  • A block list is a chain: A→B→C.
  • An inline list [a, b] always means a fan-out.
  • A mapping is a routing map, keyed by Event(route=...).
  • .agent.fn is a function in the package, wrapped as a FunctionNode. x.yaml is an agent file.
  • Nodes are cached by name. The second generate_headline.yaml is the same instance, so the loop is a real cycle.

$ adk create --type=config my_agent   # root_agent.yaml + .env
$ adk web .

Keys include agent_class, model, instruction, static_instruction, tools, sub_agents (config_path), output_schema, output_key, include_contents, *_callbacks.

Docs: “experimental and has some known limitations”. Only Gemini models; A2aAgent and LangGraphAgent are not supported. The Visual Builder in adk web writes Agent Config YAML.

  • ADK parses with yaml.safe_load only.
  • Every *_code and *_callbacks reference is checked against a denylist: the entire stdlib, plus yaml and ruamel.
  • Absolute paths are rejected. The args denylist is off by default.
  • “Treat a config that can name arbitrary modules as trusted input.”
If agent.py or __init__.py exposes root_agent, the Python wins and ADK ignores your YAML edits.
AgentConfig.json is marked deprecated and has no Workflow, so editor warnings on graph YAML are wrong. AgentConfig has no plugins key: use --extra_plugins.

agent.py · Python keeps the logic

class Feedback(BaseModel):
  grade: Literal["tech-related", "unrelated"] = Field(description="...")
  feedback: str = Field(description="...")

def process_input(node_input: str):
  return Event(state={"topic": node_input})
def route_headline(node_input: Feedback):
  return Event(route=node_input.grade)
evaluate_headline.yaml · the per-step verifier

agent_class: LlmAgent
name: evaluate_headline
instruction: |
  Grade whether the headline is related to technology or software engineering.
output_schema:
  name: loop_config.agent.Feedback
output_key: feedback

The trust gate for code references

On entry the YAML types itself, and each line draws its node on the canvas: the chain from START to route_headline. Step 1 adds the last two lines. The routing map sends "unrelated" back to generate_headline.yaml, and because nodes are cached by name, that is the same agent instance, so the edge is a real cycle. Step 2 shows the verifier agent in YAML and the Agent Config basics; note that the docs still call the feature experimental. Step 3 is security: a YAML file can import Python, so ADK blocks the stdlib, yaml and ruamel, but the args denylist is still off. Step 4 lists the two errors that waste the most time. Analogy: YAML is the floor plan, Python is the plumbing. You can move walls without a plumber, but the plan can still name any pipe, so only trusted people may edit it. Likely question: "Can product managers edit graphs in production?" Yes, through CI, but treat the config as code: review it, and pin the trust boundary.
