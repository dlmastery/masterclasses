A graph cycle has no built-in max_iterations. You bound it in the router, or in a while loop inside a dynamic @node.

app.py · verified signatures

from google.adk.apps import App
from google.adk.plugins import (
    ReflectAndRetryToolPlugin, ReflectAndRetryModelPlugin)
from google.adk.agents.run_config import RunConfig

app = App(name="coder", root_agent=root_agent, plugins=[
    ReflectAndRetryToolPlugin(max_retries=3),  # tools
    ReflectAndRetryModelPlugin(max_retries=2), # model
])
# run budget, or: export ADK_MAX_LLM_CALLS=60
run_config = RunConfig(max_llm_calls=60)

Retry is not reflection. RetryConfig runs the node again with backoff, and the model sees nothing. The reflect plugins send the error back to the model, so the next call can change.

Real loop bugs in ADK's own CHANGELOG.
2.2: infinite retry in LoadSkillResourceTool on RESOURCE_NOT_FOUND, a non-retriable error sent back as retriable.
2.6: transfer_to_agent ping-pong between agents (2.9 adds transfer_reason).
2.12: a SetModelResponseTool repair loop. 2.13: JoinNode inside a loop, and interrupt_id reused across iterations.

Hard-code the edge if one answer is yes

  1. 1Is the next step data-determined? A field, a threshold or a status code decides it.
  2. 2Does the step have an irreversible side effect? A payment, an email or a deploy.
  3. 3Does compliance need an auditable path?
  4. 4Does a cheap verifier already decide it? Tests pass or fail.
  5. ?The input is unstructured intent: use an LLM router, a ClassifierNode or output_schema with a Literal route.

Allow an autonomous loop only inside one node. The graph bounds its blast radius.

If you can clearly map the workflow, use determinism.
