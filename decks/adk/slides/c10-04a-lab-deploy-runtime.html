export PROJECT=my-proj REGION=us-central1
# create: managed sessions + Memory Bank, traces without content
adk deploy agent_engine --project=$PROJECT --region=$REGION \
  --display_name="acme-hr" --otel_to_cloud \
  --service_account=acme-hr@$PROJECT.iam.gserviceaccount.com \
  hr_agent
export AGENT_ENGINE_ID=1234567890      # printed by the first deploy
# update the same instance in place
adk deploy agent_engine --project=$PROJECT --region=$REGION \
  --agent_engine_id=$AGENT_ENGINE_ID hr_agent

The last step of the Acme HR lab ships the same hr_agent folder; this slide is the managed target, Agent Runtime. Press once: the first deploy creates an instance; --otel_to_cloud sends traces to Cloud Trace and also turns message capture off, and the service account gives the agent its own identity. The output strings come from cli_deploy.py, but the run itself is illustrative. Press again: copy the instance id from the output; it is the address of your agent. Press again: every later deploy passes --agent_engine_id, and the CLI updates that instance in place; without it, each deploy creates a new instance and your client keeps talking to the old one. Analogy: the instance id is a house number; without it the mover builds a new house each time. Likely question: "When do I pick Agent Runtime?" When you want managed sessions, Memory Bank and publishing to Gemini Enterprise. The full script, with all three targets, is labs/adk/c10-acme-hr/ship.sh.
