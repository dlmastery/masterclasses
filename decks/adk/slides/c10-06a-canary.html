labs/adk/c10-acme-hr/canary.sh · excerpt
# 1. new revision at 0% traffic; the tag gets its own URL
$ gcloud run deploy acme-hr --image IMAGE_URL --no-traffic --tag cand
# 2. eval the live candidate before any user reaches it
$ agents-cli eval run --url https://cand---acme-hr-xyz.a.run.app
# 3. shift traffic; hold while the guard metrics stay steady
$ gcloud run services update-traffic acme-hr --to-revisions REV_NEW=5
$ gcloud run services update-traffic acme-hr --to-revisions REV_NEW=25
# 4. rollback: tokens per invocation > 1.5x baseline (a loop)
$ gcloud run services update-traffic acme-hr --to-revisions REV_PREV=100

--no-traffic --tag: the revision is live, but no user reaches it.

The evals hit the real deployed revision on its own URL.

5% of the traffic. All four gauges hold.

At 25%, tokens per invocation pass 1.5x. A loop burns tokens, not errors.

One command sends 100% back to the old revision.

The before line is the default: adk deploy cloud_run creates a new revision and it takes all the traffic at once, with no eval on the live URL. Press once: deploy with --no-traffic and a tag; the candidate is live and has its own URL, but no user reaches it. Press again: point agents-cli eval run --url at that URL, so the evals hit the real deployed revision. Press again: shift 5% and hold while error rate, p99 latency, tokens per invocation and the judge score stay steady; write these four guard metrics down before the launch. Press again: at 25% the tokens gauge passes 1.5 times the baseline; that is the agent-specific signal, because a loop does not raise errors, it burns tokens. Press again: the rollback is one update-traffic command back to the previous revision. Analogy: a new chef cooks for one table before the whole room. Likely question: "What if the evals pass but users still suffer?" That is why the gauges watch live traffic at each step; the eval run is the gate, the gauges are the guard. Gauge values are illustrative.
