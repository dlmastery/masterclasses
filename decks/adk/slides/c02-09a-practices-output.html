Typed outputs: four rules to check in every code review

  • Put reasoning first in output_schema: +15-24 pts.
  • Check meaning in code: valid JSON is not correct JSON.
  • Read optional keys with .get(): None fields are dropped.
  • Never set response_schema in generate_content_config.

The chapter as rules you can test in code review, in four clicks; this slide covers typed outputs. Click 1: keep the reasoning field first, because arXiv 2608.08254 measured +15 to 24 points for it, and keep the Field descriptions consistent with the instruction. Click 2: check meaning in code after the extraction, because constrained decoding gives valid JSON that can still carry a wrong severity (arXiv 2609.23742); check_claim in the lab is the pattern. Click 3: read optional keys with .get, because output_key drops null fields such as incident_date. Click 4: never put response_schema into generate_content_config: ADK raises and tells you to use output_schema. Analogy: these are the four boxes a reviewer ticks on every schema pull request. A likely question: "Should every field have a description?" Yes, but review it like a prompt, because the model reads it as one.
