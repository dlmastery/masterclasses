The same folder ships to Cloud Run or GKE and stays private

labs/adk/c10-acme-hr/ship.sh · excerpt
# B) Cloud Run: private, one warm instance
adk deploy cloud_run --project=$PROJECT --region=$REGION \
  --service_name=acme-hr \
  --session_service_uri="agentengine://$AGENT_ENGINE_ID" \
  hr_agent -- --no-allow-unauthenticated --min-instances=1

# C) GKE: ClusterIP by default, no public IP
adk deploy gke --project=$PROJECT --region=$REGION \
  --cluster_name=agents-prod --service_type=ClusterIP hr_agent

# also: --extra_packages (new in 2.13), --validate-agent-import
# --trace_to_cloud is deprecated

Flags after -- go to gcloud run deploy. Keep the service private.

Without --session_service_uri, sessions live in instance memory.

ClusterIP is the default. LoadBalancer gives a public IP.

Same package, three trade-offs. Pick by what you must run yourself.

The same folder goes to the two self-managed targets. Press once: adk deploy cloud_run passes everything after the double dash to gcloud run deploy, so we keep the service private with --no-allow-unauthenticated and keep one warm instance. Press again: --session_service_uri points sessions at the Agent Runtime instance from the last slide; without it they live in the container's memory and vanish when Cloud Run recycles the instance, which is the first gotcha later in this chapter. Press again: GKE gives a ClusterIP service by default, so nothing is public until you ask for a LoadBalancer. 2.13 also added --extra_packages for local packages, and --trace_to_cloud is deprecated in favour of --otel_to_cloud. Press again: the lists show the trade-off: Agent Runtime for managed sessions, Memory Bank and Gemini Enterprise; Cloud Run for the ADK FastAPI routes, revisions and your own session database; GKE for GPUs and self-hosted models. Analogy: one shipping container, three ports: a managed port, a self-service dock and your own warehouse. Likely question: "Can I mix them?" Yes, as here: Cloud Run serves, Agent Runtime stores the sessions.
