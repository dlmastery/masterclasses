def issue_refund(ctx: Context, order_id: str, final_amount: float):
  ok = ctx.state.get("approved")      # manager_gate writes it with the yes
  if ok != {"order_id": order_id, "amount": final_amount}:
    raise PermissionError("refund differs from the approved payload")

The third paper, Approve What, Exactly?, audited agent runtimes and found that the arguments changed after approval in 4 of 8 runtimes where binding could be measured; it also found no runtime that produces a third-party-verifiable approval record. Effect binding means the tool checks the exact approved payload again when it runs. Walk the animation: the manager approves A-2040 for 820 dollars; by the time the tool runs, the amount has become 8,200; the payloads differ, so the tool raises PermissionError and nothing is paid. ADK does not do this for you, so write the approved order and amount to state in manager_gate together with the yes, and compare inside issue_refund, as the code shows. The same paper lists threshold splitting: two 490-dollar refunds each stay under the 500-dollar gate, so also keep a running refunded total in state and pause when the session sum passes the limit. Analogy: the bank compares the amount on the cheque with the amount in words before it pays. A likely question: "Is this the same as the idempotency key?" No: the key stops the same payment twice, binding stops a different payment from riding on an old yes. Next: how Temporal makes each call durable.
