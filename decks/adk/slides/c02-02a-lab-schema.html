class ClaimIntake(BaseModel):
    reasoning: str = Field(
        description="One sentence: the facts behind the labels.")
    claim_type: Literal["auto_collision", "auto_glass", "home_water",
                        "home_theft", "other"]
    severity: Literal["low", "medium", "high"] = Field(
        description="low < $2k, medium $2k-$10k, high = injury or > $10k")
    policy_number: Optional[str] = Field(
        None, description="POL-######, or null")
    incident_date: Optional[str] = Field(
        None, description="YYYY-MM-DD, or null if unknown")
    estimated_loss_usd: Optional[float] = None
    injuries_reported: bool

The schema is the claim form. The model fills it from the email.

reasoning comes first: the model writes why before it picks a label.

Literal closes each label set. The description gives the money bands.

The email has no year, so incident_date stays null. Never guess.

Step 1 of the Acme claims API: turn a first-notice-of-loss email into a typed record. The full file is labs/adk/lab2-claims-api/claims/claim_intake.py; this slide shows only the schema. Click 1: the reasoning field comes first, so the model writes one sentence of facts before it chooses a label; the paper slide later shows that this order is worth 15 to 24 points. Click 2: Literal types close the label sets, and the Field description gives the money bands, so $6,400 is medium. Click 3: the email says "Oct 19" with no year, and the instruction says never guess, so incident_date stays null. Analogy: the schema is the paper claim form, and the small print under each box is part of the instructions. A likely question: "Is the description just documentation?" No, the model reads it as a second prompt, so keep it consistent with the instruction.
