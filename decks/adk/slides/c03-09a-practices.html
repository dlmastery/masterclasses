Graph rules for routing and data, each with its reason

Routing route_ticket

  • The LLM labels into a Literal set. A function routes, so rules get tests.
  • Always add DEFAULT_ROUTE. An unmatched route only logs.

Data edges and state

  • Same Pydantic class on both edge ends. The build checks it.
  • Pass data on edges. Use state for values many nodes read.
This slide and the next turn the chapter into rules you can check in code review. Step 1, routing: the model only classifies into a closed Literal set, and a plain function decides the route, so a rule like "p1 always pages on-call" gets a unit test; watch the other ticket take the DEFAULT wire, because an unmatched route only logs. In the YAML version, give every label its own key. Step 2, data: the build checks producer and consumer schemas on each edge where both ends declare a type, so use the same Pydantic class. Step 3: pass data on edges, and keep state for values many nodes or prompts read, such as {ticket} for the billing prompt. Analogy: the LLM is the triage nurse who writes the label, and the function is the hospital rule book that sends the patient to a ward. Likely question: "Why not let the LLM return the route directly?" You can, but then a casing slip like "Billing" ends the branch with only a log line, and you cannot unit-test the rule.
