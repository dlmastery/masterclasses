01

Why RAG

Models need knowledge they were never trained on.

  • Frozen. Knowledge stops at the training cutoff. An update needs a retrain.
  • No source. The model cannot cite, so you cannot audit a hallucination.
  • No private data. Tickets, contracts and inventory were never in training.
  • No access control. You cannot filter weights per user.

The RAG answer. Keep knowledge in an external index that you can swap and filter by permission. At query time, retrieve the top-k passages. Condition the answer on them.

Update = re-index, not retrain.

Interview: when RAG, when fine-tuning, and where to look first

When do you choose RAG over fine-tuning?
Use RAG for fresh, private or permissioned facts and for citations. An update is a re-index, not a retrain. Use fine-tuning for behaviour, format and style. Combine them when you need both.
Explain RAG-Sequence vs RAG-Token.
RAG-Sequence uses one retrieved document for the whole output. RAG-Token can use a different document for each token. Both marginalize over the top-k documents. On NQ, RAG-Sequence scored 44.5 EM and RAG-Token 44.1.
Your RAG bot gives wrong answers. What do you check first?
Check recall@k on a golden set. If the gold chunk is not in the top-k, the generator cannot fix the answer. Separate retrieval failures from generation failures, then fix the stage that fails.

import anthropic
client = anthropic.Anthropic()
def situate(doc: str, chunk: str) -> str:
    msg = client.messages.create(
        model="claude-haiku-4-5",  # illustrative; blog used Claude 3 Haiku
        max_tokens=150,
        system=[{"type": "text", "text": f"<document>\n{doc}\n</document>",
                 "cache_control": {"type": "ephemeral"}}],  # cached once
        messages=[{"role": "user", "content":
            f"Here is the chunk we want to situate within the whole document\n"
            f"<chunk>\n{chunk}\n</chunk>\n"
            "Please give a short succinct context to situate this chunk within "
            "the overall document for the purposes of improving search "
            "retrieval of the chunk. Answer only with the succinct context "
            "and nothing else."}])
    return msg.content[0].text + "\n\n" + chunk  # index for dense AND BM25
Start with the problem chunk: alone, it does not say which company or which quarter, so neither the embedder nor BM25 can match a query that names them. Step 1, late chunking: run the long-context embedder over the whole document first, then mean-pool each chunk's token span; the token "Its" now carries attention from "Berlin", so the cosine rises from 0.708 to 0.825. Step 2, Contextual Retrieval: an LLM writes a short context note for each chunk, and you index note plus chunk in both the dense and the BM25 index. Step 3: the gains stack, from 5.7% to 1.9% failures with reranking. Steps 4 and 5: the cache_control block is the reason this is cheap, about $1.02 per million document tokens, because the document is written to the cache once and read for every chunk. Analogy: late chunking reads the whole book before it summarizes a page; Contextual Retrieval writes a header on each index card. Likely question: "Which fix do I choose?" Answer: late chunking needs an open long-context embedder with token outputs; Contextual Retrieval works with any embedder and also fixes BM25, but costs one LLM call per chunk.

How do you choose a chunk size?
Run an eval, not a guess. Measure token-level recall and IoU on a golden set. Start with recursive ~200 tokens, no overlap (Chroma: recall 88.1, IoU 6.9). Move to structure-aware chunks when the parser is good.
Why is Contextual Retrieval cheap enough to run on every chunk?
Prompt caching. The document is written to the cache once. Each chunk call reads it from the cache and adds only the chunk. Cost: about $1.02 per million document tokens, one time. Failures fall 5.7% → 2.9% before reranking.
Financial PDFs full of tables give bad answers. Design the fix.
Use a layout parser that isolates tables (Docling, Unstructured). Send charts and scans to a VLM tier. Or retrieve page images with ColPali (chapter 8). Keep each table as its own chunk, with its caption and section as context.
Parent-child retrieval: what do you index and what do you send?
Index small children for a precise match. Send the parent or a sentence window for context (LlamaIndex AutoMergingRetriever, LangChain ParentDocumentRetriever). Cost: more storage and more bookkeeping.
Ask the room each question before you reveal the answer. Q1 tests if the candidate measures; the strong answer names token-level recall and IoU and a golden set, not a magic number. Q2 tests cost reasoning: the document is the large part of each prompt, and caching turns it into a cheap read. Q3 is a design question; a strong answer separates parsing (tables, charts, scans) from chunking and names a fallback (page-image retrieval). Q4 checks the small-to-big idea: small units match well, large units answer well. Likely follow-up: "How do you keep parent and child in sync when a document changes?" Answer: re-chunk the whole document, delete its old children by document id, then upsert.

Embeddings and vector indexes

An encoder maps meaning to a vector. Similar meanings land near each other. An index finds the nearest vectors fast.

Similarity is geometry

Use cosine, dot product on normalized vectors, or L2. In 2026 one space can hold text, images, audio, video and PDFs.

Exact search does not scale

Exact k-NN costs O(N × d) per query. ANN gives up a little recall for orders of magnitude more speed.

Three questions for this chapter

Which model?How many dimensions?Which index?
This chapter is about the geometry under every dense retriever. First, the points are scattered; press next and they move into topic clusters, because the encoder puts similar meanings near each other. Then the grid shows how an index cuts the space into cells, so a query only looks in a few cells and not at every vector. Analogy: a library puts books on shelves by subject, so you walk to one shelf and do not read every spine. A student often asks: "Why not just compute exact distances?" Answer: exact k-NN is O(N × d) per query, which is too slow at tens of millions of vectors, and ANN keeps most of the recall at a small fraction of the cost.

HNSW descends from long links to short links, while IVF-PQ, DiskANN and ScaNN trade memory for recall

Every index is a point on the recall / latency / memory / build-time surface. HNSW (Malkov & Yashunin, IEEE TPAMI 2018) is the default in pgvector, Qdrant, Weaviate, Milvus, Elasticsearch/OpenSearch and FAISS.

PQ

Split a vector into M sub-vectors; code each with 2nbits centroids. 768-d float32: 3,072 B → PQ96x8: 96 B.

DiskANN / Vamana

PQ codes in RAM; graph and full vectors on SSD. SIFT1B on a 64 GB box: >5,000 QPS, <3 ms, 95%+ 1-recall@1.

ScaNN + SOAR

Anisotropic quantization. SOAR spills each vector to a second, near-orthogonal cluster. Runs Vertex AI Vector Search and AlloyDB.

HNSW works like a road network: the top layer is the highway with a few long links, and layer 0 is the street level with every vector. The search enters at the top, moves greedily to the neighbour nearest the query until it cannot improve, drops one layer, and repeats; on layer 0 it runs a beam search of width efSearch and returns the top k. Step 4 shows the other family: IVF cuts the space into nlist k-means cells and searches only the nprobe nearest cells, and PQ compresses each vector to 96 bytes. DiskANN keeps only PQ codes in RAM, which is how one workstation serves a billion vectors. Likely question: "HNSW or IVF-PQ?" Answer: HNSW for the best recall and latency when the vectors fit in RAM; IVF-PQ or DiskANN when memory is the limit, and always measure recall@k against exact k-NN.

Interview: embeddings and ANN index design

Design an index for 1B vectors on a tight memory budget.
Use DiskANN (PQ codes in RAM, graph and full vectors on SSD) or IVF-PQ. Cut to 768 dims with MRL, then use int8 or binary. Re-score the top candidates with the full vectors. Measure recall@k against exact k-NN on a sample. DiskANN served SIFT1B from one 64 GB workstation at >5,000 QPS.
What do HNSW M, efConstruction and efSearch change?
M is the graph degree: more memory (HNSWFlat costs 4·d + M·2·4 B) and higher recall. efConstruction sets build quality: higher values make the build slower. efSearch is the query beam width: higher values give more recall and more latency. You set efSearch at query time.
Can you query a gemini-embedding-001 index with gemini-embedding-2 vectors?
No. The two models make different vector spaces, so the distances have no meaning. Do a blue/green re-embed: build a second index with the new model, compare both on the golden set, then move the traffic.
Numbers to know.
10M × 3072 × 4 B ≈ 123 GB; 768-bit binary ≈ 0.96 GB. PQ96x8 = 96 B per vector (3,072 B for 768-d float32). MRL: up to 14× smaller at the same accuracy. Exact k-NN: O(N × d) per query.

This chapter follows one query through the retrieval funnel. The first band is recall: cheap retrievers (BM25, dense and learned sparse) search millions of documents, metadata filters run inside this stage, and RRF fuses the lists into about 100 to 150 candidates. BM25 and dense retrieval fail on different queries, so run both

BM25 wins. Dense vectors miss exact tokens: error codes, SKUs, names and rare acronyms.

Dense wins. "car" ≈ "automobile". BM25 misses synonyms and paraphrase.

Both hit. The failures barely overlap, so the union raises recall. BEIR (NeurIPS 2021): "BM25 is a robust baseline."

SPLADE (Formal et al., SIGIR 2021): a BERT MLM head projects each token onto the whole 30,522-term vocabulary. Log-saturation and a FLOPS regulariser keep a few hundred weights. Expansion adds "vehicle" and "automobile" to a "car" passage.

Reciprocal Rank Fusion merges ranked lists by rank only, with k = 60

RRFscore(d) = Σ 1 / (k + rank_r(d)) over all rankers r. Only ranks count, so BM25 (unbounded) and cosine (−1..1) need no calibration.

rrf.py

def rrf(rankings: list[list[str]], k: int = 60) -> list[tuple[str, float]]:
    scores: dict[str, float] = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)

Agentic RAG patterns

Classic RAG is one fixed pass. The pipeline retrieves once, also when the question does not need it. Nothing checks the retrieved evidence before the model uses it.

Agentic RAG is a policy. An LLM decides whether to retrieve, where (vector DB, SQL, web, API, MCP server), what to query (rewrite, decompose), if the evidence is good enough (grade, reflect) and when to stop.

Agentic RAG works by “embedding autonomous AI agents into the RAG pipeline.”

Classic RAG retrieves once before generation. Dynamic RAG retrieves while the model writes. IRCoT uses each new chain-of-thought sentence as the next query, which gave up to 21 points better retrieval and 15 points better QA on four multi-hop sets. FLARE drafts the next sentence and retrieves only when a token has low confidence; the red token is the trigger. DRAGIN makes both decisions from the model's internals: RIND fires on an uncertain, important, non-stopword token, and QFS builds the query from the context tokens that this token attends to, not only from the last sentence. That is why DRAGIN needs logits and attention weights, which hosted APIs do not return. This chapter is about questions that plain top-k similarity cannot answer. First, global questions: the answer is a summary of the whole corpus, so every chunk is a little relevant and no five chunks are enough. Second, multi-hop questions: each hop is in a different chunk, and the middle chunks do not look like the question. Analogy: top-k is a search light; global questions need a map of the whole room, multi-hop questions need a rope from one object to the next. Structured RAG builds that map or that rope at index time: an entity graph, communities, a summary tree or a SQL schema. Then end with the caution: GraphRAG-Bench shows that graphs often lose to vanilla RAG, so measure before you adopt. Likely question: "Can I not just raise k?" Larger k adds cost and distractors and still misses chunks that are not similar to the query.

  1. Offline: OpenIE triples → phrase nodes, synonym edges (similarity > 0.8), passage nodes linked by "contains".

When is GraphRAG worth its indexing cost?
When users ask corpus-wide sensemaking questions over a stable corpus: indexing costs about 1000x vector RAG, and global search wins 72–83% on comprehensiveness. For specific facts, use hybrid search + a reranker. For data that changes daily, use LazyGraphRAG (index = vector cost) or LightRAG (graph union updates).
Explain how HippoRAG 2 uses Personalized PageRank.
Offline, OpenIE triples make a KG of phrase and passage nodes, with synonym edges. Online, the query gets top-5 triples; an LLM filter keeps the good ones. Kept phrases and all passages (× 0.05) are the seeds. PPR spreads activation over the graph, and passages rank by their score. Result: associative multi-hop recall, 59.8 avg F1 vs 57.0 for dense.
Why do GraphRAG papers and HippoRAG disagree on LightRAG?
They use different metrics. GraphRAG-family papers use LLM-judge win rates on comprehensiveness and diversity: LightRAG is about 50% vs GraphRAG. HippoRAG 2 uses F1 on factual QA: LightRAG gets 6.6. Pick the metric that matches your task, and always include a strong dense baseline.
Text-to-SQL on a 1,000-column warehouse: your design?
Retrieve the schema, not documents: embed DDL + column docs and link only the relevant tables. Retrieve similar (question, SQL) pairs as few-shot examples. Execute, and send errors back for self-correction. Use a read-only role with row-level security. Why: on Spider 2.0, an o1-preview agent solves only 21.3%.

Cursor: re-index only what changed

  1. A Merkle tree of file hashes finds the changed files. 50,000 files give about 3.2 MB of hashes.
  2. One changed file changes every hash up to the root. Compare roots, then walk down.
  3. Split changed files into syntactic chunks. Embed them asynchronously. Cache embeddings by chunk content.
  4. A simhash seeds a new user's index from a teammate's (92% average similarity). Content proofs return only files the client has.

Evaluation and security

A RAG system is as good as its measured retrieval and as safe as its least trusted document.

  • Fails in three places: retrieval, grounding, usefulness. Score each one separately.
  • Is attacked in three places: the documents, the index, the tools.

“LLM-Integrated Applications blur the line between data and instructions.”

Retrieval metrics need relevance labels

  • Recall@k: relevant chunks in the top-k. Main RAG metric.
  • Precision@k: relevant chunks in the top-k, divided by k.
  • MRR: mean of 1/rank of the first relevant hit.
  • nDCG@10: graded and rank-discounted. MTEB/BEIR headline.
  • Hit rate / Match@k: any relevant chunk in the top-k.

Faithfulness = supported claims / all claims. Here 3 of 4 claims have evidence: 0.75.

Context Precision@K is rank-aware: swap a relevant and an irrelevant chunk and ContextUtilization drops from ≈1.0 to ≈0.5. No LLM: IDBasedContextPrecision (2/4 = 0.5). Cheap judge: FaithfulnesswithHHEM (HHEM-2.1-Open, CPU).

Filter by the end user's permissions inside the query, before ranking, and redact PII at ingestion

Embeddings drop the source document's ACL. Top-k returns what is similar, not what this user may see. The retriever becomes a confused deputy.

Docs OWASP LLM08: “permission-aware vector stores”
  1. Index time: copy the source ACL onto every chunk as metadata. Use group ids. Deny overrides grant.
  2. Query time: pass the end user's identity, not a service account. Filter inside the vector and BM25 queries, before ranking and fusion.
  3. Re-sync chunk ACLs when permissions change.
  4. Partition semantic caches and memories the same way.

Five levers for latency and cost

  • Retrieve less: rerank the top-50 to the top-5.
  • Prompt cache: static prefix first; reads cost 0.1x (Anthropic).
  • Semantic cache: ~0.05 s hit vs ~1.8 s LLM call.
  • Route and cascade: small model first, escalate on low confidence.
  • Batch APIs for indexing and offline eval.

Freshness: stop zombie chunks

index() + RecordManager hashes each chunk and skips unchanged ones. Cleanup: incremental · full · scoped_full. Never point it at a store that another process filled. New embedding model = full blue/green re-embed.

semantic_cache.py · RedisVL

from redisvl.extensions.cache.llm import SemanticCache
from redisvl.utils.vectorize import HFTextVectorizer
from redisvl.query.filter import Tag

cache = SemanticCache(name="llmcache",
    redis_url="redis://localhost:6379",
    distance_threshold=0.1,     # Redis COSINE 0-2, lower = stricter
    vectorizer=HFTextVectorizer("redis/langcache-embed-v1"),
    filterable_fields=[{"name": "user_id", "type": "tag"}])
def answer(q: str, uid: str) -> str:
    hit = cache.check(prompt=q, filter_expression=Tag("user_id") == uid)
    if hit:                               # ~0.05 s instead of ~1.8 s
        return hit[0]["response"]
    out = rag_answer(q)                   # retrieve, rerank, generate
    cache.store(prompt=q, response=out, filters={"user_id": uid})
    cache.set_ttl(3600)                   # freshness bound
    return out

file_search.py · Gemini API, Interactions API

import time
from google import genai                       # google-genai 2.33.0
client = genai.Client()
store = client.file_search_stores.create(config={
    "display_name": "my-store",
    "embedding_model": "models/gemini-embedding-2"})   # images need -2

op = client.file_search_stores.upload_to_file_search_store(
    file="sample.txt", file_search_store_name=store.name,
    config={"display_name": "display-file-name"})
while not op.done:                     # service parses, chunks, embeds
    time.sleep(5); op = client.operations.get(op)

interaction = client.interactions.create(
    model="gemini-3.8-flash", input="Can you tell me about ...",
    tools=[{"type": "file_search", "file_search_store_names": [store.name]}])
for step in interaction.steps:
    if step.type == "model_output":
        for b in step.content:
            if b.type == "text":
                print(b.text, [a.file_name for a in (b.annotations or [])
                               if a.type == "file_citation"])

  • 01Measure first. Build a 100–500 item golden set. Gate every merge in CI (RAGAS, LangSmith experiments, adk eval).
  • 02Parse well. Use a layout parser for the bulk and a VLM tier for hard pages.
  • 03Chunk simply. Start with ~200-token recursive or structure-aware chunks. Add Contextual Retrieval.
  • 04Retrieve hybrid. Run BM25 + dense search and fuse the lists with RRF (k = 60).
  • 05Rerank. Cut ~150 candidates to ~20. Send few chunks. Put the best chunks first and last.
  • 06Skip the index when you can. Under ~200k static tokens, cache the whole corpus in the prompt.
  • 07Workflows before agents. Use a router, Adaptive-RAG or a corrective loop with max_iterations. Budget multi-agent search at ~15x tokens.
  • 08Load context just in time. Keep knowledge, instructions (skills) and tool context behind identifiers. Load them when a step needs them.
  • 09Trust nothing retrieved. Treat retrieved text and MCP tool output as data. Filter ACLs inside the query. Remove PII at ingest.
  • 10Operate it. Trace on OpenTelemetry. Set freshness SLOs. Re-embed blue/green.

Design RAG for 50M documents, p95 under 1 second, with per-user ACLs.
Run hybrid BM25 + ANN (HNSW or DiskANN; MRL 768 dims + int8). Apply the ACL pre-filter inside both queries with the end user's identity. Fuse with RRF. Rerank the top-100 with a small, fast reranker. Cache the static prompt prefix. Stream the output. Give each span a latency budget and trace it.
Build your own pipeline, or use File Search / RAG Engine?
Use managed for speed, citations and low ops. Build DIY when you need custom chunking, hybrid weights, rerankers, ACL logic or a non-Google stack. Measure both on the same golden set before you decide.
How do you migrate to a new embedding model with zero downtime?
Blue/green. Build the new index in parallel. Compare both indexes on the golden set. Switch reads when the new index wins. Keep the old index for rollback. Never mix vectors from two models in one index.
What are the risks of a semantic cache?
Cross-user leakage: partition by user or tenant. False hits: tune the threshold; at 0.5 a "Nice" question hit the "Paris" answer (RedisVL docs). Stale answers: set a TTL and invalidate entries by doc_id when a document changes.
