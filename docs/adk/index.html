Start with the one-sentence answer to the interview question "What is ADK 2.0?": it is a graph-based Workflow Runtime, and agents, tools and functions are all nodes, because BaseAgent now subclasses BaseNode. Start with the two definitions from Anthropic: in a workflow the code fixes the path; in an agent the model picks the path. Step 1 is the compounding-error argument: at 95% per step, a 20-step run succeeds only 0.95 to the power 20, about 36% of the time. Interview drill: defend when an agent is worth its cost

Workflow or agent for a refund process?
A workflow spine. The path is data-determined, it has irreversible side effects and it needs an audit trail. Use an LLM node only for the unstructured complaint. Google: “If you can clearly map the workflow, use determinism.” Its illustrative refund run went from 5,152 to 2,265 tokens.
A 20-step agent is 95% reliable per step. What is the end-to-end success, and what do you change?
About 36% (0.9520). Put cheap verifiers after the risky steps, hard-code the data-determined edges and remove steps. Each removed or verified step raises the product.
Why did the single growing ReAct prompt fail on long tasks?
Context rot: Chroma (2025-07-14) found that all 18 tested models degrade as input grows. Attention is an n² budget, and tool output piles up in the window. Modern harnesses move state into files, memory and subagents, and each call gets a compiled view.
What is harness engineering, and who named it?
Mitchell Hashimoto, 2026-02-05: each agent mistake triggers an engineered fix in the environment, so the mistake does not repeat. Böckeler splits the controls into guides (feedforward) and sensors (feedback), each computational or inferential. In ADK, each failure becomes an eval case and a CI gate.

from google.adk import Agent, Event, Workflow
from pydantic import BaseModel

city_generator_agent = Agent(name="city_generator_agent",
    model="gemini-flash-latest",
    instruction="Return the name of a random city. "
                "Return only the name, nothing else.")

class CityTime(BaseModel):
    time_info: str  # time information
    city: str       # city name
def lookup_time_function(node_input: str):
    return CityTime(time_info="10:10 AM", city=node_input)

city_report_agent = Agent(name="city_report_agent",
    model="gemini-flash-latest", input_schema=CityTime,
    instruction="It is {CityTime.time_info} in {CityTime.city} right now.")
def completed_message_function(node_input: str):
    return Event(message=f"{node_input}\n WORKFLOW COMPLETED.")

root_agent = Workflow(name="root_agent", edges=[
    ("START", city_generator_agent, lookup_time_function,
     city_report_agent, completed_message_function)])

Every node runs the same three phases

  1. Validate node_input against input_schema. Dicts are coerced into the model.
  2. Run the user logic: a function, an Agent, a BaseTool or a nested Workflow.
  3. Normalize each yield: None is dropped, an Event passes, a RequestInput becomes an interrupt, any other value becomes Event(output=value).

Four Event fields carry the run

outputData for the next node. Only one per node run.
messageContent that the user sees.
stateA delta that the session saves.
routeThe branch to take (next slide).

The hand-off is the return value. You do not need session state for it.

Workflow(...) checks 10 rules at construction

  • Unique node names. Reuse one instance to loop back.
  • START is present, with no incoming edges and no routes.
  • Every node is reachable. No unconditional cycles.
  • output_schema equals the successor's input_schema (often from type hints).
  • An LlmAgent(mode='chat') only directly after START.

The check is structural, not behavioural.

from google.adk import START raises ImportError. Import START from google.adk.workflow. The string "START" works in chain tuples, but not in Edge(...).
Two terminal nodes that both output fail the run with WorkflowConfigurationError. The engine cannot choose the workflow output. Put a JoinNode before the end.
A node is any NodeLike: a function (auto-wrapped in FunctionNode), an Agent (usually mode='single_turn'), a tool, a Workflow, or the START sentinel __START__, which never executes.

A router emits a route label, and only the matching edge fires

A node yields Event(route=v). The value v is a str, int or bool. A routing dict maps v to the next node.

The router emits "BUG". Only the edge with the key "BUG" fires. The other branches do not run.

A list route fans out: Event(route=["BUG", "LOGISTICS"]) starts every matching branch.

No match and no default: the branch ends silently. ADK writes only a log warning. Other branches continue.

DEFAULT_ROUTE (the literal "__DEFAULT__") fires when a route is emitted and no key matches. Since 2.10 it can fan out.

  • (a) Function router: rules in code, e.g. codelab L2b "HOT" if temp >= 70 else …
  • (b) LLM + schema: output_schema with Literal[...], a function routes on the field.
  • (c) ClassifierNode (2.13, labs): calibrated score, threshold gate.
Pitfall: an LLM router with free-text output and no DEFAULT_ROUTE can invent a label, for example "REFUND". The request then disappears with no error. Constrain the label with a Literal schema and add a default edge.

Fan-out runs branches in parallel, and a JoinNode waits for every one of them

  • A tuple of nodes inside a chain is a parallel fan-out.
  • JoinNode sets _requires_all_predecessors → True. It emits one dict keyed by predecessor node name.
  • Compact form: (START, (word_count, shout), join, report). Then report reads node_input['shout'] and node_input['word_count'].
  • Without a join, the successor runs once per predecessor (sample multi_triggers).
  • Map over a runtime list: @node(parallel_worker=True) or Agent(..., parallel_worker=True). One run per item. The next node gets a list.
  • max_parallel_workers caps the per-item concurrency. Here it is 2: two run, two wait.
  • Codelab level L4a sizes the fan-out at runtime. Level L2a uses a fixed tuple and a JoinNode.

Workflow(max_concurrency=2) caps graph-scheduled nodes only. ctx.run_node children are exempt: “throttling them would cause deadlock”.

0–1model calls per level, codelab L0–L2b
5–30model calls per run, L4b fan-out

Fixes: 2.8 counts START as a satisfied join predecessor. 2.13 makes a JoinNode in a loop wait for each iteration's predecessors.

Step 1 is the barrier. The three functions start together and finish at different times: 1.0, 1.8 and 2.6 seconds in the animation. Each output waits at the JoinNode gate, and the gate opens only when the last one arrives. Step 2: the gate emits one dict keyed by predecessor node name, and aggregate reads the three keys. Step 3 is the other parallel tool, parallel_worker: the list size is known only at run time, and a cap of two workers makes two items wait. Step 4 covers the concurrency caps and the cost: the codelab's simple levels make 0 to 1 model calls, the recursive fan-out makes 5 to 30. Analogy: a restaurant pass. A loop is a conditional back-edge, and you must bound it yourself

Sample workflows/loop (generator-critic): (route_headline, {"unrelated": generate_headline}) is a conditional back-edge.

evaluate_headline has output_schema=Feedback with grade: Literal["tech-related", "unrelated"]. The router returns Event(route=node_input.grade).

A self-loop also works: (guess_number, {"guessed_wrong": guess_number}).

“A graph cycle is not bounded automatically.”

Construction rejects only unconditional cycles. A conditional cycle has no max_iterations. Each pass re-activates the node “with a fresh lifecycle”, and node_info.path shows the pass, e.g. request_input@1/request_human_review@2.

Lever 1: a round counter in the router

The router reads rounds from ctx.state, adds one, and writes it back through Event(state=...). The counter survives a pause and a resume, because the session stores it.

Lever 2: escalate on the last round

On round 3 the router emits give_up. The edge goes to human_review, which yields a RequestInput.

Backstop: RunConfig.max_llm_calls (default 500) raises LlmCallsLimitExceededError. Since 2.8 you can set ADK_MAX_LLM_CALLS.

1.x loop vs 2.0 loop

The Next '26 codelab uses LoopAgent(sub_agents=[researcher, judge, escalation_checker], max_iterations=3). The checker yields EventActions(escalate=True) on "pass".

In 2.0 the judge feeds a router, and the back-edge is the loop. Since 2.5, ADK rejects old orchestrators inside Workflow graphs.

bounded_critic.py · pattern composed from verified APIs

from google.adk import Context, Event, Workflow

MAX_ROUNDS = 3

def route_headline(node_input: Feedback, ctx: Context):
    rounds = ctx.state.get("rounds", 0) + 1
    if node_input.grade == "tech-related":
        return Event(route="pass", state={"rounds": rounds})
    if rounds >= MAX_ROUNDS:
        return Event(route="give_up", state={"rounds": rounds})
    return Event(route="revise", state={"rounds": rounds})

root_agent = Workflow(name="bounded_critic", edges=[
    ("START", process_input, generate_headline,
     evaluate_headline, route_headline),
    (route_headline, {"revise": generate_headline,
                      "pass": publish,
                      "give_up": human_review}),
])
Step 1 shows the danger: the critic keeps saying "unrelated", the token circles the back-edge, and the LLM-call counter climbs by two per lap, one call for the generator and one for the critic. Interview drill: control what the model sees and remembers

Name four context failure modes. How does a graph limit poisoning?
Poisoning, distraction, confusion and clash (Breunig). In a Workflow graph each node sees only its node_input, and include_contents='none' gives a sub-agent no caller history. So a bad fact stays inside one node and does not spread to every later call.
preload_memory or load_memory: which, and when?
preload_memory searches on every turn: predictable, but it costs tokens and latency each turn. load_memory is a tool, so the model searches only when it needs past context. Neither one writes memory: call add_session_to_memory, usually in after_agent_callback.
Why can the current time in the system instruction raise cost about 10x?
It changes the prefix on every call, so the KV/context cache never hits. Manus pays $0.30 per MTok for cached input and $3 for uncached input. Put stable text in static_instruction and dynamic data in the tail of the context.
Skill, rule, tool or sub-agent: what is the difference?
A rule is always-on guidance. A skill is an on-demand folder of know-how, loaded by progressive disclosure. A tool is one callable function. A sub-agent is a separate context with its own prompt, tools and model, and it returns a summary.

Watch the context bars. Step one: the lead plans and fans out; each worker burns its own large window (about 50k tokens) on search. Step two: each worker returns only a small summary, so the lead's bar stays thin. That is context isolation, and in 2026 it is the main reason to use subagents. Step three: only the lead writes the artifact; parallel writes by workers are the Flappy Bird failure, where two children make conflicting hidden decisions. Analogy: many researchers read in the library, one editor writes the book. Interview question: "When does multi-agent pay off?" For high-value, parallel, read-heavy tasks with a strong verifier, and only if the task can pay about 15 times the tokens of a chat.

A generator-verifier loop converges only as fast as its verifier is trustworthy

verified_sql.py · guard node with a routed back-edge

from google.adk import Agent, Event, Workflow
from pydantic import BaseModel
class Draft(BaseModel):
    sql: str
    attempts: int = 0
writer = Agent(name="sql_writer", model=MODEL, output_schema=Draft,
    instruction="Write a BigQuery SQL query. Return only SQL.")
MAX_ATTEMPTS = 3

def sql_guard(node_input: Draft):        # verifier: plain code
    sql = node_input.sql.strip().upper()
    if sql.startswith("SELECT") and "DELETE" not in sql:
        return Event(route="PASS", output=node_input)
    if node_input.attempts + 1 >= MAX_ATTEMPTS:
        return Event(route="GIVE_UP", output=node_input)
    return Event(route="FAIL", output=node_input.model_copy(
        update={"attempts": node_input.attempts + 1}))

root_agent = Workflow(name="verified_sql", edges=[
    ("START", writer, sql_guard),
    (sql_guard, {"PASS": run_query, "FAIL": writer,
                 "GIVE_UP": escalate_to_human})])

Anthropic Harness design for long-running apps (2026-03-24): self-evaluation is lenient
Follow the token. The writer drafts SQL, and sql_guard is plain code, the cheapest trustworthy verifier. Press: attempt 1 starts with DELETE, so FAIL sends the draft back with the reason. Press: attempt 2 fails too. Press: attempt 3 hits MAX_ATTEMPTS, the FAIL edge closes and the run goes to a human. Press: a new request passes on the first attempt and runs. Graph cycles in ADK 2.0 have no built-in cap, so the counter in the draft is the stop condition. Analogy: a student who grades their own exam gives a high mark; a separate examiner with an answer key does not. Interview question: "Why should the evaluator be a different agent, or code, than the generator?" Self-evaluation is lenient (Anthropic's harness study: 20 minutes and $9 gave a broken game, 6 hours and $200 with a separate evaluator gave a working one), and code gives objective feedback.
