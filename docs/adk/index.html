Start with the one-sentence answer to the interview question "What is ADK 2.0?": it is a graph-based Workflow Runtime, and agents, tools and functions are all nodes, because BaseAgent now subclasses BaseNode. Follow the token. On the billing route, plain functions do the data-determined steps, and a RequestInput node waits for a human. On the general route, one Agent works alone inside a bounded LLM island. Google gives the reason in "Why we built ADK 2.0" (Google Developers Blog, 2026-07-01): "For production-grade reliability, you need full deterministic control over your application flow." Analogy: the graph is the railway track and the switches. The model is the driver who reads the signals at each station. Likely question: "Is this only LangGraph again?" Answer: explicit edges are a shared idea. In ADK, node input and output are typed, the graph is validated when you construct it, and HITL pause and resume come from the session event log. The node colours match the adk web graph view: amber RUNNING, violet WAITING, green COMPLETED.

Interview drill: defend when an agent is worth its cost

Workflow or agent for a refund process?
A workflow spine. The path is data-determined, it has irreversible side effects and it needs an audit trail. Use an LLM node only for the unstructured complaint. Google: “If you can clearly map the workflow, use determinism.” Its illustrative refund run went from 5,152 to 2,265 tokens.
A 20-step agent is 95% reliable per step. What is the end-to-end success, and what do you change?
About 36% (0.9520). Put cheap verifiers after the risky steps, hard-code the data-determined edges and remove steps. Each removed or verified step raises the product.
Why did the single growing ReAct prompt fail on long tasks?
Context rot: Chroma (2025-07-14) found that all 18 tested models degrade as input grows. Attention is an n² budget, and tool output piles up in the window. Modern harnesses move state into files, memory and subagents, and each call gets a compiled view.
What is harness engineering, and who named it?
Mitchell Hashimoto, 2026-02-05: each agent mistake triggers an engineered fix in the environment, so the mistake does not repeat. Böckeler splits the controls into guides (feedforward) and sensors (feedback), each computational or inferential. In ADK, each failure becomes an eval case and a CI gate.
Doc Why we built ADK 2.0 Doc Chroma, Context Rot Doc Hashimoto

ADK 2.0 replaced the agent tree with a graph engine and kept the 1.x features as its base

The docs call 2.0 the move “from a hierarchical agent executor to a graph-based execution engine”. “Agents, Tools, and Functions are evaluated as individual nodes within a workflow graph.”

In Python, BaseAgent subclasses BaseNode.

  • 2.0: code owns the edges. START, function nodes and routers sit between the agents. A return value is the next node's input.

Interview drill: explain the ADK 2.0 runtime without hand-waving

What is the difference between a plugin and a callback? What does a non-None return from before_model_callback do?
A callback acts on one agent. A plugin is a named BasePlugin class on the App. It runs first, for every agent, model and tool call. A returned LlmResponse skips the LLM call, the later plugins and the agent callbacks. Use this for caches and guardrails.
Which state prefix do you use for a user's cart and for scratch data? When is a write persisted?
Use user:cart: all sessions of that user in the app share it. Use temp:x for scratch: ADK never persists it. A write is committed only after the Runner processes the yielded event that carries its state_delta. Before that, local code can see a dirty read.
What breaks when you upgrade from ADK 1.x to 2.0?
Events get node_info and output. Rigid DB tables and strict validators fail, so upgrade all readers first and use adk migrate session. Overrides of _run_async_impl are ignored. session.events.append breaks determinism: yield the event. A broad except stops retries, and catching BaseException traps NodeInterruptedError.
Where do you register plugins in ADK 2.x Python? How do you add one to a YAML-only agent?
Put them on App(plugins=[...]), then build Runner(app=app). Runner(plugins=) is deprecated, and both together raise ValueError. AgentConfig has no plugins key, so pass adk web --extra_plugins=…. These plugins run after the App's own plugins.

from google.adk import Agent, Event, Workflow
from pydantic import BaseModel

city_generator_agent = Agent(name="city_generator_agent",
    model="gemini-flash-latest",
    instruction="Return the name of a random city. "
                "Return only the name, nothing else.")

class CityTime(BaseModel):
    time_info: str  # time information
    city: str       # city name
def lookup_time_function(node_input: str):
    return CityTime(time_info="10:10 AM", city=node_input)

city_report_agent = Agent(name="city_report_agent",
    model="gemini-flash-latest", input_schema=CityTime,
    instruction="It is {CityTime.time_info} in {CityTime.city} right now.")
def completed_message_function(node_input: str):
    return Event(message=f"{node_input}\n WORKFLOW COMPLETED.")

root_agent = Workflow(name="root_agent", edges=[
    ("START", city_generator_agent, lookup_time_function,
     city_report_agent, completed_message_function)])

Every node runs the same three phases

  1. Validate node_input against input_schema. Dicts are coerced into the model.
  2. Run the user logic: a function, an Agent, a BaseTool or a nested Workflow.
  3. Normalize each yield: None is dropped, an Event passes, a RequestInput becomes an interrupt, any other value becomes Event(output=value).

Four Event fields carry the run

outputData for the next node. Only one per node run.
messageContent that the user sees.
stateA delta that the session saves.
routeThe branch to take (next slide).

The hand-off is the return value. You do not need session state for it.

Workflow(...) checks 10 rules at construction

  • Unique node names. Reuse one instance to loop back.
  • START is present, with no incoming edges and no routes.
  • Every node is reachable. No unconditional cycles.
  • output_schema equals the successor's input_schema (often from type hints).
  • An LlmAgent(mode='chat') only directly after START.

The check is structural, not behavioural.

A router emits a route label, and only the matching edge fires

A node yields Event(route=v). The value v is a str, int or bool. A routing dict maps v to the next node.

The router emits "BUG". Only the edge with the key "BUG" fires. The other branches do not run.

A list route fans out: Event(route=["BUG", "LOGISTICS"]) starts every matching branch.

No match and no default: the branch ends silently. ADK writes only a log warning. Other branches continue.

DEFAULT_ROUTE (the literal "__DEFAULT__") fires when a route is emitted and no key matches. Since 2.10 it can fan out.

Fan-out runs branches in parallel, and a JoinNode waits for every one of them

  • A tuple of nodes inside a chain is a parallel fan-out.
  • JoinNode sets _requires_all_predecessors → True. It emits one dict keyed by predecessor node name.
  • Compact form: (START, (word_count, shout), join, report). Then report reads node_input['shout'] and node_input['word_count'].
  • Without a join, the successor runs once per predecessor (sample multi_triggers).
  • Map over a runtime list: @node(parallel_worker=True) or Agent(..., parallel_worker=True). One run per item. The next node gets a list.
  • max_parallel_workers caps the per-item concurrency. Here it is 2: two run, two wait.
  • Codelab level L4a sizes the fan-out at runtime. Level L2a uses a fixed tuple and a JoinNode.

Workflow(max_concurrency=2) caps graph-scheduled nodes only. ctx.run_node children are exempt: “throttling them would cause deadlock”.

5–30model calls per run, L4b fan-out

“A graph cycle is not bounded automatically.”

Construction rejects only unconditional cycles. A conditional cycle has no max_iterations. Each pass re-activates the node “with a fresh lifecycle”, and node_info.path shows the pass, e.g. request_input@1/request_human_review@2.

Interview drill: design and debug an ADK 2.0 graph

How do you branch, and what happens to a route with no matching edge?
Yield Event(route=...) and map routes in a dict. An unmatched route ends the branch silently, with only a log warning. Add DEFAULT_ROUTE ("__DEFAULT__"). Constrain LLM routers with a Literal output schema, or use a ClassifierNode with a threshold.
Why can a graph cycle run forever, and how do you bound it?
Construction rejects only unconditional cycles. A conditional cycle has no max_iterations. Keep a round counter in ctx.state with a give_up route, or use a dynamic @node with a for bound. Backstop: max_llm_calls (default 500).
Graph workflow or dynamic workflow?
Graph for declarative flows: 10 construction rules check it, and adk web draws it. Dynamic (ctx.run_node, while, gather) for recursion and data-dependent loops. The parent needs rerun_on_resume=True. Deterministic child run ids are the checkpoint keys.
Two terminal nodes both produce output. What happens?
The run fails with WorkflowConfigurationError (“multiple terminal nodes produced output”), because the engine cannot choose the workflow output. Join them with a JoinNode. It emits one dict keyed by predecessor node name.

Name four context failure modes. How does a graph limit poisoning?

When do you use preload_memory, and when load_memory?

It changes the prefix on every call, so the KV/context cache never hits. Manus pays $0.30 per MTok for cached input and $3 for uncached input. Put stable text in static_instruction and dynamic data in the tail of the context.

from google.adk import Agent, Event, Workflow
from pydantic import BaseModel
class Draft(BaseModel):
    sql: str
    attempts: int = 0
writer = Agent(name="sql_writer", model=MODEL, output_schema=Draft,
    instruction="Write a BigQuery SQL query. Return only SQL.")
MAX_ATTEMPTS = 3

def sql_guard(node_input: Draft):        # verifier: plain code
    sql = node_input.sql.strip().upper()
    if sql.startswith("SELECT") and "DELETE" not in sql:
        return Event(route="PASS", output=node_input)
    if node_input.attempts + 1 >= MAX_ATTEMPTS:
        return Event(route="GIVE_UP", output=node_input)
    return Event(route="FAIL", output=node_input.model_copy(
        update={"attempts": node_input.attempts + 1}))

Eval-driven development: the eval suite is the spec

  • Start with 20 to 50 tasks taken from real failures.
  • Use one vocabulary: task, trial, grader, transcript, outcome.
  • Grade the outcome: the reservation exists in the database. Add trajectory checks only where the path matters.
  • Capability evals start low. Regression evals stay near 100%.
  • Read the transcripts. A 0% pass@100 usually means a broken task, not a weak agent.

pass@k: at least one of k trials succeeds. pass^k: all k trials succeed. At 75% per trial, pass^3 = 0.75³ ≈ 42%. A customer-facing agent needs pass^k.

Rubric judges: judge_model_options: {judge_model, num_samples: 5} samples the judge five times and takes the majority vote. Per-case rubrics merge with criterion rubrics.

  • Tier 1, every PR: deterministic checks and trajectory.
  • Tier 2, nightly or on release: rubric judges, multi-run.
  • Tier 3, online: judges on sampled production traffic.

Judge scores are noisy. Gate on the delta against the main baseline (agents-cli eval compare). Keep absolute floors for safety and must-pass cases.

Do not change thresholds and prompts in the same PR.

Interview drill: prove your agent is reliable and safe

A step fails. Do you use RetryConfig, a routed back-edge or ReflectAndRetryToolPlugin?
RetryConfig for exceptions and transient faults: backoff from 1 s to 60 s, completed children are replayed, and the model sees nothing. A back-edge for semantic failures, where the output is valid but wrong: it carries the verifier's reason as feedback and needs a round counter, because graph cycles are not bounded. ReflectAndRetryToolPlugin for tool errors that the model can fix: it sends reflection_guidance, allows 3 retries by default, and needs an extract_error_from_result override for soft errors like {"status": "error"}.
What is the difference between EXACT, IN_ORDER and ANY_ORDER trajectory matching?
EXACT allows no extra and no missing calls. IN_ORDER needs the expected calls in order but allows extra calls. ANY_ORDER ignores the order. EXACT fails on a harmless extra lookup and makes a better plan look worse, so keep it for strict, regulated flows. Add ignore_args or a rubric tool-use metric when the arguments can vary.
For a customer-support agent, do you report pass@k or pass^k? Why?
pass^k: every attempt must succeed, because each customer gets one attempt. At 75% per trial, pass^3 = 0.75³ ≈ 42%, while pass@3 ≈ 98% looks fine. In ADK, set multi_run_config with num_runs: 3 and min_over_runs, or pass_rate with a threshold when some flakiness is acceptable.
Apply the Rule of Two to an email assistant that reads the inbox and can send mail.
It has all three: untrusted email [A], private data [B] and an external send [C]. Drop one per session: a read-only summarizer, or a send tool limited to allow-listed recipients. If the task needs all three, put a RequestInput approval on each send. Then add layers: ModelArmorPlugin, user identity read from trusted state (never from model arguments), egress policy, and output escaping in the UI.

Ship only when the checklist holds: simple design, owned context, verified steps, measured runs

Design

  • Wrote it as a workflow first. An eval justifies each agent loop.
  • One agent with tools before multi-agent.
  • Prototype on the most capable model. Then downshift per step with evals.

Instructions

  • Right altitude. Structured (XML or Markdown). Critical items first.
  • Few canonical examples. No contradictions. Current date stated.
  • Prompts versioned and reviewed: “a prompt change is a deploy”.

Tools

  • Few, namespaced tools, shaped around workflows.
  • Readable, paginated returns. Actionable errors.
  • Every tool risk-rated. High risk → confirmation.

State and context

  • Event-sourced and resumable.
  • Scoped state: temp:, session, user:, app:. Artifacts for binaries.
  • Static prefix first. Caching and compaction configured.

Reliability

  • Bounded retries with backoff. A failover model.
  • max_llm_calls and timeouts set.
  • Idempotent tools. No broad except.

Security

  • Rule of Two per session, or HITL.
  • Identity from trusted context, never from model arguments.
  • Layered guardrails. Dependencies pinned.

Evals and ops

  • 20–50 real-failure tasks, outcome-graded, pass^k reported.
  • Capability and regression suites kept apart.
  • OTel tracing, dashboards, eval-gated CI/CD with canary.
  • Pinned model IDs: aliases like gemini-flash-latest drift.

Multimodal

  • Minimum resolution per item.
  • Files API IDs or artifacts inside loops, not base64.
  • Text inside media is untrusted input.

Interview drill: run an agent in production on Google Cloud

Agent Runtime, Cloud Run or GKE?
Agent Runtime for managed sessions, Memory Bank, Agent Identity, A2A and publishing to Gemini Enterprise with the least ops. Cloud Run for a custom FastAPI surface and revision traffic splitting. GKE for GPUs or self-hosted models. Cloud Run and GKE can still use managed Sessions and Memory Bank through agentengine:// URIs.
How do you canary a new agent version safely?
Deploy with --no-traffic --tag. Run the eval suite against the tag URL. Shift 1 → 5 → 25 → 100% with session-sticky routing. Watch error rate, p99, tokens per invocation and judge score. Roll back with --to-revisions PREV=100. Never shadow with live write tools.
Name three agent SLIs that a web SRE does not track.
Tokens per invocation, LLM calls per invocation (the loop signature) and an online judge or task-success score. A fourth: tool error rate by tool_origin (LOCAL, MCP, SUB_AGENT, A2A), which blames an upstream MCP server.
What in ADK 2.13 can silently break your monitoring?
OTel GenAI v2 became the default, and the call_llm span was removed. Dashboards and alerts keyed on call_llm go blank, so detection itself fails. Update them to generate_content, or set ADK_TELEMETRY_SCHEMA_VERSION_OPT_IN=otel_semconv_1_36.
